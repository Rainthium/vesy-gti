## Жёсткие рамки

1. **АИС «СВХ» не меняется.** Ответы и события АИС остаются байт-в-байт: новые поля документа (`weighed_at_utc`, `scale.kind`, `site.customs_code`) — только в таможенном варианте документа. Обязательный тест-фиксатор: документ v2 для АИС до и после доработки совпадает.
2. **Только центр.** Агенты не обновляются.
3. **Центр не объявляет топологию у таможни.** У `vesy-center` нет прав configure и read: никаких `declare_exchange` / `declare_queue` / `bind` — только публикация в существующий exchange (в aio-pika: `channel.get_exchange(name, ensure=False)`). Нынешний `RabbitBroker` объявляет топологию — для таможни нужен отдельный класс.
4. **Токен таможни — только чтение.** Им нельзя слать команды взвешивания (`POST /api/v2/weighings`) и привязывать `ais_ref`.
5. **В таможню не идут:** перенесённые тарирования (`source=imported`), записи-сторно как отдельные операции (сторно — событием `weighing.reversed` по исходной записи).
6. Публикатор — фоновая задача процесса центра (uvicorn одним воркером), как публикатор АИС.
7. Перед каждым коммитом: субагент reviewer + `uv run ruff format . && uv run ruff check . && uv run mypy . && uv run pytest -q`. Пуш — через терминал Игоря. Выкат на ВМ — только после зелёного CI и с бэкапом БД.

## Разбиение по заходам

Одним заходом не делается: шаги 9–10 зависят от Таргет-центра и от двухнедельного прогона. Код (шаги 1–7) — два-три захода, каждый заканчивается зелёными проверками и коммитом:

1. **Заход А** — шаги 1, 2, 3, 6: данные, документ, постановка событий, отказы. Наружу ничего не видно, выкатывать можно без риска.
2. **Заход Б** — шаги 4, 5, 7: чтение для Таргет-центра, публикатор, панель и мониторинг.
3. **Заход В** — шаг 8: выкат в тестовом режиме и первое сообщение.

Дальше — короткие заходы по событиям: замечания теста, коды, TLS, история, боевой поток.
