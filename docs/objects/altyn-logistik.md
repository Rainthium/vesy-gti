## Весы и индикатор — протокол «D2008F», ТРЕТИЙ ТИП ИНДИКАТОРА

Пресет протокола в UniServer называется **«D2008F»** — по имени это индикатор **Keli D2008F(A)**
(Keli Sensing, Китай — очень распространён на автомобильных весах; подтвердить фото шильдика).
Драйверы cas22 и vesar НЕ подходят — **нужен третий драйвер агента** (реестр `agent/drivers/DRIVERS`
расширяем, задача этапа 2 «другие CAS/Keli» предугадала).

Разметка WeightIndicator1 (глазами UniServer; байты [8..10] не размечены — вскрыть живым дампом):

- Пакет **12 байт**: `[0]`=`0x02` STX · `[1..7]`=**масса, СТРОКА 7 символов** (UniServer парсит
  как есть) · `[8..10]`=**не размечены** (возможны статус/точка/КС — покажет дамп) · `[11]`=`0x03` ETX.
- Контрольная сумма в UniServer **не используется** (CRCType=0); знак минус не определяется;
  **флага стабильности в разметке нет** — вычисляется программно (успокоение **2 с / 3 дискреты**;
  на Кара-Суу для vesar было 1 с / 3 — наши параметры выберем по дампу).
- Поток непрерывный: запросов нет (Request 0), команд инициализации/обнуления нет — как cas22/vesar.
- Порт **COM3**, 9600 8-N-1, поток None, **DTR/RTS не поднимать**; переоткрытие порта при ошибке
  включено (по отсутствию данных — выключено). Переходник COM3 (PCI/USB) — уточнить на месте.
- `Massa_Discret` в UniServer = **10 кг**, но **все 20 значений журнала кратны 20 кг**
  (40240, 39200, 33900… — вероятность случайности ~2⁻²⁰) → **фактическая дискретность весов,
  похоже, 20 кг** (огрубляет сам индикатор, вес приходит уже кратным 20 — не как на Д-А, где
  огрублял UniServer). Уточнить по шильдику: от d зависят пороги цикла и критерий сверки.
- Модель самих весов неизвестна (НПВ ≥ 44 т по журналу, вероятно 60–80 т) — фото шильдика весов.

## Весовой ПК и UniServer

- UniServer на `http://192.168.174.240:8087` → IP весового ПК **192.168.174.240**. Версия
  UniServer, имя ПК, Windows, диск для агента (C:/D:), антивирус — уточнить при установке.
- **SERIALTCPIP1 включён** (скриншот: «Выполняется», получено 0 Б/с — источник не настроен),
  в выгрузке модуля нет — ровно как на Кара-Суу. Рецепт готов: для дампа — `Mode=Client` на
  рабочее место (брандмауэр весовых ПК режет входящие), для боя — `Mode=Server, Host=127.0.0.1,
  Port=4001, SourceRepeaterSerialPort=SerialPort_WI1` → агент `socket://127.0.0.1:4001`;
  com0com не пробовать вовсе (урок 19.08).
- Журнал SQLite, нумерация `%.6d` в пределах года, последний документ **005420** от 26.08.2026
  11:21 → **~23 документа/день** (средняя загрузка; К-С ~49). Объект **круглосуточный**
  (записи 02:19, 03:21, 03:59 ночи).
- **Все операции журнала — «Вручную оператором», тип БРУТТО, тара/нетто 0, номера ТС пустые**:
  двойное взвешивание и тары на объекте фактически не используются (режим Double настроен,
  но не применяется), автовзвешивание выключено (glob_AutoMode=0), документы не создаются
  (Never), автопечать выключена. Печатают «Накладную отвеса» вручную.
- Поверка в UniServer не заполнена (`Report_ScaleDoc` пуст) — у нас данные есть (№217, выше).
