## 1. Что такое UniServer AUTO (текущая система, которую заменяем)

ПО «ВесыСофт» (vesysoft.ru), продукт «АСУ АвтоВесы». Модульный веб-сервер под Windows: ядро + плагины, у каждого плагина есть страница настроек и Web-API. Документация: https://docuwiki.vesysoft.ru/doku.php?id=webapi:uniserver_auto

Модули, реально запущенные на Кызыл-Кые (видел список): `SERIALPORT1`, `SERIALPORT_WI1` (COM-порт индикатора), `SERIALTCPIP1`, `STORETABLE` (справочник мест хранения), `TRANSPORTTABLE` (справочник транспорта), `WEIGHTINDICATOR1` (весовой индикатор), плагин `AutoScale1` (логика взвешивания «Весы 1»), камеры (2 шт.), журнал взвешиваний.

Веб-интерфейс UniServer на Кызыл-Кые: `http://127.0.0.1:8087/` (порт **8087**, совпадает с полем `port` в запросе АИС).

### Web-API UniServer (пригодится для чтения его данных на переходный период)

Авторизация — query-параметры `auth_user`/`auth_password`. Два способа вызова: `GET /core/SendMsg?Name=<Плагин>_<Метод>` или `GET /core/plugins/<Плагин>/<Метод>`.

- **WeightIndicator1**: `Massa` (текущий вес), `Parameters` (JSON: вес, флаг стабильности, состояние подключения, имя протокола), `PressZero` (обнуление).
- **AutoScale1**: `Enable`, `SetAutoMode` (автомат вкл/выкл), `Parameters` → JSON вида `{"Name":"Весы 1","Enable":true,"StateName":"WeighingComplete","StState":"Взвешивание завершено","Massa":55.09,"Stabil":true,"modeAuto":true,"Precision":2,"WeighingResult":{...}}`. Состояние `WeighingComplete` = взвешивание завершено.
- **Журнал (AutoScaleJournal1)**: `GetRecords` (фильтры Range/Like/Equal по полям, SortField, FirstRow/MaxRows), `GetRecord` (по CODE), `GetRecordCount`, `GetBlobs`/`BlobDATA` (фото по CODE записи + NAME файла), `BlobThumb` (миниатюра 64×64), `GetDocLink` (связанные записи ТАРА↔БРУТТО), `LastFetched` (точка синхронизации). Времена — ISO 8601.

Пример фильтра журнала: `{Filter:{DateTime_Create:{Range:["2020-08-01T05:08:26.086","2020-09-01T00:00:00.000"]}},MaxRows:100}`.

### Настройки AutoScale1 «Весы 1» — сняты со скринов боевой системы (07.08.2026)

**Основные настройки:**
- Тип весов: «Автомобильные с полным заездом ТС на платформу».
- Режим взвешивания (определение НЕТТО): **«Тара из базы (один отвес — Брутто, Тара из ранних отвесов)»**.
- **НмПВ: 20 дискрет = 200 кг** (дискрета 10 кг) — вес ниже игнорируется. Это и есть «порог пустых весов» для нашего конфига.
- Разрешить загрузку транспорта на весах: выключено.
- Двукратный режим: период актуальности 1-го взвешивания **48 часов** (в этом режиме первый отвес считается незавершённым).
- Режим «Тара из базы»: допустимое отклонение тары 6 дискрет = 60 кг; период актуальности тары в UniServer — 100 дней. ✅ РЕШЕНИЕ (Игорь, 07.08.2026): в новой системе тара действует **3 месяца**, как в АИС (значение конфигурируемое, по умолчанию 3 календарных месяца).

**Идентификация транспорта:** распознавание номеров и считыватели меток — не используются (номер вводит оператор). Подтверждает решение «распознавание не делаем».

**Отчётность и печать:** формат PDF; тип документа печати — **«Отвес»** (талон); автопечать выключена; дислокация «СВХ ГП „ТИ“ „Кызыл-Кыя“». Для нашей печати талона использовать НОВОЕ название организации (ОАО «ГТИ»).

**Оборудование:** весовой индикатор WeightIndicator1; **фотофиксация с 4 источников** — Camera1–4.GetFrameJpg (не 2! в контракте АИС отдаются только front/rear, но снимков делается до четырёх ❗уточнить у Игоря: снимать в новой системе 2 или 4). Датчики присутствия ТС — не используются.

**Журналы:** журнал отвесов AutoScaleJournal1 + журнал документов DocsJournal; авто-создание документа — «При ручном взвешивании» (документ = связка ТАРА+БРУТТО на основе одного/двух отвесов — отсюда колонки «№» и «Документ» в журнале). **Автопополнение справочника транспорта: включено, после 4 повторяемых отвесов с одинаковым номером ТС** тара пишется в справочник ТС.
- ✅ РЕШЕНИЕ (Игорь, 07.08.2026): механику UniServer «тара из справочника» и ручное занесение в справочник в новой системе **НЕ воспроизводим**. Единственный источник тары — тарирования, проведённые через систему (реестр тарирований, ≤3 мес). Процесс строго по архитектуре: при сети — всё только из АИС «СВХ»; без сети оператор лишь выбирает «Взвесить/Оттарировать» и вводит **только номер АТС и номер прицепа** — массы система берёт сама, ничего больше оператор не вводит.

**Автоматическое взвешивание:** ВЫКЛЮЧЕНО (оператор/АИС инициирует). Параметры на будущее: источник события `AutoScale1.StateReadyWeighing`, время стабильной фиксации события **5 сек**. ЖД-вагоны и датчики вагонов — не используются.

**Определение осей:** расчётная осевая нагрузка 10 т, режим «По заезду», порог оси 50 (по умолчанию). Для этапа 1 осевые нагрузки не реализуем; параметры записаны на будущее.

**Итог для конфига агента (Кызыл-Кыя):** порог пустых весов 200 кг (НмПВ = Weighing_MinMassa 20 дискрет), стабильность фиксации 5 с (glob_AutoModeTimeOut), дискретность 10 кг, актуальность тары 90–100 дней (согласовать), допуск отклонения тары 60 кг (6 дискрет), **фото — 2 шт.**, тип цикла — полный заезд, ручной запуск.

## 3. Интеграция с АИС «СВХ» — как работает СЕЙЧАС

Цепочка: **АИС «СВХ» → скрипт-маршрутизатор (наш, самописный) → UniServer нужного объекта**. Оператор АИС выбирает вкладку («Взвешивание» или «Тарирование») и жмёт «Взвесить» — по вкладке АИС сама определяет тип операции. При взвешивании АИС подставляет последнее тарирование этого ТС **не старше 3 месяцев** и считает нетто.

Запрос АИС к скрипту (реальный образец):

```json
{
  "ip_address": "192.168.150.185",
  "port": 8087,
  "username": "admin",
  "password": "admin",
  "autoscale": 2
}
```

Ответ (реальный образец):

```json
{
  "code": "OK",
  "massa": 43310.0,
  "weighing_datetime": "2025-04-16T15:59:26",
  "unit_meas": "kg",
  "front_image": "/vesy/2025/04/16/913cb979ae034d0eb4748278d9f4cfcf_photo1.jpeg",
  "rear_image": "/vesy/2025/04/16/913cb979ae034d0eb4748278d9f4cfcf_photo2.jpeg"
}
```

Что известно точно: АИС забирает фото **своим сервером** и проксирует пользователям (подтверждено Игорем) — значит скачивание server-to-server. `weighing_datetime` — локальное время **Asia/Bishkek (UTC+6, без перехода на летнее)**, без указания пояса; в новой системе хранить в UTC, наружу отдавать локальное в том же формате.

Что НЕ известно: точный URL/метод/заголовки запроса АИС к скрипту; тексты `code` при ошибках; с какого хоста/порта отдаются фото; как скрипт общается с UniServer (предположение: через AutoScale1 Parameters/журнал — см. §1).

**РЕШЕНИЕ (Игорь, 07.08.2026): АИС «СВХ» на этапе разработки и пилота НЕ ТРОГАЕМ.** Интеграция с реальной АИС — отдельным шагом позже. Вместо неё делаем **имитатор АИС** — тестовый клиент (`tools/ais_client.py` + кнопка «Тестовое взвешивание» в панели центра), который шлёт запросы в формате v1 «как будто из АИС» и показывает ответ. Следствия: недостающие детали текущего контракта (точные тексты ошибок старого скрипта и т.п.) перестают блокировать разработку — наш v1-контракт (`docs/contracts/ais-api-v1.md`) становится эталонным, а при реальном переключении АИС сверим и, если нужно, добавим слой совместимости. Пилот на Кызыл-Кые идёт параллельно с UniServer, АИС продолжает работать через старую цепочку до момента переключения.

### Что мы РЕШИЛИ ПОМЕНЯТЬ в контракте (согласовано с Игорем, ждёт подтверждения АИС)

Полный контракт: `docs/contracts/ais-api-v1.md`. Кратко:

1. В запрос добавляется `operation`: `"weighing"` | `"taring"` (сейчас тип определяется вкладкой на стороне АИС; отсутствие поля = weighing).
2. В ответ взвешивания добавляются `tare`, `tare_datetime`, `netto` (расчёт нетто переезжает к нам; правило ≤3 мес; нет тары → `no_valid_tare: true`).
3. Коды ошибок — фиксированный перечень `ERR_*` (architecture §4.1) + русское `message`.
4. Фото: постоянные URL + сервисный токен АИС в `Authorization` + IP-allowlist; повторное скачивание старых фото — свободно в пределах 5 лет хранения.
5. Этап 2: события `weighing.completed` (включая досылку офлайн-операций) через существующий RabbitMQ организации, отдельный vhost.
6. Весовые данные первично хранятся в нашей системе (не только в АИС).
7. **Время — с явным поясом.** Всё время в системе — бишкекское (Asia/Bishkek, UTC+6, без сезонных переводов); в БД храним UTC. Отсутствие пояса в `weighing_datetime` текущего контракта признано ошибкой (Игорь, 07.08.2026): в новом контракте все даты-времена отдаются в ISO 8601 **с поясом** — `2026-08-07T17:53:59+06:00`.
