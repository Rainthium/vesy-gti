# Установка агента на весовой ПК (Windows)

Инструкция для установки `ves-agent` службой Windows. Копия этого файла
лежит в архиве сборки под именем `УСТАНОВКА.md`.

## Что понадобится

1. **Архив сборки** `ves-agent-<версия>-win64.zip` — со страницы релизов
   репозитория (тег `agent-v*`) или из артефактов workflow «Сборка агента».
   Запасной путь без GitHub: собрать на любой Windows-машине скриптом
   `packaging/agent/build.bat` (нужен только uv, он сам поставит Python).
2. **nssm** (менеджер служб): скачать с <https://nssm.cc/download>,
   из архива взять `win64\nssm.exe`.
3. **ffmpeg.exe** — ТОЛЬКО если камеры объекта не отдают HTTP-снапшот
   (не Hikvision, в конфиге камер один rtsp_url — как на Джалал-Абаде):
   официальная сборка ffmpeg-release-essentials с <https://www.gyan.dev/ffmpeg/builds/>,
   из архива взять `bin\ffmpeg.exe`, положить в папку агента и указать
   в конфиге `ffmpeg_path`. Кадры с таких камер агент берёт из
   постоянного RTSP-потока (agent/cameras/stream.py, с 0.4.7).
   Урок Кербена (10.09.2026): у камер Dahua пароль для HTTP-снапшота может
   отличаться от того, что стоит в RTSP-строке штатного ПО (ВесыСофт): рабочим
   оказался пароль из поля «Пароль» формы камер. Проверка с ВМ центра без пароля
   в командной строке — `curl --digest -u admin:$PW http://<ip>/cgi-bin/snapshot.cgi?channel=1`
   (PW читать из файла); Basic даёт 401 всегда, агент сам переходит на Digest.
4. Данные объекта: COM-порт индикатора, адреса и пароли камер,
   адрес центра и **токен агента** (выпускает центр; токены пилота лежат
   на ВМ центра: `~/agent-token-<объект>.txt`). Заведение объекта в центре —
   скриптом в контейнере app по образцу `provision_kerben.py` / `provision_kokcho.py`
   (лежат вне git в `docs/справка/выгрузка-<объект>/`): объект, весы, настройки
   (порт/скорость, цикл, ручной режим), поверка, камеры, агент → токен только в файл;
   пароль камер — через env `CAM_PW`, извлечённый из config.toml мастер-папки прямо
   на ВМ, чтобы не светить его в командах.

В архиве:

```
app\                  сборка агента (ves-agent.exe + _internal\)
config.example.toml   образец конфига (для Кызыл-Кыи — с адресами камер)
install-service.bat   установка службы (запускать от администратора)
update.bat            обновление на новую версию
УСТАНОВКА.md          этот файл
```

## Шаг 1. Разложить файлы

Создать `C:\vesy-agent` и распаковать туда содержимое архива — получится:

```
C:\vesy-agent\
  app\ves-agent.exe
  config.example.toml
  install-service.bat
  update.bat
  nssm.exe            ← положить сюда скачанный nssm
```

Каталог можно выбрать другой — скрипты привязаны к своему расположению,
но тогда поправьте пути `C:/vesy-agent/...` в конфиге (шаг 2).

## Шаг 2. Конфиг

Скопировать `config.example.toml` → `config.toml` и вписать реальные значения:

- `[scale] port` — COM-порт индикатора (Кызыл-Кыя: `COM5`).
- `[[cameras]]` — логин/пароль камер в URL (спецсимволы пароля — percent-encoding,
  `@` → `%40`). Пароли — из выгрузки объекта, в git их нет (правило №7).
- `[center] url` — адрес центра. Пилот: `ws://192.168.140.70/agents/ws`.
- `[center] token` — токен агента (см. выше).
- `[web] session_secret` — случайная строка (минимум 16 символов, лучше 32).
- `[web] host` — `0.0.0.0`: интерфейс оператора доступен из сети предприятия
  по IP весового ПК (решение для пилота); `127.0.0.1` — только с этого ПК.
- `[storage] photo_retention_days` — через сколько дней после подтверждённой
  загрузки в центр убирать локальный файл снимка (по умолчанию 30, `0` —
  не убирать). Снимки, ещё не принятые центром, не удаляются никогда.
  С агента 0.4.25 срок задаётся и из центра («Настройки» весов, поле
  «Хранить локальные фото»; пустое — действует локальный конфиг), а кнопка
  «Освободить» в строке «Диск ПК» на карточке весов убирает все уже принятые
  центром снимки сразу. Записи журнала не удаляются никогда (правило №2).
  После уборки журнал оператора показывает миниатюры из центра (с 0.4.26 они
  остаются на диске, а отказ центра помнится 10 минут); у записей, чьих копий
  в центре нет (старше чистки журнала центра), вместо снимка — прочерк, это
  не сбой.

Проверка конфига без запуска службы — из `cmd` в `C:\vesy-agent`:

```
app\ves-agent.exe --config config.toml
```

Агент запустится в консоли (Ctrl-C — остановка). Опечатка в конфиге
даст понятную ошибку валидации сразу при старте.

> **COM-порт и UniServer.** С 07.09.2026 ни один объект не работает
> параллельно с UniServer (АИС на центре, агенты на физических портах —
> способ 3 ниже); всё про параллельную работу оставлено для нового объекта,
> где UniServer ещё обслуживает АИС. Порт индикатора может держать только одна
> программа. Пока UniServer работает параллельно, агент получит ошибку
> открытия порта и будет показывать «нет данных» (сам переоткрывает порт
> и оживёт, как только порт освободится). Для одновременной работы нужна
> ретрансляция порта (com0com/hub4com) — настраивается отдельно на пилоте.

> Драйверы индикатора в `[scale] driver`: `cas22` (CAS CI-серии), `vesar` (VESAR, Keli D2008 —
> десятые кг, дискрета 10), `xk3190` (Yaohua XK3190-DS3/D2+ — тот же кадр, десятые кг,
> дискрета 20; агент 0.4.27+). Для vesar/xk3190 трактовку кадра можно перекрыть:
> `weight_divisor = 10` (десятые кг) или `1` (целые), `discrete_kg = 20` — по табло индикатора.
>
> Объект без подключённой АИС «СВХ»: админ ставит в панели («Настройки» весов) галочку
> «Ручной режим при связи с центром» — оператор взвешивает сам, записи уходят в центр сразу
> (агент 0.4.28+; исключение из правила №3, decisions 03.09.2026). Снять после подключения АИС.
>
> Лимит массы тарирования (агент 0.4.29+, decisions 04.09.2026): «Настройки» весов →
> «Лимит массы тары, кг» (умолчание 25 000, 0 — без лимита; локально — `[cycle] max_tare_kg`).
> Тяжелее лимита — тарирование не проводится: АИС получает `ERR_TARE_TOO_HEAVY` с текстом,
> оператор ручного режима — сообщение на форме. Тара не меньше брутто при взвешивании не
> подставляется (нетто пусто, причина в записи) — такое тарирование сторнируют из панели.
>
> Быстрая проверка ручного режима без машины (Кокчо-Коз, 03.09.2026): временно опустить
> пороги цикла в «Настройках» весов (пустые 20 / заезд 60), встать на платформу — кнопка
> «Взвесить» станет активной после стабилизации; затем вернуть боевые пороги (400/800),
> иначе человек на платформе будет считаться заездом.

### COM-порт и UniServer: два способа параллельной работы (история — до 07.09.2026)

Пока UniServer работает рядом с агентом, порт индикатора занят им. Есть два
проверенных способа отдать агенту тот же поток:

1. **Виртуальная пара портов com0com + ретрансляция UniServer в COM**
   (Кызыл-Кыя, Джалал-Абад): пара COMx↔COMy с галкой «use Ports class»
   (номера назначает Windows), в UniServer модуль SERIALPORT1 —
   `PortName = COMx`, `SourceRepeaterSerialPort = SerialPort_WI1`; агент
   читает `COMy`. Рецепт — `docs/uniserver-kyzylkia.md` §4.4.
2. **Ретрансляция UniServer в TCP, без драйверов** (Аламедин, 19.08.2026):
   на Windows 11 драйвер com0com (2012 г.) может не грузиться —
   `sc start com0com` → ошибка **577** «не удаётся проверить цифровую
   подпись» (Code Integrity). Тогда в UniServer модуль **SERIALTCPIP1**:
   `Mode = Server`, `Host = 127.0.0.1`, `Port = 4001`,
   `SourceRepeaterSerialPort = SerialPort_WI1`; проверка на весовом ПК —
   `netstat -ano | findstr :4001` показывает `LISTENING`. Агенту в
   `config.toml`: `port = "socket://127.0.0.1:4001"` (pyserial-URL; нужна
   сборка **0.4.20+** — раньше замороженный exe не знал протокол socket://).
   Перезапускать UniServer после настройки лучше службой
   (`sc stop UniServerAuto` → `sc start UniServerAuto`), а не кнопкой
   «Перезапуск сервера» в вебе — на Аламедине кнопка оставила сервер лежать,
   пока службу не запустили вручную.

В обоих случаях модуль SERIALPORT_WI1 (физический порт индикатора) не
трогать: UniServer продолжает обслуживать АИС как раньше. Когда АИС
переведут на центр — порт агента переключить на физический (из панели
центра: «Настройки» весов → COM-порт), см. способ 3. На пилотных шести
объектах это сделано 04.09–07.09.2026.

## Шаг 3. Локальные операторы

Ручной (офлайн) режим требует входа оператора. Завести учётки:

```
app\ves-agent.exe --config config.toml add-operator --login a.osmonov --full-name "А. Осмонов"
```

Пароль спрашивается интерактивно (минимум 8 символов, `admin/admin` запрещён).
Повторный запуск с тем же логином меняет пароль.

Основной путь — заводить операторов в панели центра (экран «Пользователи»,
роль «оператор»): они реплицируются на агентов сами. CLI — аварийный доступ;
с агента 0.4.14 заведённые так учётки видны администратору центра: экран
«Пользователи» → блок «Учётки на агентах», пометка «заведена на месте».

## Шаг 4. Служба

Запустить `install-service.bat` **от администратора** (правый клик →
«Запуск от имени администратора»). Скрипт создаст службу `ves-agent`
(автозапуск, перезапуск при падении, логи в `logs\agent.log` с ротацией)
и сразу её запустит. Имя службы он записывает в `service.txt` — по нему
агент при автообновлении останавливает именно свою службу.

Если интерфейс открыт в сеть (`host = "0.0.0.0"`) — разрешить входящий
порт в брандмауэре (от администратора):

```
netsh advfirewall firewall add rule name="ves-agent web" dir=in action=allow protocol=TCP localport=8090
```

3. **UniServer выключен насовсем** (Кокчо-Коз с 03.09.2026, Кара-Суу с 07.09.2026):
   агент читает физический порт сам. Переход с ретрансляции — только после
   перевода АИС на центр: выключить в UniServer модули `SERIALTCPIP1`,
   `SERIALPORT_WI1`, `WEIGHTINDICATOR1` (тумблеры модулей индикатора порт
   НЕ освобождают, пока включён SERIALTCPIP1), остановить и отключить службу
   (`sc stop UniServerAuto`, `sc config UniServerAuto start= disabled`), затем
   в панели центра «Настройки» весов → COM-порт = физический порт. Агент
   пробует новый порт 12 с и при молчании откатывается; итог (порт применён
   или откат) — в «Событиях» панели и Telegram, в аудите — `scale_settings`
   и `agent_config_status`. С агента 0.4.30 экран показывает живой порт
   сразу (до 0.4.30 — только после перезапуска службы), а сохранение
   настроек не сбрасывает наблюдение платформы, если пороги наблюдения не
   менялись (до 0.4.30 — сбрасывало: стоящей машине приходилось
   пересъезжать). Локальный `config.toml` править НЕ обязательно (решение
   Игоря 07.09.2026): порт из панели агент хранит в снимке настроек центра
   в своей БД, при старте снимок главнее config.toml, обрыв связи ничего не
   сбрасывает, неудачный порт в снимок не попадает; файл важен только при
   переустановке с чистой БД без связи с центром — тогда агент стартует на
   порту из файла и переключится при первом подключении. Мастер-папки
   объектов уже на физических портах.
   **Вариант без остановки службы** (Д-А, К-К, Аламедин, Алтын с 07.09.2026,
   решение Игоря): UniServer остаётся работать ради веба и архива —
   выключаются только модули индикатора и ретрансляции (`SERIALPORT_WI1`,
   `WEIGHTINDICATOR1`, `SERIALPORT1` или `SERIALTCPIP1`; порт освобождают
   именно тумблеры, и они переживают перезапуск службы — проверено на Д-А),
   а весовщики отсекаются удалением учёток кроме админской и сменой
   пароля. При желании выключить и `Camera1/2`, `Recognize1/2` — без
   индикатора они только держат потоки камер и грузят ЦП. Учётки удалять
   только после перевода АИС: одна из них — учётка АИС для старого
   контракта. Между выключением модулей и «Сохранить» в панели лучше
   уложиться в 3 минуты — иначе уйдёт алерт «Индикатор» (закроется сам).

### Проверка COM-порта из командной строки

Ответ агента при откате — «индикатор молчит на порту COMx» — один и для
занятого порта, и для пустого. Различает их проба из `cmd` на весовом ПК
(права администратора не нужны, порт открывается на 3 с):

```
powershell -NoProfile -Command "$port='COM5'; try { $p = New-Object System.IO.Ports.SerialPort $port,9600,None,8,one; $p.ReadTimeout = 3000; $p.Open(); $b = New-Object byte[] 64; $n = $p.Read($b, 0, 64); $p.Close(); $port + ' free, bytes: ' + $n } catch { $port + ': ' + $_.Exception.Message }"
```

- `COM5 free, bytes: 22` (больше нуля) — порт свободен, индикатор вещает:
  можно переключать из панели.
- «Доступ к порту закрыт» — порт держит другой процесс (обычно UniServer:
  модуль-ретранслятор ссылается на `SerialPort_WI1` и не отпускает порт,
  пока не выключен сам; крайний случай — `sc stop UniServerAuto`).
- «Время ожидания истекло» — порт свободен, но данных нет: не тот номер
  или индикатор выключен. Список портов —
  `powershell -NoProfile -Command "[System.IO.Ports.SerialPort]::GetPortNames()"`,
  номер USB-переходника — в диспетчере устройств («USB-SERIAL CH340 (COMx)»).
- «Присоединенное к системе устройство не работает» (ошибка 31) — завис
  USB-переходник CH340 (Кызыл-Кыя 07.09.2026). Программный сброс самого
  устройства (`Get-PnpDevice … | Disable-PnpDevice`, затем `Enable-PnpDevice`)
  не помогает — статус OK, ошибка та же; помогает сброс родительского
  USB-концентратора (тот же приём по `DEVPKEY_Device_Parent`; на 5 с
  отвалятся все устройства концентратора, для AnyDesk это не помеха),
  перетыкание USB на месте или перезагрузка ПК. После перезагрузки ничего
  делать не нужно: центр пришлёт порт из панели при подключении агента.
  Радикально — перейти на встроенный COM или плату PCI-E (WCH), как на
  Аламедине и Кара-Суу.

### Антивирус (обязательно при стороннем AV)

**AVG AntiVirus Free (Кербен, 10.09.2026):** «выключить навсегда» у него нет — защита
включается обратно сама, из автозагрузки службы не убираются. Решение Игоря — удалить:
Параметры → Приложения → AVG AntiVirus Free → Удалить (от администратора) → перезагрузка;
если не удаляется — утилита AVG Clear с avg.com. После удаления Защитник Windows включается
сам, ему ничего не нужно. Пока сторонний AV стоит — исключения на папку и файл `ves-agent.exe`
(ниже, урок 360).

Мелочь того же дня: имя ПК Кербена DESKTOP-GPQIS69 совпало с ПК Кокчо-Коза (клон образа
поставщика) — агенту безразлично (опознаётся токеном), но в инструментах удалённого доступа
объекты по имени не различить, ориентироваться по IP.

Боевой урок Джалал-Абада (12.08.2026): **360 Total Security** молча
блокировал автообновление — не давал неподписанному `ves-agent.exe`
записывать системную DLL (`ucrtbase.dll` в `app_new`), ошибка в журнале
агента: `Permission denied`. Белый список ПАПКИ не помогает — 360 решает
по репутации процесса-писателя.

Если на весовом ПК сторонний антивирус, добавить в его белый список
**оба пункта**:

- папку агента (`C:\vesy-agent` или `D:\vesy-agent`);
- **сам файл `...\vesy-agent\app\ves-agent.exe`** (в 360: Настройки →
  Белый список → «Добавить файл») — именно это разрешает его операции.

Симптом, что это снова оно: обновление кнопкой «ничего не делает»,
а в журнале агента `автообновление ... НЕ выполнено: Permission denied`.

С агента 0.4.8 файлы новой версии при автообновлении раскладывает не
сам процесс агента, а системные инструменты Windows (tar/PowerShell) —
им антивирусы доверяют; в бою при включённом 360 это прошло четыре
релиза подряд (0.4.9→0.4.13), блокировка ушла. С 0.4.13 инструмент
запускает сам агент дочерним процессом ещё до остановки службы
(быстрее и с честной ошибкой в панели), а при любой неудаче агент
автоматически откатывается на распаковку из задачи планировщика.
Боевой урок Джалал-Абада 18.08.2026 (обновление до 0.4.17): при БЕЛОМ
СПИСКЕ на месте (папка + exe) 360 всё равно резал уже дочерние процессы
агента — в журнале агента `распаковка инструментом: tar вернул 1: … Can't
create '…\app_unpack\app\_internal\ucrtbase.dll'` и `schtasks /Create
недоступен: [WinError 5] Отказано в доступе`; агент честно ушёл на запасной
путь, но там тот же запрет — служба жива, версия старая, центру ошибка не
приходит (bat не докладывает). Лечение: в 360 «Настройки → Исключения»
добавить папку агента (и/или разрешить события за это время в отчёте
«Активной защиты»), после чего повторить кнопку — помогло сразу.

Вторая ловушка того же дня: обновление дошло до подмены папки, но `move app
→ app_old` сорвался, потому что в AnyDesk-сессии была ОТКРЫТА В ПРОВОДНИКЕ
папка `D:\vesy-agent\app` — служба перезапустилась прежней версией (bat
откатился). Перед нажатием кнопки закрывать окна Проводника/консоли в папке
агента; с 0.4.18 bat делает подмену с шестью повторами по 5 с.

Белый список всё равно рекомендуем: прочей работе
агента (фото, база, логи) антивирусы пока не мешали, но поручиться за
каждый нельзя. Если обновление не прошло, а в журнале агента спустя
15 минут появилась строка «служба так и не была перезапущена» —
подробности смотреть в `logs\update.log` на весовом ПК.

## Шаг 5. Проверка

1. `logs\agent.log` — строка «агент … запущен», без ошибок далее.
2. Интерфейс оператора: `http://<IP весового ПК>:8090` — вход, на главном
   экране вес с индикатора (или «нет данных», если порт занят UniServer).
3. Панель центра → «Объекты»: агент онлайн, статусы индикатора и камер.

## Обновление

Штатно агент обновляется **из центра** (панель → «Релизы», deploy/README §9):
релиз назначается каналу pilot/stable, и агенты канала получают команду
сами. Агент скачивает архив, проверяет его, дожидается свободных весов и
перезапускает службу задачей планировщика (`self-update.bat`); с 0.4.19
новая версия проходит **самопроверку** (веб-порт, связь с центром, поток
индикатора), и при провале или если служба не поднялась за 6 минут bat сам
возвращает прежнюю версию. Следы на диске: `app_old` — прежняя версия,
`app_failed` — сбойная сборка после отката (для разбора, убирается при
следующем обновлении), `update-context.json` / `update-check.ok` /
`update-check.fail` / `update-rollback.txt` — файлы протокола между агентом
и bat (живут минуты; застрявший файл безвреден — агент уберёт его при
следующем старте, доложив центру), `logs\update.log` — что делал bat.

Вручную (без центра):

1. Скачать новый архив, распаковать, папку `app` из него положить в
   `C:\vesy-agent` под именем `app_new`.
2. Запустить `update.bat` от администратора: он остановит службу, заменит
   `app` (старая версия останется в `app_old` для отката) и запустит снова.
   Конфиг, база `agent.sqlite3` и фото не затрагиваются.

## Второй агент на том же ПК (объект с двумя весами)

Одни весы = один агент (см. `docs/decisions.md`, 11.08.2026). Если на
объекте двое весов и оба индикатора заведены на один ПК, ставится второй
экземпляр агента — отдельной службой, рядом с первым. Общего у них только
компьютер: папка, конфиг, база, фото, веб-порт и токен — свои.

1. Разложить архив во **вторую папку**, например `C:\vesy-agent-2`
   (весь набор: `app\`, `nssm.exe`, `config.toml`).
2. В её `config.toml` задать: свой `agent_id` и `token` (агент выпускается
   в панели для ВТОРЫХ весов), COM-порт второго индикатора, URL его камер
   и **другой веб-порт** — например `port = 8091` в секции `[web]`.
   Одинаковый порт у двух агентов = второй не поднимется.

   **Обязательно переписать пути в `[storage]`** на свою папку:

   ```toml
   [storage]
   db_path = "C:/vesy-agent-2/agent.sqlite3"
   photos_dir = "C:/vesy-agent-2/photos"
   ```

   Пути в образце абсолютные, и если оставить их от первого агента, два
   агента сядут на одну базу и один каталог фото. Это не косметика:
   при старте агент удаляет из своего `photos_dir` снимки, которых нет в
   его журнале, — то есть сотрёт фото соседних весов (правило №2 —
   фото неприкосновенны).
3. Установить службу под своим именем — имя первым аргументом:

```
install-service.bat ves-agent-2
```

Дальше всё как обычно: в панели центра появятся две карточки весов, у
каждой свой статус и своя кнопка обновления; обновление одного агента
второго не трогает. Интерфейсы оператора — `http://<IP>:8090` и
`http://<IP>:8091`.

На стороне весового ПК под вторые весы нужна своя пара com0com и своя
ретрансляция COM в UniServer (как в `docs/uniserver-kyzylkia.md` §4.4) —
пока UniServer работает параллельно; без UniServer — просто свой
физический порт у каждого экземпляра.

## Удаление службы

```
nssm.exe stop ves-agent
nssm.exe remove ves-agent confirm
```

Если экземпляр не единственный — подставить его имя службы (оно записано
в `service.txt` рядом с конфигом).

Данные (`config.toml`, `agent.sqlite3`, `photos\`) остаются на диске.

## Превью камер Hikvision: не всякий «суб-поток» лёгкий

**Превью Hikvision (урок Канта 11.09.2026)**: у этой прошивки `/ISAPI/Streaming/channels/102/picture` и `103/picture` отдают тот же кадр 2560×1440 (300–355 КБ, 0,6–1,7 с), что и 101 — в быстром режиме превью (раз в секунду) браузер обрывал незавершённую загрузку, и картинка на экране оператора не обновлялась. Лечение: `preview_url` = `/ISAPI/Streaming/channels/102/picture?videoResolutionWidth=640&videoResolutionHeight=360` — камера отдаёт 640×360 (21–27 КБ, 0,15–0,26 с). На Канте поставлено в центре для весов №1 (агент получает при hello/сохранении в панели); снимки операций — по-прежнему канал 101 в полном размере. У Dahua тары `subtype=1` размер тоже не уменьшает (258 КБ, ~0,55 с) — пока терпимо. Проверять при обследовании: `curl … /channels/102/picture` и смотреть размер и разрешение (`file snap.jpg`); если оно равно основному — сразу брать URL с `videoResolutionWidth/Height`.

С агента **0.4.31** кадр превью ужимается самим агентом до 640 px (снимки операций не трогаются), при срыве одной съёмки 10 с отдаётся последний удачный кадр, срывы превью пишутся в `logs\agent.log` («превью камеры rear: …»), а страница оператора не запрашивает новый кадр, пока не догрузился предыдущий. `preview_url` по-прежнему полезен там, где камера отдаёт лёгкий кадр быстрее полного; если лёгкого кадра у камеры нет (Dahua Канта) — поле оставить пустым, превью пойдёт с основного снимка раз в 2 с.

## Превью не обновляется — порядок разбора (урок Канта 11–12.09.2026)

Разбирать снизу вверх, каждый шаг отсекает свой слой:

1. **Страница.** После обновления агента вкладка оператора продолжает работать старым скриптом — перезагрузить (F5). Вкладка не на переднем плане — браузер замораживает таймеры (в журнале агента запросы `/cameras/*.jpg` пачками с паузами ~80 с). С 0.4.32 на кадре превью есть плашка с временем съёмки: бежит — кадры свежие, проблема дальше по цепочке от агента к браузеру; стоит — свежих кадров нет.
2. **Журнал агента** (панель → карточка весов → «Журнал агента», или «Диагностика» на агенте). Строки `превью камеры: <роль>: <ошибка> (url)` — причина срыва (timed out / отказ соединения / не JPEG); `превью камеры <роль>: кадр снят за N с` — камера отвечает медленно; запросы `/cameras/*.jpg` без ответа минутами при живых `/fragments/*` — съёмка висит. Все `200 OK` при стоящей картинке — смотреть п. 1.
3. **Камера с ВМ** (другой маршрут — отсекает камеру и её настройки): `curl -s -o /dev/null -w "%{http_code} %{size_download}B %{time_total}s" --digest -u "$UP" URL` (учётка из файла, не в командной строке), размер/разрешение кадра (`file snap.jpg`), 25 запросов подряд в ритме превью, md5 пяти кадров подряд (все разные = кадры свежие). Тем же кодом агента: `agent.cameras.capture._http_snapshot` из контейнера app.
4. **Кадр слишком тяжёлый?** Hikvision может отдавать по 102/103 полный кадр — использовать `?videoResolutionWidth=640&videoResolutionHeight=360`; Dahua `subtype=1` кадр не уменьшает — preview_url не задавать (агент 0.4.31+ ужимает сам). Настройки камер доставляются агенту «Сохранить» в «Настройках» весов; подтверждение — лог контейнера app «настройки применены агентом».
5. **Путь ПК → камера.** Если с ВМ всё быстро, а у агента `timed out` — проблема между весовым ПК и камерой: с ПК `ping -n 20 -l 32 <камера>` против `ping -n 20 -l 1400 <камера>` (маленькие проходят, большие с потерями = линия/порт/дуплекс), `curl.exe --digest` с таймингом, `netstat -an | findstr <камера>`. RTSP-видео UniServer по UDP «работает» и при такой линии — не ориентир. Лимит подключений на камере проверяется выключением её RTSP-модуля в UniServer (на Канте не подтвердился). Обход для второго агента — поставить его на ПК рядом с камерами.
