## 1. Назначение и общая схема

Единая весовая система ОАО «ГТИ» (далее — весовая система) заменяет UniServer AUTO и скрипт-маршрутизатор на 13 объектах: на каждом весовом ПК работает агент (читает индикатор, снимает камеры, ведёт журнал), а центральный сервер (далее — центр) принимает команды АИС, маршрутизирует их на весы объекта, хранит журнал операций и фотографии, ведёт единый реестр тарирований и считает нетто.

Для АИС «СВХ» взаимодействие сводится к трём каналам с одним и тем же документом операции (раздел 5) и одному обратному вызову:

| Канал | Направление | Назначение |
|---|---|---|
| `POST /api/v2/weighings` | АИС → центр | Команда «взвесить» / «тарировать». Синхронно (документ операции в ответе) либо `202` сразу и исход событием — режим `wait` (4.3). |
| События `weighing.completed` / `weighing.failed` (RabbitMQ) | центр → АИС | Исход каждой команды АИС (успех — документ операции, отказ — код и причина) и каждая операция, выполненная на объекте офлайн при потере связи. |
| `GET /api/v2/…` | АИС → центр | Перечитать документ по id или номеру АИС, список за период, проверить тару ТС до взвешивания. |
| `POST /api/v2/weighings/{id}/ais_ref` | АИС → центр | Сообщить номер документа АИС (`WEI…`/`TAR…`), заведённого по офлайн-операции (7.6). |

Порядок работы оператора АИС не меняется: машина заезжает на весы → оператор нажимает «Взвесить» → приходят брутто, тара, нетто и фотографии. Исход команды АИС может брать из синхронного HTTP-ответа либо из события RabbitMQ (по ответу АИС от 17.08.2026 — из RabbitMQ; режим `wait`, 4.3): в обоих случаях это один и тот же документ. Меняется источник тары и нетто: их определяет весовая система по единому реестру тарирований (раздел 9); АИС ничего не досчитывает сама и не передаёт тару в запросе.

## 2. Соглашения о данных

- JSON, UTF-8. Имена полей — `snake_case`. Неизвестные поля АИС должна игнорировать: весовая система может добавлять поля без смены версии контракта; удаление или переименование поля — только новой версией.
- Время — ISO 8601 с явным поясом Бишкека: `2026-08-14T15:30:12+06:00`. Все моменты в документах приведены к `+06:00` (в базе центра хранится UTC).
- Массы — числа JSON в килограммах, возможна дробная часть: `43310.0`. Дискретность индикаторов 10–20 кг, но полагаться на целочисленность не следует.
- Идентификаторы: `id` — UUID операции (строка из 36 символов), уникален во всей системе и не меняется; `ais_ref` — номер и UUID документа АИС (`WEI000094176` / `TAR000012206` — префикс операции и 9 цифр — плюс UUID документа в АИС; хранятся и возвращаются как строки, как есть); `ais_object` — «Специальный идентификатор СВХ» из справочника АИС, строка из четырёх цифр с ведущими нулями (`0014` — Кызыл-Кыя, `0013` — Джалал-Абад ПЗТК, `0002` — Кант); `card_number` — номер печатной весовой карточки (`ВЕС-20260814-153012`, `ТАР-20260612-102100`), справочный.
- Номера ТС — строки до 32 символов; центр приводит к верхнему регистру и обрезает пробелы по краям. `trailer_number: null` — машина без прицепа.
- Тексты (`message`) — на русском, для показа оператору.

| Авторизация | Заголовок `Authorization: Bearer <токен>` на всех запросах: командах, GET и фотографиях. Токен сервисный, отзываемый, выдаётся весовой системой при подключении; хранить как секрет. |
| Ограничение по адресу | Запросы принимаются только с IP-адресов серверов АИС: боевой `192.168.140.150`, тестовый `192.168.6.116` (ответ АИС от 17.08.2026). Те же адреса — для доступа к RabbitMQ. |
| Ответ при отказе в доступе | `401` — нет или неверный токен; `403` — адрес не в списке. Тело — JSON `{"code": "ERR_UNAUTHORIZED" или "ERR_FORBIDDEN", "message": "…"}`. |

| Повторы | Повтор команды безопасен благодаря идемпотентности по номеру АИС (4.5), но не обязателен: исход придёт событием (раздел 7) и доступен по GET (8.2). |

## 4. Команда взвешивания и тарирования

### 4.1 Порядок для оператора

Как и в UniServer, команда не ждёт заезда: сначала машина заезжает на платформу и вес устанавливается, затем оператор нажимает «Взвесить». Агент постоянно следит за платформой и держит готовую фиксацию, поэтому команда обычно выполняется за секунды: берётся зафиксированный вес, в момент команды снимаются обе камеры, запись уходит в журнал. Если платформа пуста — немедленный отказ `ERR_VEHICLE_TIMEOUT` («сначала загоните машину»).

Без снимков обеих камер операция не проводится (`ERR_CAMERA`): вес не возвращается и не записывается.

### 4.2 Запрос

```
POST /api/v2/weighings
Authorization: Bearer <токен>
Content-Type: application/json
```

```json
{
  "ais_ref": { "number": "WEI000094176", "id": "6d0e5c2a-7b4f-4e1c-9a3d-8f2b1c0e7a55" },
  "ais_object": "0014",
  "scale_no": 1,
  "operation": "weighing",
  "vehicle_number": "01KG777AAA",
  "trailer_number": "01KG500AB",
  "operator": "Акимов Нурлан Боронбаевич",
  "wait": false
}
```

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `ais_ref.number` | строка ≤ 32 | да | Порядковый номер документа АИС: `WEI` + 9 цифр для взвешивания, `TAR` + 9 цифр для тарирования. Уникален в АИС; ключ идемпотентности (4.5). Префикс должен соответствовать `operation`. |
| `ais_ref.id` | строка (UUID) | да | UUID документа АИС. Хранится и возвращается как есть (строка ≤ 64 символов, содержимое центр не разбирает). |
| `ais_object` | строка | да | «Специальный идентификатор СВХ» из справочника АИС — четыре цифры с ведущими нулями (`0014`). Передавать строкой, нули не терять. Привязку к весам держит центр (4.6). |
| `scale_no` | целое ≥ 1 | нет, по умолчанию 1 | Номер весов на объекте («Авто весы 1 / 2»). Для объектов с одними весами всегда 1. |
| `operation` | `weighing` / `taring` | да | Взвешивание (брутто) или тарирование (масса порожней сцепки). |
| `vehicle_number` | строка ≤ 32 | да | Номер головы (тягача / автомобиля). Без номера операция не принимается: не из чего подобрать тару, а тарирование не попадёт в реестр. |
| `trailer_number` | строка ≤ 32 или null | нет | Номер прицепа / полуприцепа. `null` или отсутствие — без прицепа. |
| `operator` | строка ≤ 200 | да | ФИО оператора АИС, нажавшего «Взвесить». Пишется в запись и печатается на весовой карточке. |
| `wait` | булево | нет, по умолчанию `true` | `true` — синхронно: HTTP-ответ содержит исход операции (документ или код отказа). `false` — центр сразу отвечает `202` и запускает операцию; исход приходит событием `weighing.completed` / `weighing.failed` (раздел 7). Событие исхода публикуется в обоих режимах. |

### 4.3 Ответ

Синхронный режим (`wait: true`). Операция состоялась — `HTTP 200`:

```json
{
  "code": "OK",
  "weighing": { "…": "документ операции, раздел 5" }
}
```

Операция не состоялась (машины нет на весах, индикатор молчит, камера недоступна и т.п.) — тоже `HTTP 200`, ничего не записывается:

```json
{
  "code": "ERR_VEHICLE_TIMEOUT",
  "message": "на весах нет АТС с зафиксированным весом: загоните машину на платформу и повторите команду"
}
```

Повтор команды по уже состоявшейся операции (4.5) — `HTTP 200`, тот же документ и признак `repeated`:

```json
{
  "code": "OK",
  "repeated": true,
  "weighing": { "…": "тот же документ" }
}
```

Режим `wait: false` — центр проверяет запрос и сразу отвечает `HTTP 202`, не дожидаясь весов:

```json
{
  "code": "ACCEPTED",
  "ais_ref": { "number": "WEI000094176", "id": "6d0e5c2a-7b4f-4e1c-9a3d-8f2b1c0e7a55" },
  "message": "команда принята, исход придёт событием"
}
```

Дальше исход приходит только событием: `weighing.completed` с документом либо `weighing.failed` с кодом и причиной (7.3). Повтор команды по уже состоявшейся операции в этом режиме тоже даёт `202`, а событие `weighing.completed` публикуется повторно (у АИС оно схлопнется по `id`). Правило одно для обоих режимов: **каждая принятая команда порождает ровно одно событие исхода**.

Не-200/202 только когда неверен сам запрос — это ошибка настройки или программы, а не исход операции; такие ответы приходят сразу и в обоих режимах:

| HTTP | `code` | Когда |
|---|---|---|
| 401 | `ERR_UNAUTHORIZED` | Нет или неверный токен |
| 403 | `ERR_FORBIDDEN` | IP-адрес не в списке разрешённых |
| 404 | `ERR_UNKNOWN_SCALE` | `ais_object` + `scale_no` не привязаны к весам в справочнике центра (4.6) |
| 422 | `ERR_VALIDATION` | Тело не разбирается или поля не проходят проверку (нет обязательного, префикс номера не соответствует операции и т.п.); подробности в `details` |

Правило для клиента: статус не 200/202 → техническая ошибка, показать администратору; 200 → смотреть `code`; 202 → ждать событие.

### 4.4 Коды результата операции

| `code` | Значение | Что делать оператору |
|---|---|---|
| `OK` | Операция проведена и записана | — |
| `ERR_VEHICLE_TIMEOUT` | На весах нет машины с зафиксированным весом (платформа пуста или заезд не зафиксирован) | Загнать машину на платформу, дождаться устойчивого веса, повторить |
| `ERR_UNSTABLE` | Машина только что заехала, вес не устоялся за отведённые секунды | Повторить через несколько секунд |
| `ERR_SCALE_OFFLINE` | Агент на связи, но данных с индикатора нет (кабель, порт, питание индикатора) | Сообщить на объект; повторить после восстановления |
| `ERR_AGENT_OFFLINE` | Нет связи центра с весовым ПК объекта | Взвешивание на объекте возможно в ручном режиме — запись придёт событием после восстановления связи (раздел 7) |
| `ERR_CAMERA` | Одна из камер недоступна — операция не проведена, вес не возвращается | Сообщить на объект; повторить после восстановления камеры |
| `ERR_BUSY` | На этих весах уже выполняется операция (в том числе по этому же номеру АИС) | Дождаться завершения, повторить |
| `ERR_NOT_ZERO` | Весы не пусты перед началом операции (в текущем режиме работы не возникает, зарезервирован) | Освободить платформу |
| `ERR_INTERNAL` | Прочее: агент не ответил за отведённое время, внутренняя ошибка — подробности в `message` | Повторить; при повторении сообщить в поддержку весовой системы |

В синхронном режиме код приходит в HTTP-ответе, в режиме `wait: false` — в событии `weighing.failed` (7.3); перечень и смысл кодов одинаковы.

### 4.5 Идемпотентность: один номер АИС — одна операция

В АИС один документ `WEI…` / `TAR…` соответствует одной операции, поэтому номер `ais_ref.number` служит ключом идемпотентности без ограничения по времени:

- операция по этому номеру уже состоялась (`OK`) — центр не запускает второе взвешивание, а возвращает тот же документ с `repeated: true` (в режиме `wait: false` — `202` и повторное событие `weighing.completed`); это защита от двойного нажатия, потерянного ответа и автоматических повторов клиента;
- операция по этому номеру ещё выполняется — `ERR_BUSY` (в режиме `wait: false` — событие `weighing.failed` с этим кодом);
- прошлая попытка кончилась отказом (`ERR_*`, ничего не записано) — новая попытка с тем же номером разрешена: машину поправили, нажали снова.

Параметры повторной команды с документом не сверяются: документ уже зафиксирован и неизменяем (раздел 9).

### 4.6 Привязка объектов и весов

АИС присылает «Специальный идентификатор СВХ» (`ais_object`) и номер весов на объекте (`scale_no`); соответствие «идентификатор СВХ + номер весов → весы» хранится в справочнике центра и правится администратором весовой системы. На стороне АИС настройки объектов при добавлении весов менять не нужно: идентификаторы уже есть в справочнике АИС.

Привязка на пилоте:

| `ais_object` | Объект в АИС | Объект в весовой системе | `scale_no` |
|---|---|---|---|
| `0014` | Кызыл-Кыя | СВХ «Кызыл-Кыя» (`kyzyl-kyia`) | 1 |
| `0013` | Джалал-Абад ПЗТК | ПЗТК «Джалал-Абад» (`jalal-abad`) | 1 |
| `0002` | Кант | СВХ «Кант» — при подключении | 1 и 2 («Авто весы 1 / 2») |

Непривязанная пара → `404 ERR_UNKNOWN_SCALE`; такие запросы попадают в журнал аудита центра с присланным идентификатором, чтобы привязку было легко починить.

## 5. Документ операции

Один и тот же JSON-объект приходит в синхронном ответе на команду (`weighing`), в событии `weighing.completed` (`weighing`) и по GET-запросам. Все три источника — одна и та же запись журнала центра, поэтому сама операция (вес, время, номера, тара, нетто, фото) везде совпадает. Позже заполняются только сопутствующие поля: `photos.*.available` (файлы снимков доезжают с объекта чуть позже, раздел 6), `ais_ref` у офлайн-операций после привязки номера АИС (7.6) и, как следствие, `tare.ais_ref` у взвешиваний по такой таре.

### 5.2 Поля документа

| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID | Идентификатор операции. Один и тот же на весовом ПК, в центре, в ответе и в событии. Ключ дедупликации для АИС. |
| `card_number` | строка | Номер печатной весовой карточки (`ВЕС-` / `ТАР-ГГГГММДД-ЧЧММСС` от бишкекского времени операции). Справочный — для акта. |

| `vehicle_number`, `trailer_number` | строка; строка или null | Номера головы и прицепа после нормализации. |
| `operator` | строка или null | Кто провёл операцию: для команд АИС — ФИО из запроса; для офлайн — учётная запись оператора весового ПК. |
| `unit` | строка | Всегда `kg`. |
| `massa` | число | Измеренная масса: при взвешивании — брутто, при тарировании — тара (масса порожней сцепки). |
| `tare` | объект или null | Тарирование сцепки, найденное для этого взвешивания (5.3). У тарирований — `null`. |
| `netto` | число или null | Брутто − тара. `null`, если тара не подставлена (5.3). У тарирований — `null`. |
| `photos` | объект | Снимки `front` (перед) и `rear` (зад): `url` — постоянный путь относительно базового адреса центра, `sha256` — контрольная сумма файла, `available` — файл уже доставлен в центр (раздел 6). |
| `checksum` | строка | Контрольная сумма записи (SHA-256 по ключевым полям и хешам фото). Запись неизменяема; сумма позволяет доказать это при спорах. |

### 5.3 Тарирование во вложении

Поле `tare` показывает, что система знает о таре этой сцепки на момент взвешивания:

| `tare` / `tare.status` | Смысл | `netto` |
|---|---|---|
| `null` | Тарирований этой сцепки (пары голова + прицеп) в системе не было. | `null` |
| `applied` | Тарирование действовало на момент взвешивания и подставлено в расчёт. Это тарирование, по которому реально считали нетто; оно записано в операцию и не меняется задним числом. | число |
| `expired` | Последнее тарирование сцепки истекло к моменту взвешивания (старше 3 календарных месяцев). Приводятся его id, номер АИС, дата и масса — для показа оператору «тара от 12.06.2026, 15 300 кг — устарела»; в расчёт не подставлено. | `null` |
| `not_applied` | Редкий случай: тарирование по сроку действовало, но не было подставлено — офлайн-взвешивание на объекте, у которого локальная копия реестра ещё не содержала это тарирование. Трактовать как «нетто не рассчитано». | `null` |

Инвариант: `netto` не `null` тогда и только тогда, когда `tare.status == "applied"`. Поля объекта `tare`: `status`, `id` (UUID тарирования), `card_number`, `ais_ref` (номер `TAR…` и UUID документа АИС, если он известен центру: из команды либо по привязке 7.6; иначе `null`), `tared_at`, `massa`.

## 6. Фотографии

- Два снимка на каждую операцию: `front` (перед) и `rear` (зад), JPEG в родном разрешении камеры с оверлеем весовой системы (объект, дата-время, вес).
- Ссылка постоянная: `GET <базовый адрес>/vesy/ГГГГ/ММ/ДД/<id без дефисов>_photo1.jpeg` (`photo1` — перед, `photo2` — зад) с заголовком `Authorization: Bearer <токен>` и с разрешённого IP. Ссылка серверная: пользователям АИС снимки показывает сервер АИС, скачивая их у центра при обращении (или из своего кэша). Браузер пользователя напрямую к центру не ходит — у него нет ни токена, ни разрешённого адреса; если АИС нужна прямая загрузка в браузер, это отдельный механизм (подписанные ссылки), обсуждается отдельно (вопрос 4 раздела 12).
- Файл после сохранения не пересжимается и не заменяется никогда; `sha256` в документе — его контрольная сумма. Ответ несёт `ETag` (= sha256) и `Cache-Control: immutable` — кэшировать можно бессрочно.
- Сразу после операции файл может ещё ехать с объекта: в норме секунды, при потере связи с объектом — до её восстановления. На это время `404`, в документе `available: false`. Показать «снимок ещё не доставлен» и повторить позже; `404` не кэшировать как «фото нет».
- Статусы: `200 image/jpeg`; `401` / `403` — доступ; `404` — файл ещё не доставлен либо путь неверен.
- Срок хранения — 5 лет с момента операции. Скачивания журналируются центром.

## 7. События (RabbitMQ) и обратная связь по офлайн-операциям

### 7.1 Назначение

Два события:

- `weighing.completed` — по каждой состоявшейся операции (`code OK`): по командам АИС и выполненным на объекте офлайн (ручной режим при потере связи — для них это единственный путь доставки). Несёт документ операции.
- `weighing.failed` — отказ по команде АИС (`ERR_*`): что именно не получилось и почему. Несёт `ais_ref`, код и причину; документа нет, потому что ничего не записано. Нужен, чтобы АИС могла брать исход команды целиком из очереди (ответ АИС от 17.08.2026), не дожидаясь HTTP-ответа.

Правило: каждая принятая команда АИС порождает ровно одно событие исхода — `completed` или `failed`; повтор команды по уже состоявшейся операции — повторное `completed`. Офлайн-операции приходят только как `completed`. Так АИС получает единый поток исходов и записей, страховку от потерянного HTTP-ответа (в событии всегда есть `ais_ref`) и офлайн-записи, о которых она иначе не узнала бы.

### 7.2 Подключение

| Параметр | Значение |
|---|---|
| Брокер | RabbitMQ весовой системы на сервере центра, `192.168.140.70:5672` (AMQP 0-9-1; TLS на 5671 — после установки сертификата) |
| vhost | `vesy` |
| Учётная запись | `ais-svh` — только чтение своей очереди; пароль выдаётся при подключении |
| Exchange | `vesy.events`, тип `topic`, durable — объявляет и сопровождает весовая система |
| Routing key | `weighing.completed.<ais_object>` / `weighing.failed.<ais_object>`, например `weighing.completed.0014` |
| Очередь АИС | `ais-svh.weighings` — одна на все объекты и оба события (по ответу АИС от 17.08.2026; объект различается по `ais_object` в конверте), durable, без TTL, привязка `weighing.#` — объявляет весовая система; консьюмер АИС только читает |
| Свойства сообщения | `content_type: application/json`, `delivery_mode: 2` (persistent), `message_id` = `event_id`, `type` = тип события, `timestamp`, `app_id: vesy-center` |

`weighing.completed`:

```json

  "type": "weighing.completed",
  "version": 1,
  "published_at": "2026-08-14T15:30:14+06:00",
  "ais_object": "0014",
  "ais_ref": { "number": "WEI000094176", "id": "6d0e5c2a-7b4f-4e1c-9a3d-8f2b1c0e7a55" },
  "weighing": { "…": "документ операции, раздел 5" }
}
```

`weighing.failed`:

```json
{
  "event_id": "4e2a9c7b-1f0d-4b6e-8c3a-7d5e2f1a0b98",
  "type": "weighing.failed",
  "version": 1,
  "published_at": "2026-08-14T15:31:02+06:00",
  "ais_object": "0014",

  "failure": {
    "operation": "weighing",
    "scale_no": 1,
    "code": "ERR_VEHICLE_TIMEOUT",
    "message": "на весах нет АТС с зафиксированным весом: загоните машину на платформу и повторите команду",
```

В конверте обоих событий: `event_id` (уникален; повторная публикация несёт тот же `event_id`), `type`, `version`, `published_at`, `ais_object` — специальный идентификатор СВХ (продублирован из документа, чтобы разбирать одну очередь по объектам без чтения тела), `ais_ref` — документ АИС (`null` у офлайн-операций). Тело: `weighing` у `completed`, `failure` у `failed`.

### 7.4 Гарантии и обязанности консьюмера

- Доставка at-least-once: одно и то же событие может прийти повторно (переподключение, повторная публикация по запросу). Консьюмер сохраняет операцию upsert'ом по `weighing.id` (отказы — по `event_id`) и подтверждает (`ack`) только после сохранения. Ошибка обработки — не подтверждать (`nack` / разрыв), сообщение вернётся в очередь.
- Порядок не гарантируется: офлайн-пачки приходят позже, тарирование может прийти после взвешивания, которое на него ссылается. Документ самодостаточен (тарирование вложено), поэтому события можно обрабатывать независимо друг от друга.
- В синхронном режиме событие может прийти раньше, чем HTTP-ответ на ту же команду. Обе стороны говорят об одной записи с одним `id`.
- Задержка события относительно исхода — секунды: центр публикует из журнала сразу после записи исхода.
- Пока консьюмер отключён, сообщения копятся в durable-очереди без ограничения времени, ничего не теряется. Если очередь всё же утеряна — журнал за период восстанавливается запросом 8.3.
- На стороне центра события публикуются из журнала с подтверждением брокера и повторами до успеха; любую операцию можно опубликовать повторно по просьбе АИС.

### 7.5 Зарезервированные события (необязательные)

Эти события в первой версии не публикуются; описаны, чтобы АИС могла заказать их позже без смены контракта.

- `agent.status` — потеря и восстановление связи центра с весовым ПК объекта. Зачем: АИС могла бы показывать оператору «весы объекта сейчас недоступны, взвешивание идёт на месте в ручном режиме» и не слать команды, которые заведомо кончатся `ERR_AGENT_OFFLINE`; после восстановления — ждать офлайн-записи. Без него оператор узнаёт о недоступности только по коду отказа.
- `weighing.reversed` — сторнирование записи. Записи журнала неизменяемы; если операцию нужно отменить (ошибочный номер и т.п.), в весовой системе появится новая запись-сторно со ссылкой на исходную (функция запланирована). Зачем: АИС могла бы автоматически аннулировать свой документ вместо ручной сверки.

Формат — той же схемы (`event_id`, `type`, `version`, `published_at`, `ais_object`, тело). Если АИС это не нужно — не реализуем.

### 7.6 Обратная связь: номер документа АИС для офлайн-операций

Офлайн-операция (взвешивание или тарирование в ручном режиме при потере связи) выполняется без участия АИС, поэтому номера `WEI…` / `TAR…` у неё нет: событие приходит с нашим `id`, `source: local_offline`, `ais_ref: null`, номерами машины и прицепа, объектом (`site.ais_object`), временем, массами, тарой и фото. Дальше:

1. АИС по объекту (`ais_object`), номеру машины и времени сопоставляет операцию с регистрацией и заводит документ взвешивания или тарирования по данным события. Если сопоставить не удалось — документ всё равно создаётся, но остаётся без привязки к регистрации; ручного сопоставления оператором не предусмотрено (ответ АИС от 17.08.2026). То есть номер `WEI…` / `TAR…` у офлайн-операции появляется всегда.
2. Заведя документ (сопоставленный или нет), АИС сообщает его номер и UUID центру:

```
POST /api/v2/weighings/{id}/ais_ref
Authorization: Bearer <токен>

{ "number": "WEI000094200", "id": "3c2b1a09-8f7e-4d6c-b5a4-3e2d1c0b9a87" }
```

Ответ `200` с обновлённым документом (`{"weighing": {…}}`). Ошибки: `404 ERR_NOT_FOUND` — нет операции с таким `id`; `409 ERR_ALREADY_LINKED` — у операции уже другой номер АИС либо этот номер уже привязан к другой операции; `422 ERR_VALIDATION` — префикс номера не соответствует операции. Повторный вызов с тем же номером — `200`, без изменений.

3. С этого момента `ais_ref` заполнен во всех каналах: в GET-ответах, в панели центра (страница записи), в последующих событиях и во вложении `tare.ais_ref` у взвешиваний, которые считались по этой таре. Сама операция при этом не меняется — привязка хранится рядом с записью, не в ней.

Центр показывает диспетчеру офлайн-операции без номера АИС, чтобы «зависшие» сопоставления были видны с обеих сторон.

## 8. Запросы для сверки и подсказок

Все — `GET`, тот же токен, ответы `200` с JSON; `404 ERR_NOT_FOUND` — нет такой записи.

### 8.1 Документ по id

`GET /api/v2/weighings/{id}` → `{"weighing": {…}}`

### 8.2 Документ по номеру АИС

`GET /api/v2/weighings?ais_number=WEI000094176` → `{"weighings": [{…}]}` — пустой список, если операция по этому номеру не состоялась. Способ узнать исход команды после тайм-аута.

### 8.3 Список за период

`GET /api/v2/weighings?from=2026-08-14T00:00:00%2B06:00&to=2026-08-15T00:00:00%2B06:00&ais_object=…&scale_no=1&operation=weighing&page=1&per_page=200`

→ `{"weighings": [{…}], "page": 1, "per_page": 200, "total": 57}`. Отбор по `weighed_at`, сортировка по возрастанию; `ais_object`, `scale_no`, `operation` необязательны; `per_page` ≤ 200. Для сверки журналов и восстановления после сбоев (в том числе поиска офлайн-операций без номера АИС: `source=local_offline&unlinked=true`).

### 8.4 Тара ТС до взвешивания

`GET /api/v2/tares?vehicle_number=01KG777AAA&trailer_number=01KG500AB` →

```json
{
  "status": "active",
  "tare": {
    "id": "7a1e2c90-5b3d-4f6a-8e2b-1c9d0f4a6b33",
    "card_number": "ТАР-20260612-102100",
    "ais_ref": { "number": "TAR000012206", "id": "c1f0a9d4-2e6b-4c8a-b7d3-5e9f0a1b2c34" },
    "tared_at": "2026-06-12T10:21:00+06:00",
    "massa": 15300.0
  }
}
```

`status`: `active` — тарирование действует сейчас и будет подставлено; `expired` — последнее тарирование устарело, нетто не будет рассчитано (данные приведены для показа); `none` — тарирований сцепки не было, `tare: null`. Состояние — на момент запроса; при самом взвешивании оно определяется заново по моменту фиксации веса.

Зачем (необязательный запрос): сегодня в форме взвешивания АИС есть кнопка «Найти тару ТС», которая ищет тару в базе АИС. После перехода тару подбирает весовая система в момент взвешивания, и в ответе / событии она уже есть — но оператор узнаёт об этом только после взвешивания. Этот запрос позволяет оставить кнопке прежний смысл: до команды показать, есть ли действующая тара, когда она снята и не пора ли перетарировать (иначе брутто пройдёт без нетто). Если АИС такая проверка не нужна — не реализуем.

## 9. Правила тары, нетто и журнала

- Тара привязана к сцепке — паре «голова + прицеп». Тарирование без прицепа действует только для машины без прицепа; смена прицепа означает, что действующей тары нет и нужно новое тарирование.
- Действует последнее тарирование сцепки не старше 3 календарных месяцев на момент взвешивания. Реестр тарирований единый по всем объектам: тарироваться и взвешиваться можно на разных весах.
- Единственный источник тары — тарирования, проведённые через весовую систему (по командам АИС или офлайн). Справочников тары и ручного ввода массы нет; АИС тару не передаёт и не выбирает.
- Записи журнала неизменяемы: не редактируются и не удаляются; исправление — только сторнированием новой записью (событие `weighing.reversed`, 7.5). Фото и запись связаны контрольными суммами.
- Отказы не записываются: журнал состоит только из состоявшихся операций.

## 10. Отличия от контракта v1

Совместимый контракт v1 (`POST /api/v1/weigh`, формат UniServer) продолжает работать; АИС может переключиться на него сменой адреса, а на v2 — когда удобно. Отличия:

| Аспект | v1 | v2 |
|---|---|---|
| Адресация весов | `ip_address` + `port` + `autoscale` (адрес UniServer объекта) | `ais_object` + `scale_no` (идентификатор объекта в АИС) |
| Авторизация | `username` / `password` в теле (`admin` / `admin`) | `Authorization: Bearer <токен>` + IP-allowlist |
| Ссылка на документ АИС | нет | `ais_ref` (`WEI…` / `TAR…`), идемпотентность по номеру, обратная привязка для офлайн-операций |
| Ответ | Плоский: `code, massa, weighing_datetime, unit_meas, front_image, rear_image, tare, tare_datetime, netto, no_valid_tare` | `code` + документ операции: id, номер карточки, объект / весы с поверкой, тарирование во вложении со статусом, фото с sha256, контрольная сумма |
| Устаревшая тара | `tare: null, netto: null, no_valid_tare: true` | `tare.status: "expired"` с датой, массой и номером тарирования; `netto: null` |
| HTTP-статусы | Всегда 200 | 200 для исходов операции; 401 / 403 / 404 / 422 для неверного запроса |
| События | нет | RabbitMQ: `weighing.completed` по каждой операции, `weighing.failed` по каждому отказу команды; режим `wait: false` |
| Сверка | нет | GET по id, по номеру АИС, за период; проверка тары ТС |
| Даты | ISO 8601 с `+06:00` (уже в v1) | так же |

## 11. Порядок внедрения

1. Согласование этого документа (замечания АИС → правки → версия 1.0).
2. Реализация v2 и событий на стороне весовой системы.
3. Выдача АИС токена и учётной записи RabbitMQ; открытие доступа с серверов АИС (`192.168.140.150` боевой, `192.168.6.116` тестовый) к центру `192.168.140.70` по HTTP и 5672 — задание системщику; привязка объектов по специальным идентификаторам СВХ (`0014`, `0013`).
4. Тестовый контур: весовая система предоставит эталонный скрипт-консьюмер, примеры запросов и, по договорённости, тестовые весы-эмулятор на центре, чтобы гонять команды без машины на реальных весах.
5. Параллельная работа: АИС продолжает работать через старую цепочку, новые запросы проверяются на тестовом контуре и на пилотных объектах (СВХ «Кызыл-Кыя», ПЗТК «Джалал-Абад»).
6. Переключение по объектам; UniServer выводится из эксплуатации пообъектно.
