## 1. Назначение и общая схема

Единая весовая система ОАО «ГТИ» (далее — весовая система) заменяет UniServer AUTO и скрипт-маршрутизатор на 13 объектах: на каждом весовом ПК работает агент (читает индикатор, снимает камеры, ведёт журнал), а центральный сервер (далее — центр) принимает команды АИС, маршрутизирует их на весы объекта, хранит журнал операций и фотографии, ведёт единый реестр тарирований и считает нетто.

Взаимодействие с АИС «СВХ» — два режима с одним и тем же документом операции (раздел 5):

| Канал | Направление | Когда | Назначение |
|---|---|---|---|
| `POST /api/v2/weighings` | АИС → центр | Онлайн: связь центра с весами объекта есть | Команда «взвесить» / «тарировать». Синхронно: ответ — документ операции или код отказа. Повтор команды идемпотентен (4.5). |
| Событие `weighing.completed` (RabbitMQ) | центр → АИС | Офлайн: операция выполнена на объекте при потере связи с центром | Досылка офлайн-операций после восстановления связи. Тот же документ. |
| `POST /api/v2/weighings/{id}/ais_ref` | АИС → центр | После обработки офлайн-операции | Сообщить номер документа АИС (`WEI…` / `TAR…`), заведённого по офлайн-операции (7.5). |
| `GET /api/v2/weighings…` | АИС → центр | По необходимости | Перечитать документ по нашему id или по номеру АИС, список за период — для сверки. |

Порядок работы оператора АИС не меняется: машина заезжает на весы → оператор нажимает «Взвесить» → в HTTP-ответе приходят брутто, тара, нетто и фотографии. Меняется источник тары и нетто: их определяет весовая система по единому реестру тарирований (раздел 9); АИС ничего не досчитывает сама и не передаёт тару в запросе.

## 2. Соглашения о данных

- JSON, UTF-8. Имена полей — `snake_case`. Неизвестные поля АИС должна игнорировать: весовая система может добавлять поля без смены версии контракта; удаление или переименование поля — только новой версией.
- Время — ISO 8601 с явным поясом Бишкека: `2026-08-14T15:30:12+06:00`. Все моменты в документах приведены к `+06:00` (в базе центра хранится UTC).
- Массы — числа JSON в килограммах, возможна дробная часть: `43310.0`. Дискретность индикаторов 10–20 кг, но полагаться на целочисленность не следует.
- Идентификаторы: `id` — UUID операции в весовой системе (строка из 36 символов), уникален и не меняется; `ais_ref` — номер документа АИС, он же его идентификатор в АИС: `WEI` + 9 цифр у взвешивания (`WEI000094176`), `TAR` + 9 цифр у тарирования (`TAR000012206`); передаётся и возвращается строкой как есть; `ais_object` — «Специальный идентификатор СВХ» из справочника АИС, строка из четырёх цифр с ведущими нулями (`0014` — Кызыл-Кыя, `0013` — Джалал-Абад ПЗТК, `0002` — Кант); `card_number` — номер печатной весовой карточки (`ВЕС-20260814-153012`, `ТАР-20260612-102100`), справочный.
- Номера ТС — строки до 32 символов; центр приводит к верхнему регистру и обрезает пробелы по краям. `trailer_number: null` — машина без прицепа. ФИО оператора — до 200 символов (лимиты подтверждены АИС).
- Тексты (`message`) — на русском, для показа оператору.

## 3. Подключение и безопасность

| Параметр | Значение |
|---|---|
| Базовый адрес центра | Предварительно `http://192.168.140.70` (внутренняя сеть ГТИ). После установки сертификата — HTTPS по доменному имени; пути не меняются. |
| Авторизация | Заголовок `Authorization: Bearer <токен>` на всех запросах: командах, GET и фотографиях. Токен сервисный, отзываемый, выдаётся весовой системой при подключении; хранить как секрет. |
| Ограничение по адресу | Запросы принимаются только с серверов АИС: боевой `192.168.140.150`, тестовый `192.168.6.116`. Те же адреса — для доступа к RabbitMQ. |
| Ответ при отказе в доступе | `401` — нет или неверный токен; `403` — адрес не в списке. Тело — JSON `{"code": "ERR_UNAUTHORIZED" или "ERR_FORBIDDEN", "message": "…"}`. |
| Тайм-аут команды | Операция на весах длится до 120 с (обычно 1–5 с, если машина уже стоит на весах). Рекомендуемый тайм-аут HTTP-клиента АИС — не менее 130 с; при более коротком тайм-ауте исход не теряется — повторная команда с тем же `ais_ref` вернёт его (4.5). |
| Повторы | Повтор команды с тем же `ais_ref` безопасен: второе взвешивание не запускается, центр отдаёт исход первой (4.5). |

## 4. Команда взвешивания и тарирования (REST)

### 4.1 Порядок для оператора

Как и в UniServer, команда не ждёт заезда: сначала машина заезжает на платформу и вес устанавливается, затем оператор нажимает «Взвесить». Агент постоянно следит за платформой и держит готовую фиксацию, поэтому команда обычно выполняется за секунды: берётся зафиксированный вес, в момент команды снимаются обе камеры, запись уходит в журнал. Если платформа пуста — немедленный отказ `ERR_VEHICLE_TIMEOUT` («сначала загоните машину»).

Без снимков обеих камер операция не проводится (`ERR_CAMERA`): вес не возвращается и не записывается.

### 4.2 Запрос

```
POST /api/v2/weighings
Authorization: Bearer <токен>
Content-Type: application/json
```

```json
{
  "ais_ref": "WEI000094176",
  "ais_object": "0014",
  "scale_no": 1,
  "operation": "weighing",
  "vehicle_number": "01KG777AAA",
  "trailer_number": "01KG500AB",
  "operator": "Акимов Нурлан Боронбаевич"
}
```

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `ais_ref` | строка ≤ 32 | да | Номер документа АИС: `WEI` + 9 цифр для взвешивания, `TAR` + 9 цифр для тарирования. Уникален в АИС; ключ идемпотентности (4.5). Префикс должен соответствовать `operation`. |
| `ais_object` | строка | да | «Специальный идентификатор СВХ» из справочника АИС — четыре цифры с ведущими нулями (`0014`). Передавать строкой, нули не терять. Привязку к весам держит центр (4.6). |
| `scale_no` | целое ≥ 1 | нет, по умолчанию 1 | Номер весов на объекте — «Авто весы 1 / 2» из формы взвешивания. Для объектов с одними весами всегда 1. |
| `operation` | `weighing` / `taring` | да | Взвешивание (брутто) или тарирование (масса порожней сцепки). |
| `vehicle_number` | строка ≤ 32 | да | Номер головы (тягача / автомобиля). Без номера операция не принимается: не из чего подобрать тару, а тарирование не попадёт в реестр. |
| `trailer_number` | строка ≤ 32 или null | нет | Номер прицепа / полуприцепа. `null` или отсутствие — без прицепа. |
| `operator` | строка ≤ 200 | да | ФИО оператора АИС, нажавшего «Взвесить». Пишется в запись и печатается на весовой карточке. |

### 4.3 Ответ

Операция состоялась — `HTTP 200`:

```json
{
  "code": "OK",
  "weighing": { "…": "документ операции, раздел 5" }
}
```

Операция не состоялась (машины нет на весах, индикатор молчит, камера недоступна и т.п.) — тоже `HTTP 200`, ничего не записывается:

```json
{
  "code": "ERR_VEHICLE_TIMEOUT",
  "message": "на весах нет АТС с зафиксированным весом: загоните машину на платформу и повторите команду"
}
```

Повтор команды по уже состоявшейся операции (4.5) — `HTTP 200`, тот же документ и признак `repeated`:

```json
{
  "code": "OK",
  "repeated": true,
  "weighing": { "…": "тот же документ" }
}
```

Не-200 только когда неверен сам запрос — это ошибка настройки или программы, а не исход операции:

| HTTP | `code` | Когда |
|---|---|---|
| 401 | `ERR_UNAUTHORIZED` | Нет или неверный токен |
| 403 | `ERR_FORBIDDEN` | IP-адрес не в списке разрешённых |
| 404 | `ERR_UNKNOWN_SCALE` | `ais_object` + `scale_no` не привязаны к весам в справочнике центра (4.6) |
| 422 | `ERR_VALIDATION` | Тело не разбирается или поля не проходят проверку (нет обязательного, префикс номера не соответствует операции, превышена длина и т.п.); подробности в `details` |

Правило для клиента: статус не 200 → техническая ошибка, показать администратору; 200 → смотреть `code`.

### 4.4 Коды результата операции

| `code` | Значение | Что делать оператору |
|---|---|---|
| `OK` | Операция проведена и записана | — |
| `ERR_VEHICLE_TIMEOUT` | На весах нет машины с зафиксированным весом (платформа пуста или заезд не зафиксирован) | Загнать машину на платформу, дождаться устойчивого веса, повторить |
| `ERR_UNSTABLE` | Машина только что заехала, вес не устоялся за отведённые секунды | Повторить через несколько секунд |
| `ERR_SCALE_OFFLINE` | Агент на связи, но данных с индикатора нет (кабель, порт, питание индикатора) | Сообщить на объект; повторить после восстановления |
| `ERR_AGENT_OFFLINE` | Нет связи центра с весовым ПК объекта | Взвешивание на объекте возможно в ручном режиме — запись придёт событием после восстановления связи (раздел 7) |
| `ERR_CAMERA` | Одна из камер недоступна — операция не проведена, вес не возвращается | Сообщить на объект; повторить после восстановления камеры |
| `ERR_BUSY` | На этих весах уже выполняется операция по другому документу АИС | Дождаться завершения, повторить |
| `ERR_TARE_TOO_HEAVY` | Тарирование не проведено: масса на весах больше лимита тары этих весов (по умолчанию 25 000 кг, настраивается в весовой системе) — на платформе гружёная машина, а не порожняя сцепка. Ничего не записано, `message` содержит массу и лимит (добавлено 04.09.2026) | Провести **взвешивание** (документ `WEI…`), а не тарирование; тарировать сцепку порожней |
| `ERR_NOT_ZERO` | Весы не пусты перед началом операции (в текущем режиме работы не возникает, зарезервирован) | Освободить платформу |
| `ERR_INTERNAL` | Прочее: агент не ответил за отведённое время, внутренняя ошибка — подробности в `message` | Повторить; при повторении сообщить в поддержку весовой системы |

### 4.5 Идемпотентность: один номер АИС — одна операция

В АИС один документ `WEI…` / `TAR…` соответствует одной операции, поэтому `ais_ref` служит ключом идемпотентности без ограничения по времени. Повторная команда с тем же `ais_ref`:

- операция по этому номеру уже состоялась (`OK`) — центр не запускает второе взвешивание, а возвращает тот же документ с `repeated: true`. Это закрывает потерянный ответ, тайм-аут клиента, двойное нажатие и автоматические повторы;
- команда по этому номеру ещё выполняется — центр не запускает вторую, а дожидается исхода первой и отвечает им же (обеим сторонам один результат);
- прошлая попытка кончилась отказом (`ERR_*`, ничего не записано) — новая попытка с тем же номером разрешена: машину поправили, нажали снова.

Параметры повторной команды с документом не сверяются: документ уже зафиксирован и неизменяем (раздел 9). Схема согласована с АИС: онлайн — только REST, при неудаче АИС повторяет запрос, а весовая система понимает, что он повторный.

### 4.6 Привязка объектов и весов

АИС присылает «Специальный идентификатор СВХ» (`ais_object`) и номер весов на объекте (`scale_no`); соответствие «идентификатор СВХ + номер весов → весы» хранится в справочнике центра и правится администратором весовой системы. На стороне АИС настройки объектов при добавлении весов менять не нужно: идентификаторы уже есть в справочнике АИС.

Привязка на пилоте:

| `ais_object` | Объект в АИС | Объект в весовой системе | `scale_no` |
|---|---|---|---|
| `0014` | Кызыл-Кыя | СВХ «Кызыл-Кыя» (`kyzyl-kyia`) | 1 |
| `0013` | Джалал-Абад ПЗТК | ПЗТК «Джалал-Абад» (`jalal-abad`) | 1 |
| `0002` | Кант | СВХ «Кант» — при подключении | 1 и 2 («Авто весы 1 / 2») |

Непривязанная пара → `404 ERR_UNKNOWN_SCALE`; такие запросы попадают в журнал аудита центра с присланным идентификатором, чтобы привязку было легко починить.

## 5. Документ операции

Один и тот же JSON-объект приходит в ответе на команду (`weighing`), в событии `weighing.completed` (`weighing`) и по GET-запросам. Это одна и та же запись журнала центра, поэтому сама операция (вес, время, номера, тара, нетто, фото) везде совпадает. Позже заполняются только сопутствующие поля: `photos.*.available` (файлы снимков доезжают с объекта чуть позже, раздел 6), `ais_ref` у офлайн-операций после обратной связи от АИС (7.5) и, как следствие, `tare.ais_ref` у взвешиваний по такой таре.

### 5.2 Поля документа

| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID | Идентификатор операции в весовой системе. Один и тот же на весовом ПК, в центре, в ответе и в событии. Ключ дедупликации для АИС. |
| `card_number` | строка | Номер печатной весовой карточки (`ВЕС-` / `ТАР-ГГГГММДД-ЧЧММСС` от бишкекского времени операции). Справочный — для акта. |
| `operation` | `weighing` / `taring` | Тип операции. |
| `source` | `ais` / `local_offline` | `ais` — по команде АИС; `local_offline` — выполнена оператором весового ПК в ручном режиме без участия АИС: при потере связи с центром (дослана автоматически после восстановления) либо на объекте, к которому АИС ещё не подключена (ручной режим разрешён администратором весовой системы; уточнение 03.09.2026). |
| `ais_ref` | строка или null | Номер документа АИС. У операций по командам — из запроса; у офлайн-операций — `null`, пока АИС не сообщит номер заведённого документа (7.5). |
| `site` | объект | Объект: `code` — код в весовой системе, `name` — название, `ais_object` — «Специальный идентификатор СВХ» этого объекта в АИС (по нему офлайн-записи относятся к нужному СВХ; он же продублирован в конверте события). |
| `scale` | объект | Весы: `id` — id в справочнике центра, `no` — номер весов на объекте (как `scale_no`), `name`, `verification` — свидетельство о поверке этих весов (`number`, `date`, `valid_until`; `null`, если не заполнено). |
| `weighed_at` | дата-время | Момент фиксации веса. Для операций по команде АИС — по часам центра; для офлайн — по часам весового ПК. |
| `recorded_at` | дата-время | Момент записи в журнал центра. У офлайн-операций позже `weighed_at` — на время без связи. |
| `vehicle_number`, `trailer_number` | строка; строка или null | Номера головы и прицепа после нормализации. |
| `operator` | строка или null | Кто провёл операцию: для команд АИС — ФИО из запроса; для офлайн — учётная запись оператора весового ПК. |
| `unit` | строка | Всегда `kg`. |
| `massa` | число | Измеренная масса: при взвешивании — брутто, при тарировании — тара (масса порожней сцепки). |
| `tare` | объект или null | Тарирование сцепки, найденное для этого взвешивания (5.3). У тарирований — `null`. |
| `netto` | число или null | Брутто − тара. `null`, если тара не подставлена (5.3). У тарирований — `null`. |
| `photos` | объект | Снимки `front` (перед) и `rear` (зад): `url` — постоянный путь относительно базового адреса центра, `sha256` — контрольная сумма файла, `available` — файл уже доставлен в центр (раздел 6). |
| `storno` | объект или null | Запись аннулирована сторнированием в весовой системе (добавлено 04.09.2026): `at` — момент сторно, `reason` — причина. Исходная запись при этом не меняется (правило журнала, раздел 9); для весовой системы операция «как не было»: тарирование выпадает из реестра тар, в отчёты не входит. Сама запись-сторно в API и событиях не показывается. `null` — запись действует. |
| `checksum` | строка | Контрольная сумма записи (SHA-256 по ключевым полям и хешам фото). Запись неизменяема; сумма позволяет доказать это при спорах. |

### 5.3 Тарирование во вложении

Поле `tare` показывает, что система знает о таре этой сцепки на момент взвешивания:

| `tare` / `tare.status` | Смысл | `netto` |
|---|---|---|
| `null` | Тарирований этой сцепки (пары голова + прицеп) в системе не было. | `null` |
| `applied` | Тарирование действовало на момент взвешивания и подставлено в расчёт. Это тарирование, по которому реально считали нетто; оно записано в операцию и не меняется задним числом. | число |
| `expired` | Последнее тарирование сцепки истекло к моменту взвешивания (старше 3 календарных месяцев). Приводятся его id, номер АИС, дата и масса — для показа оператору «тара от 12.06.2026, 15 300 кг — устарела»; в расчёт не подставлено. | `null` |
| `not_applied` | Редкий случай: тарирование по сроку действовало, но не было подставлено — офлайн-взвешивание на объекте, у которого локальная копия реестра ещё не содержала это тарирование. Трактовать как «нетто не рассчитано». | `null` |

Инвариант: `netto` не `null` тогда и только тогда, когда `tare.status == "applied"`. Поля объекта `tare`: `status`, `id` (UUID тарирования), `card_number`, `ais_ref` (номер `TAR…` документа АИС, если он известен центру: из команды либо по обратной связи 7.5; иначе `null`), `tared_at`, `massa`.

Дополнение 04.09.2026: у `tare.status == "not_applied"` есть поле `reason` — `"tare_not_below_gross"` (тара не меньше брутто: тарирование сцепки ошибочно — так тарируют гружёную машину; весовая система такую тару не подставляет и нетто не считает) либо `"replica_lag"` (отставшая копия реестра при офлайн-взвешивании); у прочих статусов `reason: null`. У вложения `tare` есть также `storno` (как в 5.2): тарирование сторнировано после того, как было подставлено, — запись взвешивания при этом не меняется (`applied`, нетто остаётся), а `storno` показывает, что тару аннулировали.

## 6. Фотографии

- Два снимка на каждую операцию: `front` (перед) и `rear` (зад), JPEG в родном разрешении камеры с оверлеем весовой системы (объект, дата-время, вес).
- Ссылка постоянная: `GET <базовый адрес>/vesy/ГГГГ/ММ/ДД/<id без дефисов>_photo1.jpeg` (`photo1` — перед, `photo2` — зад) с заголовком `Authorization: Bearer <токен>` и с разрешённого IP. Снимки у центра скачивает сервер АИС и показывает своим пользователям сам (подтверждено АИС); браузер пользователя к центру не обращается.
- Файл после сохранения не пересжимается и не заменяется никогда; `sha256` в документе — его контрольная сумма. Ответ несёт `ETag` (= sha256) и `Cache-Control: immutable` — кэшировать можно бессрочно.
- Сразу после операции файл может ещё ехать с объекта: в норме секунды, при потере связи с объектом — до её восстановления. На это время `404`, в документе `available: false`. Показать «снимок ещё не доставлен» и повторить позже; `404` не кэшировать как «фото нет».
- Статусы: `200 image/jpeg`; `401` / `403` — доступ; `404` — файл ещё не доставлен либо путь неверен.
- Срок хранения — 5 лет с момента операции. Скачивания журналируются центром.

## 7. Офлайн-операции: события RabbitMQ и обратная связь

### 7.1 Назначение

Когда связи центра с весовым ПК объекта нет, оператор весового ПК проводит взвешивание или тарирование в ручном режиме (номер машины и прицепа вводит вручную, тара подбирается по локальной копии реестра). Такие операции выполняются без участия АИС, поэтому единственный путь доставить их в АИС — событие: после восстановления связи запись доезжает в центр, и центр публикует `weighing.completed` с документом операции (`source: local_offline`, `ais_ref: null`).

Онлайн-операции (по командам АИС) событиями не публикуются — их исход АИС получает в HTTP-ответе (раздел 4). По договорённости публикацию можно расширить и на онлайн-операции без смены формата.

### 7.2 Подключение

| Параметр | Значение |
|---|---|
| Брокер | RabbitMQ весовой системы на сервере центра, `192.168.140.70:5672` (AMQP 0-9-1; TLS на 5671 — после установки сертификата) |
| vhost | `vesy` |
| Учётная запись | `ais-svh` — только чтение своей очереди; пароль выдаётся при подключении |
| Exchange | `vesy.events`, тип `topic`, durable — объявляет и сопровождает весовая система |
| Routing key | `weighing.completed.<ais_object>`, например `weighing.completed.0014` |
| Очередь АИС | `ais-svh.weighings` — одна на все объекты (объект различается по `ais_object` в конверте), durable, без TTL, привязка `weighing.completed.#` — объявляет весовая система; консьюмер АИС только читает |
| Состав событий | События публикуются **только по весам, привязанным к «Специальному идентификатору СВХ»** (приложение А). Весовая система может обслуживать объекты вне контура АИС «СВХ» — их операции в поток `weighing.completed.*` не попадают (гарантия стороны весовой системы; уточнение 20.08.2026, интерфейс АИС не меняет) |
| Свойства сообщения | `content_type: application/json`, `delivery_mode: 2` (persistent), `message_id` = `event_id`, `type: weighing.completed`, `timestamp`, `app_id: vesy-center` |

### 7.3 Сообщение

```json
{
  "event_id": "b3f6c2a1-9d0e-4c7b-8a5f-2e1d3c4b5a69",
  "type": "weighing.completed",
  "version": 1,
  "published_at": "2026-08-14T11:05:04+06:00",
  "ais_object": "0013",
  "weighing": { "…": "документ операции, раздел 5" }
}
```

В конверте: `event_id` (уникален; повторная публикация несёт тот же `event_id`), `type`, `version`, `published_at`, `ais_object` — специальный идентификатор СВХ (продублирован из документа, чтобы разбирать одну очередь по объектам без чтения тела). Тело — `weighing`, документ операции.

### 7.4 Гарантии и обязанности консьюмера

- Доставка at-least-once: одно и то же событие может прийти повторно (переподключение, повторная публикация по запросу). Консьюмер сохраняет операцию upsert'ом по `weighing.id` и подтверждает (`ack`) только после сохранения. Ошибка обработки — не подтверждать (`nack` / разрыв), сообщение вернётся в очередь.
- Порядок не гарантируется: офлайн-пачки приходят позже, тарирование может прийти после взвешивания, которое на него ссылается. Документ самодостаточен (тарирование вложено), поэтому события можно обрабатывать независимо друг от друга.
- Пока консьюмер отключён, сообщения копятся в durable-очереди без ограничения времени, ничего не теряется. Если очередь всё же утеряна — журнал за период восстанавливается запросом 8.3.
- На стороне центра события публикуются из журнала с подтверждением брокера и повторами до успеха; любую операцию можно опубликовать повторно по просьбе АИС.

### 7.5 Обратная связь: номер документа АИС для офлайн-операции

У офлайн-операции нет номера `WEI…` / `TAR…`: событие приходит с нашим `id`, номерами машины и прицепа, объектом (`ais_object`), временем, массами, тарой и фото. Дальше:

1. АИС по объекту, номеру машины и времени сопоставляет операцию с регистрацией и заводит документ взвешивания или тарирования по данным события. Если сопоставить не удалось — документ всё равно создаётся, но остаётся без привязки к регистрации; ручного сопоставления оператором нет (ответ АИС). Номер у офлайн-операции появляется всегда.
2. Заведя документ, АИС сообщает его номер центру:

```
POST /api/v2/weighings/{id}/ais_ref
Authorization: Bearer <токен>

{ "ais_ref": "WEI000094200" }
```

Ответ `200` с обновлённым документом (`{"weighing": {…}}`). Ошибки: `404 ERR_NOT_FOUND` — нет операции с таким `id`; `409 ERR_ALREADY_LINKED` — у операции уже другой номер АИС либо этот номер уже привязан к другой операции; `422 ERR_VALIDATION` — префикс номера не соответствует операции. Повторный вызов с тем же номером — `200`, без изменений.

3. С этого момента `ais_ref` заполнен во всех каналах: в GET-ответах, в панели центра (страница записи) и во вложении `tare.ais_ref` у взвешиваний, которые считались по этой таре. Сама операция при этом не меняется — привязка хранится рядом с записью, не в ней.

Центр показывает диспетчеру офлайн-операции без номера АИС, чтобы «зависшие» сопоставления были видны и с нашей стороны.

## 8. Запросы для сверки

Все — `GET`, тот же токен, ответы `200` с JSON; `404 ERR_NOT_FOUND` — нет такой записи.

### 8.1 Документ по id

`GET /api/v2/weighings/{id}` → `{"weighing": {…}}`

### 8.2 Документ по номеру АИС

`GET /api/v2/weighings?ais_ref=WEI000094176` → `{"weighings": [{…}]}` — пустой список, если операция по этому номеру не состоялась. Способ проверить исход команды, не запуская повтор.

### 8.3 Список за период

`GET /api/v2/weighings?from=2026-08-14T00:00:00%2B06:00&to=2026-08-15T00:00:00%2B06:00&ais_object=0014&scale_no=1&operation=weighing&page=1&per_page=200`

→ `{"weighings": [{…}], "page": 1, "per_page": 200, "total": 57}`. Отбор по `weighed_at`, сортировка по возрастанию; `ais_object`, `scale_no`, `operation` необязательны; `per_page` ≤ 200. Для сверки журналов и восстановления после сбоев, в том числе поиска офлайн-операций без номера АИС (`source=local_offline&unlinked=true`).

## 9. Правила тары, нетто и журнала

- Тара привязана к сцепке — паре «голова + прицеп». Тарирование без прицепа действует только для машины без прицепа; смена прицепа означает, что действующей тары нет и нужно новое тарирование.
- Действует последнее тарирование сцепки не старше 3 календарных месяцев на момент взвешивания. Реестр тарирований единый по всем объектам: тарироваться и взвешиваться можно на разных весах.
- Единственный источник тары — тарирования, проведённые через весовую систему (по командам АИС или офлайн). Справочников тары и ручного ввода массы нет; АИС тару не передаёт и не выбирает.
- Записи журнала неизменяемы: не редактируются и не удаляются; исправление — только сторнированием новой записью. Фото и запись связаны контрольными суммами.
- Отказы не записываются: журнал состоит только из состоявшихся операций.

## 10. Отличия от контракта v1

Совместимый контракт v1 (`POST /api/v1/weigh`, формат UniServer) продолжает работать; АИС переходит сразу на v2. Отличия:

| Аспект | v1 | v2 |
|---|---|---|
| Адресация весов | `ip_address` + `port` + `autoscale` (адрес UniServer объекта) | `ais_object` (специальный идентификатор СВХ) + `scale_no` |
| Авторизация | `username` / `password` в теле (`admin` / `admin`) | `Authorization: Bearer <токен>` + IP-allowlist |
| Ссылка на документ АИС | нет | `ais_ref` (`WEI…` / `TAR…`), идемпотентность по номеру, обратная связь для офлайн-операций |
| Ответ | Плоский: `code, massa, weighing_datetime, unit_meas, front_image, rear_image, tare, tare_datetime, netto, no_valid_tare` | `code` + документ операции: id, номер карточки, объект / весы с поверкой, тарирование во вложении со статусом, фото с sha256, контрольная сумма |
| Устаревшая тара | `tare: null, netto: null, no_valid_tare: true` | `tare.status: "expired"` с датой, массой и номером тарирования; `netto: null` |
| HTTP-статусы | Всегда 200 | 200 для исходов операции; 401 / 403 / 404 / 422 для неверного запроса |
| Офлайн-операции | не доставляются | RabbitMQ `weighing.completed` + обратная связь номером АИС |
| Сверка | нет | GET по id, по номеру АИС, за период |
| Даты | ISO 8601 с `+06:00` (уже в v1) | так же |

5. Параллельная работа: АИС продолжает работать через старую цепочку, новые запросы проверяются на тестовом контуре и на пилотных объектах (СВХ «Кызыл-Кыя», ПЗТК «Джалал-Абад»).
6. Переключение по объектам; UniServer выводится из эксплуатации пообъектно.

## 12. Возможные расширения (не входят в первую версию)

По ответу АИС от 17.08.2026 в первой версии не нужны; описаны, чтобы их можно было заказать позже без смены контракта:

- Проверка тары до взвешивания — `GET /api/v2/tares?vehicle_number=…&trailer_number=…`: до команды «Взвесить» показать оператору, есть ли у сцепки действующее тарирование, когда снято или что оно устарело (иначе брутто пройдёт без нетто). Могло бы стоять за кнопкой «Найти тару ТС».
- Событие `agent.status` — потеря / восстановление связи центра с весовым ПК объекта: АИС могла бы показывать «весы объекта недоступны, взвешивание идёт на месте вручную» и не слать команды, которые кончатся `ERR_AGENT_OFFLINE`.
- Событие `weighing.reversed` — сторнирование записи: АИС могла бы автоматически аннулировать свой документ. С 04.09.2026 сторнирование в весовой системе есть (поле `storno` у записи, 5.2), событие по-прежнему не публикуется — по запросу АИС.
- Публикация `weighing.completed` и по онлайн-операциям — если АИС захочет строить журнал из одного потока.
