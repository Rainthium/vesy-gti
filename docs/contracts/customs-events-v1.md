## 1. Назначение и общая схема

Единая весовая система ОАО «ГТИ» (далее — весовая система) обслуживает весы на объектах ГТИ: статические автомобильные весы на СВХ, ПЗТК и ВЗТК и — по мере подключения — динамические (поосные) весы на пунктах пропуска. На каждом весовом ПК работает агент (читает индикатор, снимает камеры, ведёт локальный журнал); центральный сервер (далее — центр) хранит журнал операций и фотографии, ведёт единый реестр тарирований и считает нетто.

Таможенная система получает от центра каждое взвешивание и каждое тарирование по всем объектам — сразу после записи операции в журнал центра. Канал один: события в RabbitMQ таможенной системы. Команд в сторону весов у таможенной системы нет — поток только на чтение.

| Канал | Направление | Когда | Что |
|---|---|---|---|
| Событие `weighing.completed` | центр → таможня | Сразу после записи операции в журнал центра: обычно секунды после операции; операции, выполненные на объекте без связи с центром, — после восстановления связи | Документ операции (раздел 5) |
| Событие `weighing.reversed` | центр → таможня | Запись аннулирована сторнированием в весовой системе | Тот же документ с заполненным `storno` (5.2) |
| `GET /api/v2/weighings…` | таможня → центр | По необходимости | Сверка: документ по id, список за период (раздел 8) |
| `GET /vesy/…jpeg` | таможня → центр | По необходимости | Файлы снимков по ссылкам из документа (раздел 6) |

Первая редакция описывает статические весы. Динамические весы добавятся отдельным типом события с тем же конвертом (раздел 10); сообщения по статическим весам при этом не изменятся.

## 2. Соглашения о данных

- JSON, UTF-8. Имена полей — `snake_case`. Незнакомые поля и незнакомые типы событий потребитель игнорирует: весовая система может добавлять поля и типы без смены версии контракта; удаление или переименование поля — только новой версией (поле `version` конверта).
- Время — ISO 8601 с явным поясом Бишкека: `2026-09-09T14:55:45+06:00`. Все моменты приведены к `+06:00` (в базе центра хранится UTC).
- Массы — числа JSON в килограммах, возможна дробная часть: `43310.0`. Дискретность индикаторов 10–20 кг, но полагаться на целочисленность не следует.
- Идентификаторы:
  - `id` — UUID операции в весовой системе (строка из 36 символов), уникален и не меняется; ключ дедупликации операций;
  - `event_id` — UUID события; детерминирован по операции и типу события: повторная публикация того же события несёт тот же `event_id`;
  - `site.code` — код объекта в весовой системе (`kyzyl-kyia`), постоянный;
  - `site.customs_code` — код объекта в таможенной системе: необязательное текстовое поле справочника центра, заполняет администратор весовой системы по справочнику таможни; передаётся вместе с наименованием объекта; `null`, пока не заполнен;
  - `ais_ref` — номер документа АИС «СВХ» (`WEI` + 9 цифр у взвешивания, `TAR` + 9 цифр у тарирования), справочно; у операций без участия АИС — `null`;
  - `card_number` — номер печатной весовой карточки (`ВЕС-20260814-153012`, `ТАР-20260612-102100`), справочно.
- Номера ТС — строки до 32 символов; центр приводит к верхнему регистру и обрезает пробелы по краям. `trailer_number: null` — машина без прицепа. Оператор — до 200 символов.
- Тексты (`storno.reason` и т.п.) — на русском.

## 3. Подключение и безопасность

| Параметр | Значение |
|---|---|
| Брокер | RabbitMQ таможенной системы; адрес, порт и параметры TLS сообщает таможенная сторона. Центр подключается к брокеру **исходящим** соединением с сервера центра; входящих соединений к центру для событий не требуется. AMQP 0-9-1; TLS (порт 5671) предпочтительно. |
| Учётная запись | Выдаёт таможенная сторона: право публиковать в согласованный exchange (или напрямую в очередь) в выделенном vhost. У центра хранится как секрет. |
| Exchange и очередь | Предложение: exchange `vesy.events` типа `topic`, durable; очередь `customs.weighings`, durable, без TTL, привязка `weighing.#`. Объявляет и сопровождает владелец брокера (таможенная сторона); центр топологию не меняет. Возможен вариант публикации напрямую в очередь без exchange — согласовать. |
| Routing key | `<type>.<site.code>`: `weighing.completed.kyzyl-kyia`, `weighing.reversed.kokcho-koz` — поток делится по объектам без разбора тела. Код объекта в весовой системе есть всегда (в отличие от необязательного `customs_code`). |
| Свойства сообщения | `content_type: application/json`, `delivery_mode: 2` (persistent), `message_id` = `event_id`, `type` = тип события, `timestamp`, `app_id: vesy-center`. |
| Подтверждения | Publisher confirms: событие считается доставленным только после подтверждения брокера; до подтверждения центр повторяет отправку. |
| Доступ к фото и запросам сверки | `Authorization: Bearer <токен>` — сервисный, отзываемый, выдаётся весовой системой; плюс IP-адреса серверов таможенной системы в белом списке центра. Базовый адрес центра — предварительно `http://192.168.140.70` (сеть ГТИ); после установки сертификата — HTTPS по доменному имени, пути не меняются. Сетевой доступ от таможенной системы к центру — вопрос раздела 12. |
| Ответ при отказе в доступе | `401` — нет или неверный токен; `403` — адрес не в списке. Тело — JSON `{"code": "ERR_UNAUTHORIZED" или "ERR_FORBIDDEN", "message": "…"}`. |
| Размер сообщения | Документ операции — 3–5 КБ. Фото в сообщение не вкладываются (раздел 6). |

| Поле | Тип | Описание |
|---|---|---|
| `event_id` | UUID | Идентификатор события. Повторная публикация того же события — тот же `event_id`; ключ дедупликации событий. |
| `type` | строка | `weighing.completed` — операция записана; `weighing.reversed` — запись аннулирована сторнированием. Типы для динамических весов появятся во второй редакции (раздел 10); незнакомые типы игнорировать. |
| `version` | целое | Версия формата документа, сейчас `1`. |

| `producer` | строка | Всегда `vesy-center`. |
| `site` | объект | Объект: `code` — код в весовой системе, `name` — наименование, `customs_code` — код в таможенной системе или `null`. Продублирован из документа, чтобы разбирать поток без чтения тела. |
| `scale_kind` | `static` / `dynamic` | Вид весов. В первой редакции всегда `static`. |
| `weighing` | объект | Документ операции (раздел 5). |

## 5. Документ операции (статические весы)

Один и тот же JSON-объект приходит в событиях и по GET-запросам сверки. Это одна и та же запись журнала центра: сама операция (вес, время, номера, тара, нетто, фото) везде совпадает. Позже заполняются только сопутствующие поля: `photos.*.available` (файлы снимков доезжают с объекта чуть позже, раздел 6), `ais_ref` у операций, выполненных без АИС «СВХ» (если АИС «СВХ» позже заведёт по ним документ), и `storno` (событием `weighing.reversed`).

### 5.2 Поля документа

| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID | Идентификатор операции в весовой системе. Один и тот же на весовом ПК, в центре и во всех каналах. Ключ дедупликации операций. |
| `card_number` | строка | Номер печатной весовой карточки (`ВЕС-` / `ТАР-ГГГГММДД-ЧЧММСС` от бишкекского времени операции). Справочный. |
| `operation` | `weighing` / `taring` | Взвешивание (брутто) или тарирование (масса порожней сцепки). |
| `source` | `ais` / `local_offline` | `ais` — по команде АИС «СВХ»; `local_offline` — вручную оператором весового ПК без участия АИС «СВХ»: при потере связи с центром (дослана после восстановления) либо на объекте, где АИС «СВХ» нет (ручной режим разрешён администратором весовой системы). |
| `ais_ref` | строка или null | Номер документа АИС «СВХ». Справочно: у операций `source: ais` — из команды; у ручных — `null`, пока АИС «СВХ» не заведёт по операции документ и не сообщит номер. |
| `site` | объект | Объект: `code` — код в весовой системе, `name` — наименование, `customs_code` — код в таможенной системе или `null`, `ais_object` — идентификатор объекта в АИС «СВХ» или `null` (справочно). |
| `scale` | объект | Весы: `id` — id в справочнике центра, `no` — номер весов на объекте, `kind` — `static` (динамические — раздел 10), `name`, `verification` — свидетельство о поверке этих весов (`number`, `date`, `valid_until`; `null`, если не заполнено). |
| `weighed_at` | дата-время | Момент фиксации веса. Для операций по команде АИС «СВХ» — по часам центра; для ручных — по часам весового ПК. |
| `recorded_at` | дата-время | Момент записи в журнал центра. У операций, выполненных без связи с центром, позже `weighed_at` — на время без связи. |
| `vehicle_number`, `trailer_number` | строка; строка или null | Номера головы (тягача / автомобиля) и прицепа после нормализации. |
| `operator` | строка или null | Кто провёл операцию: для команд АИС «СВХ» — ФИО оператора АИС из команды; для ручных — учётная запись оператора весового ПК. |
| `unit` | строка | Всегда `kg`. |
| `massa` | число | Измеренная масса: при взвешивании — брутто, при тарировании — тара (масса порожней сцепки). |
| `tare` | объект или null | Тарирование сцепки, найденное для этого взвешивания (5.3). У тарирований — `null`. |
| `netto` | число или null | Брутто − тара. `null`, если тара не подставлена (5.3). У тарирований — `null`. |
| `photos` | объект | Снимки `front` (перед) и `rear` (зад): `url` — постоянный путь относительно базового адреса центра, `sha256` — контрольная сумма файла, `available` — файл уже доставлен в центр (раздел 6). |
| `storno` | объект или null | Запись аннулирована сторнированием: `at` — момент сторно, `reason` — причина. Исходная запись при этом не меняется (раздел 9); для весовой системы операция «как не было»: тарирование выпадает из реестра тар, в отчёты не входит. `null` — запись действует. Аннулирование приходит событием `weighing.reversed`. |
| `checksum` | строка | Контрольная сумма записи (SHA-256 по ключевым полям и хешам фото). Запись неизменяема; сумма позволяет доказать это при спорах. |

### 5.3 Тарирование во вложении

Поле `tare` показывает, что весовая система знала о таре этой сцепки на момент взвешивания:

| `tare` / `tare.status` | Смысл | `netto` |
|---|---|---|
| `null` | Тарирований этой сцепки (пары голова + прицеп) в системе не было. | `null` |
| `applied` | Тарирование действовало на момент взвешивания и подставлено в расчёт. Записано в операцию и не меняется задним числом. | число |
| `expired` | Последнее тарирование сцепки истекло к моменту взвешивания (старше 3 календарных месяцев). Приводятся его id, дата и масса; в расчёт не подставлено. | `null` |
| `not_applied` | Тарирование по сроку действовало, но не подставлено; причина в `reason`: `tare_not_below_gross` — тара не меньше брутто (сцепка тарирована ошибочно, гружёной), `replica_lag` — ручное взвешивание на объекте, у которого локальная копия реестра ещё не содержала это тарирование. | `null` |

Инвариант: `netto` не `null` тогда и только тогда, когда `tare.status == "applied"`. Поля объекта `tare`: `status`, `reason` (`null` у статусов кроме `not_applied`), `id` (UUID тарирования), `card_number`, `ais_ref` (`null`, если номера нет), `tared_at`, `massa`, `storno` (тарирование сторнировано после того, как было подставлено; запись взвешивания при этом не меняется).

## 6. Фотографии

- Два снимка на каждую операцию статических весов: `front` (перед) и `rear` (зад), JPEG в родном разрешении камеры с оверлеем весовой системы (объект, дата-время, вес). Размер 0,2–1,5 МБ в зависимости от камеры объекта.
- Ссылка постоянная: `GET <базовый адрес>/vesy/ГГГГ/ММ/ДД/<id без дефисов>_photo1.jpeg` (`photo1` — перед, `photo2` — зад) с заголовком `Authorization: Bearer <токен>` и с разрешённого IP-адреса. Снимки скачивает сервер таможенной системы и показывает своим пользователям сам; браузер пользователя к центру не обращается.
- Файл после сохранения не пересжимается и не заменяется никогда; `sha256` в документе — его контрольная сумма. Ответ несёт `ETag` (= sha256) и `Cache-Control: immutable` — кэшировать можно бессрочно.
- Сразу после операции файл может ещё ехать с объекта: в норме секунды, при потере связи с объектом — до её восстановления. На это время `404`, в документе `available: false`. Повторить позже; `404` не кэшировать как «фото нет».
- Статусы: `200 image/jpeg`; `401` / `403` — доступ; `404` — файл ещё не доставлен либо путь неверен.
- Срок хранения в центре — 5 лет с момента операции. Скачивания журналируются центром.

## 7. Гарантии доставки и обязанности потребителя

- Поток строится по схеме outbox: строка события появляется в той же транзакции, что и запись операции, и публикуется фоновым процессом с подтверждением брокера и повторами до успеха. Пока брокер таможенной системы недоступен, события копятся у центра и уходят после восстановления связи в порядке постановки; неотправленное видно на дашборде и в мониторинге весовой системы («события в таможню не уходят»).
- Доставка at-least-once: одно и то же событие может прийти повторно (переподключение, повторная публикация по запросу). Потребитель сохраняет операцию upsert'ом по `weighing.id` (или отбрасывает повтор по `event_id`) и подтверждает (`ack`) только после сохранения. Ошибка обработки — не подтверждать (`nack` / разрыв), сообщение вернётся в очередь.
- Порядок не гарантируется: операции, выполненные без связи с центром, приходят позже; тарирование может прийти после взвешивания, которое на него ссылается. Документ самодостаточен (тарирование вложено), поэтому события обрабатываются независимо друг от друга.
- `weighing.reversed` может прийти раньше `weighing.completed` той же операции только при повторной публикации; документ в обоих событиях один и тот же, поэтому обрабатывать их можно в любом порядке: `storno != null` означает «запись аннулирована».
- Пока потребитель отключён, сообщения копятся в durable-очереди без ограничения времени, ничего не теряется. Если очередь всё же утеряна — журнал за период восстанавливается запросом 8.2, а по просьбе таможенной стороны центр публикует события за любой период повторно.
- История: при подключении центр по договорённости публикует операции с согласованной даты (журнал ведётся с 02.09.2026, шесть объектов).

## 8. Запросы для сверки

Все — `GET`, тот же токен, ответы `200` с JSON; `404 ERR_NOT_FOUND` — нет такой записи. Ответы несут тот же документ операции (раздел 5).

### 8.1 Документ по id

`GET /api/v2/weighings/{id}` → `{"weighing": {…}}`

### 8.2 Список за период

`GET /api/v2/weighings?from=2026-09-08T00:00:00%2B06:00&to=2026-09-09T00:00:00%2B06:00&site=kokcho-koz&operation=weighing&page=1&per_page=200`

→ `{"weighings": [{…}], "page": 1, "per_page": 200, "total": 57}`. Отбор по `weighed_at`, сортировка по возрастанию; `site` (код объекта в весовой системе), `operation`, `source` необязательны; `per_page` ≤ 200. Параметр `site` добавляется для этой интеграции (в API для АИС «СВХ» объект задаётся её идентификатором).

## 9. Правила тары, нетто и журнала

- Тара привязана к сцепке — паре «голова + прицеп». Тарирование без прицепа действует только для машины без прицепа; смена прицепа означает, что действующей тары нет и нужно новое тарирование.
- Действует последнее тарирование сцепки не старше 3 календарных месяцев на момент взвешивания. Реестр тарирований единый по всем объектам: тарироваться и взвешиваться можно на разных весах.
- Единственный источник тары — тарирования, проведённые через весовую систему. Справочников тары и ручного ввода массы нет.
- Тарирование тяжелее лимита тары весов (по умолчанию 25 000 кг) весовая система не проводит: на платформе гружёная машина, а не порожняя сцепка.
- Записи журнала неизменяемы: не редактируются и не удаляются; исправление — только сторнированием новой записью (событие `weighing.reversed`). Фото и запись связаны контрольными суммами.
- Отказы не записываются: журнал состоит только из состоявшихся операций.

## 10. Динамические весы (вторая редакция)

Динамические (поосные) весы на пунктах пропуска подключаются позже (обследование «Торугарт»: двое Тензо-М ВА-Д-20; Кен-Сай: Уралвес ВАТ-Д-20 — этап 3 плана весовой системы). Для них появится отдельный тип события с тем же конвертом (раздел 4) и `scale_kind: "dynamic"`; сообщения статических весов не изменятся. Предварительный состав, будет уточнён после обследования оборудования и вопросов таможенной стороны:

- тип `axle_weighing.completed` (название предварительное) и, для аннулирования, `axle_weighing.reversed`;
- документ: `id`, `site`, `scale` (`kind: "dynamic"`, `verification`), `passed_at` (момент проезда), `direction` / `lane`, `speed`, `mode` (динамический проезд или статическая остановка на платформе), `vehicle_number` (распознанный номер или введённый оператором) и `trailer_number`, `axles` — список осей `{no, load, spacing}` (нагрузка и расстояние до следующей оси), `axle_groups` — группы осей с суммарной нагрузкой, `total_mass`, `photos` (число снимков и ракурсы — по оборудованию), `operator` (`null` при автоматическом проезде), `checksum`;
- тары и нетто у поосного взвешивания нет: `tare` и `netto` не передаются.

До второй редакции потребитель игнорирует незнакомые типы событий (раздел 2).

## 11. Порядок внедрения

1. Согласование этой редакции с таможенной стороной: ответы на вопросы раздела 12 → версия 1.0.
2. Таможенная сторона: брокер, vhost, учётная запись для центра, топология (exchange, очередь, привязка), сетевой доступ от сервера центра `192.168.140.70` к брокеру (порт 5671/5672) и от серверов таможенной системы к центру (HTTP/HTTPS для фото и сверки); справочник кодов объектов.
3. Весовая система: поле «код таможни» у объекта в справочнике, второй поток outbox и публикатор со своим подключением и мониторингом, фильтр `site` в списке за период, токен и белый список для серверов таможни. Меняется только центр; агенты на объектах не затрагиваются.
4. Тестовый контур: тестовая очередь, примеры сообщений и эталонный скрипт-потребитель от весовой системы; прогон на реальных операциях пилотных объектов.
5. Публикация истории с согласованной даты, затем — боевой поток. Ожидаемый объём: сейчас около 250 операций в сутки на шести объектах, с ростом по мере подключения остальных объектов (всего 13).
6. Вторая редакция — динамические весы (раздел 10), после подключения первого пункта пропуска.

## 12. Вопросы к таможенной стороне

1. Брокер: адрес, порт, TLS (сертификат, проверка), vhost, учётная запись для центра; кто объявляет exchange и очередь; имена и routing key — подходит ли предложение раздела 3; ограничение размера сообщения.
2. Сеть: доступ от сервера центра к брокеру (исходящий) и от серверов таможенной системы к центру для фото и сверки (входящий); адреса серверов таможенной системы для белого списка; нужен ли VPN.
3. Справочник объектов: коды СВХ / ПЗТК / ВЗТК и пунктов пропуска в таможенной системе для поля `customs_code`; нужны ли отдельные коды для весов внутри объекта.
4. Достаточно ли номера свидетельства о поверке в каждом сообщении (`scale.verification`), нужны ли дополнительные реквизиты весов (заводской номер, тип).
5. Фото: устраивает ли получение по ссылке с токеном и белым списком; нужны ли снимки сразу в сообщении (не рекомендуем: 0,5–3 МБ на операцию).
6. Аннулирование: нужно ли событие `weighing.reversed` или достаточно поля `storno` в документе при сверке.
7. История: с какой даты публиковать операции при подключении.
8. Подпись: нужна ли электронная подпись сообщений или достаточно `checksum` и `sha256` фото; если нужна — какой формат.
9. Динамические весы: какие параметры проезда нужны таможенной системе (оси, группы, скорость, направление, распознанный номер) — заготовка второй редакции.
10. Тестовый контур: есть ли тестовый брокер и с какого момента можно начинать прогон.
