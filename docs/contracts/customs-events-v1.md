## 1. Назначение и общая схема

Единая весовая система ОАО «ГТИ» (далее — весовая система) обслуживает весы на объектах ОАО «ГТИ»: статические автомобильные весы на СВХ, ПЗТК и ВЗТК и — по мере подключения — динамические (поосные) весы на пунктах пропуска. На каждом весовом ПК работает агент (читает индикатор, снимает камеры, ведёт локальный журнал); центральный сервер (далее — центр) хранит журнал операций и фотографии, ведёт единый реестр тарирований и считает нетто.

Таможенная система получает от центра каждое взвешивание и каждое тарирование по всем объектам — сразу после записи операции в журнал центра. Канал один: события в RabbitMQ таможенной системы. Команд в сторону весов у таможенной системы нет — поток только на чтение.

| Канал | Направление | Когда | Что |
|---|---|---|---|
| Событие `weighing.completed` | центр → таможня | Сразу после записи операции в журнал центра: обычно секунды после операции; операции, выполненные на объекте без связи с центром, — после восстановления связи | Документ операции (раздел 5) |
| Событие `weighing.reversed` | центр → таможня | Запись аннулирована сторнированием в весовой системе | Тот же документ с заполненным `storno` (5.2) |
| Событие `weighing.rejected` | центр → таможня | Тарирование по команде АИС «СВХ» отклонено: масса выше лимита тары | Сведения об отказе (5.5); операции в журнале нет |
| `GET /api/v2/weighings…` | таможня → центр | По необходимости | Сверка: документ по id, список за период (раздел 8) |
| `GET /vesy/…jpeg` | таможня → центр | По необходимости | Файлы снимков по ссылкам из документа (раздел 6) |
| `GET /api/v2/sites` | таможня → центр | По необходимости | Справочник объектов и весов (раздел 8.3) |

Первая редакция описывает статические весы. Динамические весы добавятся отдельным типом события с тем же конвертом (раздел 10); сообщения по статическим весам при этом не изменятся.

## 2. Соглашения о данных

- JSON, UTF-8. Имена полей — `snake_case`. Незнакомые поля и незнакомые типы событий потребитель игнорирует: весовая система может добавлять поля и типы без смены версии контракта; удаление или переименование поля — только новой версией (поле `version` конверта).
- Время — ISO 8601 с явным поясом Бишкека, с точностью до секунды: `2026-09-09T14:55:45+06:00`. Все моменты приведены к `+06:00` (в базе центра хранится UTC). Единственное исключение — `weighed_at_utc`: тот же момент фиксации веса в UTC с полной точностью хранения, нужен для проверки `checksum` (приложение Б).
- Массы — числа JSON в килограммах, возможна дробная часть: `43310.0`. Дискретность индикаторов 10–20 кг, но полагаться на целочисленность не следует.
- Идентификаторы:
  - `id` — UUID операции в весовой системе (строка из 36 символов), уникален и не меняется; ключ дедупликации операций;
  - `event_id` — UUID события; детерминирован по операции и типу события: повторная публикация того же события несёт тот же `event_id`;
  - `site.code` — код объекта в весовой системе (`kyzyl-kyia`), постоянный;
  - `site.customs_code` — код таможенного органа, к которому относится объект, по справочнику подразделений таможенной системы (пример: `41714106`); заполняет администратор весовой системы по списку Таргет-центра. К началу боевого потока заполнен у всех подключённых объектов; `null` возможен только на тестовом прогоне и у объекта, подключённого к весовой системе позже, — до получения его кода. Изменение кода объекта — с предварительным уведомлением Таргет-центра. Несколько объектов одного органа несут один код; объект однозначно определяют `site.code` и `site.ais_object`;
  - `ais_ref` — номер документа АИС «СВХ» (`WEI` + 9 цифр у взвешивания, `TAR` + 9 цифр у тарирования), справочно; у операций без участия АИС — `null`;
  - `card_number` — номер печатной весовой карточки (`ВЕС-20260814-153012`, `ТАР-20260612-102100`), справочно.
- Номера ТС — строки до 32 символов. Правила нормализации (других преобразований нет):
  - номер вводит человек: оператор АИС «СВХ» (приходит в команде) или оператор весового ПК (ручная операция). Распознавания номеров на статических весах нет, поэтому «нераспознанного номера» не бывает;
  - весовая система приводит номер к верхнему регистру и обрезает пробелы по краям — и только;
  - алфавит не меняется: кириллица остаётся кириллицей, латиница — латиницей, транслитерации нет;
  - внутренние пробелы, дефисы и прочие знаки сохраняются как введены;
  - `vehicle_number` у операции есть всегда; `trailer_number: null` — машина без прицепа;
  - тара ищется по точному совпадению пары строк «голова + прицеп» после этой нормализации.
  Для связи с карточками и декларациями потребителю следует сравнивать номера после собственной канонизации (например, без пробелов и дефисов, с приведением похожих букв кириллицы к латинице). Ужесточение нормализации на стороне весовой системы возможно новой редакцией — оно меняет ключ реестра тар и требует согласования с АИС «СВХ».
- Оператор — строка до 200 символов.
- Тексты (`storno.reason` и т.п.) — на русском.

## 3. Подключение и безопасность

| Параметр | Значение |
|---|---|
| Брокер | RabbitMQ таможенной системы, `192.168.0.115`, AMQP 0-9-1 по TLS, порт 5671. Центр подключается к брокеру **исходящим** соединением с сервера центра `192.168.140.70`; входящих соединений к центру для событий не требуется. Сертификат удостоверяющего центра брокера передаёт Таргет-центр, центр проверяет цепочку. Если к началу теста TLS на брокере ещё не включён, тестовый прогон начинается по порту 5672 внутри сети; переход на 5671 — до публикации истории в боевой exchange. |
| Учётная запись | Отдельная учётная запись центра `vesy-center` в vhost Таргет-центра с единственным правом — публиковать в `vesy.events` и `vesy.events.test` (без чтения очередей и без настройки топологии). Выдаёт Таргет-центр; пароль передаётся лично, не в переписке; у центра хранится как секрет. |
| Exchange и очередь | Согласовано: exchange `vesy.events` типа `topic`, durable; очередь `customs.weighings`, durable, без TTL, привязка `weighing.#`. Очередь одна на все объекты; ключ маршрутизации лишь позволяет потребителю при желании разделить поток собственными очередями. Объявляет и сопровождает Таргет-центр; центр топологию не меняет. |
| Тестовый контур | Отдельный exchange `vesy.events.test` (topic, durable) с очередью `customs.weighings.test` и привязкой `weighing.#`. На время теста центр публикует только в него; переход на боевой поток — сменой имени exchange в настройке центра. Так тестовые сообщения не попадают в боевую очередь, а формат и ключи совпадают с боевыми. Сервер центра один — тестового экземпляра весовой системы нет, прогон идёт на реальных операциях. |
| Routing key | `<type>.<site.code>`: `weighing.completed.kyzyl-kyia`, `weighing.reversed.kokcho-koz` — поток делится по объектам без разбора тела. Код объекта в весовой системе есть всегда (в отличие от необязательного `customs_code`). |
| Свойства сообщения | `content_type: application/json`, `delivery_mode: 2` (persistent), `message_id` = `event_id`, `type` = тип события, `timestamp`, `app_id: vesy-center`. |
| Подтверждения | Publisher confirms: событие считается доставленным только после подтверждения брокера; до подтверждения центр повторяет отправку. |
| Базовый адрес центра | `https://vesy.gti.kg` — HTTPS, сертификат публичного удостоверяющего центра на `*.gti.kg`. Один адрес для теста и для боевой работы. К нему добавляются пути из документа: `/vesy/…` (фото) и `/api/v2/…` (сверка, справочник). Запросы принимает прокси ОАО «ГТИ» `192.168.6.134`, порт 443; имя `vesy.gti.kg` в сети Таргет-центра должно разрешаться в этот адрес. Запасной адрес на случай недоступности HTTPS — `http://192.168.140.70`, пути те же. |
| Доступ к фото и запросам сверки | `Authorization: Bearer <токен>` плюс белый список адресов центра: согласован один адрес — `192.168.0.115` (прокси Таргет-центра). Порядок проверок: сначала токен (`401`), затем адрес (`403`). |
| Токен | Отдельный сервисный токен для Таргет-центра (не общий с АИС «СВХ»), только чтение. Выдаёт администратор весовой системы ответственному Таргет-центра лично или по защищённому каналу — не в переписке и не в документах. Отзыв и замена — по обращению любой из сторон, в течение рабочего дня; старый токен перестаёт действовать в момент замены. |
| Лимиты запросов | Фото (`/vesy/`): до 50 запросов в секунду с адреса, всплеск до 100; сверх — `429`, повторить с паузой. Запросы сверки: `per_page` ≤ 200; отдельного лимита частоты нет, просим выполнять постранично и последовательно. |
| Ответ при отказе в доступе | `401` — нет или неверный токен; `403` — адрес не в списке. Тело — JSON `{"code": "ERR_UNAUTHORIZED" или "ERR_FORBIDDEN", "message": "…"}`. |
| Размер сообщения | Документ операции — 3–5 КБ. Фото в сообщение не вкладываются (раздел 6). |

## 4. Конверт события и свойства сообщения

```json
{
  "event_id": "5731e48c-0ae4-518a-ac11-f4f28344c34b",
  "type": "weighing.completed",
  "version": 1,
  "published_at": "2026-09-09T13:26:51+06:00",
  "producer": "vesy-center",
  "site": {
    "code": "jalal-abad",
    "name": "ПЗТК «Джалал-Абад»",
    "customs_code": "…"
  },
  "scale_kind": "static",
  "weighing": { "…": "документ операции, раздел 5" }
}
```

| Поле | Тип | Описание |
|---|---|---|
| `event_id` | UUID | Идентификатор события. Повторная публикация того же события — тот же `event_id`; ключ дедупликации событий. |
| `type` | строка | `weighing.completed` — операция записана; `weighing.reversed` — запись аннулирована сторнированием; `weighing.rejected` — тарирование отклонено, операции нет (5.5). Типы для динамических весов появятся во второй редакции (раздел 10); незнакомые типы игнорировать. |
| `version` | целое | Версия формата документа, сейчас `1`. |
| `published_at` | дата-время | Момент публикации центром. |
| `producer` | строка | Всегда `vesy-center`. |
| `site` | объект | Объект: `code` — код в весовой системе, `name` — наименование, `customs_code` — код в таможенной системе или `null`. Продублирован из документа, чтобы разбирать поток без чтения тела. |
| `scale_kind` | `static` / `dynamic` | Вид весов. В первой редакции всегда `static`. |
| `weighing` | объект | Документ операции (раздел 5). У `weighing.rejected` этого поля нет. |
| `rejection` | объект | Только у `weighing.rejected`: сведения об отклонённом тарировании (5.5). |

## 5. Документ операции (статические весы)

Один и тот же JSON-объект приходит в событиях и по GET-запросам сверки. Это одна и та же запись журнала центра: сама операция (вес, время, номера, тара, нетто, фото) везде совпадает. Позже заполняются только сопутствующие поля: `photos.*.available` (файлы снимков доезжают с объекта чуть позже, раздел 6), `ais_ref` у операций, выполненных без АИС «СВХ» (если АИС «СВХ» позже заведёт по ним документ), и `storno` (событием `weighing.reversed`).

### 5.2 Поля документа

| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID | Идентификатор операции в весовой системе. Один и тот же на весовом ПК, в центре и во всех каналах. Ключ дедупликации операций. |
| `card_number` | строка | Номер печатной весовой карточки (`ВЕС-` / `ТАР-ГГГГММДД-ЧЧММСС` от бишкекского времени операции). Справочный. |
| `operation` | `weighing` / `taring` | Взвешивание (брутто) или тарирование (масса порожней сцепки). |
| `source` | `ais` / `local_offline` | `ais` — по команде АИС «СВХ»; `local_offline` — вручную оператором весового ПК без участия АИС «СВХ»: при потере связи с центром (дослана после восстановления) либо на объекте, где АИС «СВХ» нет (ручной режим разрешён администратором весовой системы). |
| `ais_ref` | строка или null | Номер документа АИС «СВХ». Справочно: у операций `source: ais` — из команды; у ручных — `null`, пока АИС «СВХ» не заведёт по операции документ и не сообщит номер. |
| `site` | объект | Объект: `code` — код в весовой системе, `name` — наименование, `customs_code` — код в таможенной системе или `null`, `ais_object` — идентификатор объекта в АИС «СВХ» или `null` (справочно). |
| `scale` | объект | Весы: `id` — id в справочнике центра, `no` — номер весов на объекте, `kind` — `static` (динамические — раздел 10), `name`, `verification` — свидетельство о поверке этих весов (`number`, `date`, `valid_until`; `null`, если не заполнено). |
| `weighed_at` | дата-время | Момент фиксации веса — **по времени центра для всех операций, включая ручные**. Часы сервера центра синхронизированы по NTP. Агент на весовом ПК при каждом обмене с центром (раз в несколько секунд) получает время центра, хранит смещение локальных часов и ставит момент операции с этой поправкой; тем же временем подписан оверлей на снимках. Без связи с центром агент использует последнее известное смещение (сохраняется на диске и переживает перезапуск). Часы самого весового ПК используются только у агента, который ни разу не связывался с центром, — в работе такого не бывает. Погрешность — доли секунды плюс уход часов ПК за время без связи. |
| `weighed_at_utc` | строка | Тот же момент в UTC с полной точностью хранения (до микросекунд): `2026-08-14T09:30:12.345678+00:00`. Именно эта строка входит в `checksum` (приложение Б). Новое поле редакции 0.2. |
| `recorded_at` | дата-время | Момент записи в журнал центра. У операций, выполненных без связи с центром, позже `weighed_at` — на время без связи. |
| `vehicle_number`, `trailer_number` | строка; строка или null | Номера головы (тягача / автомобиля) и прицепа после нормализации (правила — раздел 2). |
| `operator` | строка или null | Кто провёл операцию: для команд АИС «СВХ» — ФИО оператора АИС из команды; для ручных — учётная запись оператора весового ПК. |
| `unit` | строка | Всегда `kg`. |
| `massa` | число | Измеренная масса: при взвешивании — брутто, при тарировании — тара (масса порожней сцепки). |
| `tare` | объект или null | Тарирование сцепки, найденное для этого взвешивания (5.3). У тарирований — `null`. |
| `netto` | число или null | Брутто − тара. `null`, если тара не подставлена (5.3). У тарирований — `null`. |
| `photos` | объект | Снимки `front` (перед) и `rear` (зад): `url` — постоянный путь относительно базового адреса центра, `sha256` — контрольная сумма файла, `available` — файл уже доставлен в центр (раздел 6). |
| `storno` | объект или null | Запись аннулирована сторнированием: `at` — момент сторно, `reason` — причина. Исходная запись при этом не меняется (раздел 9); для весовой системы операция «как не было»: тарирование выпадает из реестра тар, в отчёты не входит. `null` — запись действует. Аннулирование приходит событием `weighing.reversed`. |
| `checksum` | строка | Контрольная сумма записи: SHA-256 по идентификатору, виду операции, массе, моменту фиксации, номеру головы, источнику и хешам фото. Точный алгоритм и контрольный пример — приложение Б. Запись неизменяема; сумма позволяет доказать это при спорах. |

### 5.3 Тарирование во вложении

Поле `tare` показывает, что весовая система знала о таре этой сцепки на момент взвешивания:

| `tare` / `tare.status` | Смысл | `netto` |
|---|---|---|
| `null` | Тарирований этой сцепки (пары голова + прицеп) в системе не было. | `null` |
| `applied` | Тарирование действовало на момент взвешивания и подставлено в расчёт. Записано в операцию и не меняется задним числом. | число |
| `expired` | Последнее тарирование сцепки истекло к моменту взвешивания (старше 3 календарных месяцев). Приводятся его id, дата и масса; в расчёт не подставлено. | `null` |
| `not_applied` | Тарирование по сроку действовало, но не подставлено; причина в `reason`: `tare_not_below_gross` — тара не меньше брутто (сцепка тарирована ошибочно, гружёной), `replica_lag` — ручное взвешивание на объекте, у которого локальная копия реестра ещё не содержала это тарирование. | `null` |

**Что зафиксировано, а что может уточниться.**

- `applied`, подставленная масса тары и `netto` записаны в саму операцию в момент взвешивания и не пересчитываются никогда: ни при более позднем тарировании той же сцепки, ни при сторнировании подставленного тарирования (в этом случае заполняется только `tare.storno`).
- Если тара не подставлена, `netto` остаётся `null` навсегда: проведённое позже тарирование на прошлые взвешивания не действует.
- Статус не подставленной тары (`null` / `expired` / `not_applied`) строится по журналу центра на момент взвешивания: учитываются только тарирования с `tared_at` не позже `weighed_at`. Более позднее тарирование его не меняет. Уточниться он может в одном случае: тарирование, проведённое **раньше** взвешивания на объекте без связи, доехало до центра позже — тогда `null` сменится на `not_applied` с причиной `replica_lag`.
- Отсюда правило для показателя «без тарирования»: считать по `netto == null` (равносильно `tare.status != "applied"`) — это значение неизменно. Разбивку причин (`null` / `expired` / `not_applied`) брать при сверке, а не только из первого события.

**Тарирования, перенесённые из АИС «СВХ».** При переключении объекта с прежнего ПО на весовую систему действующие тарирования его сцепок разово перенесены из выгрузки АИС «СВХ» (около 2 800 записей, сентябрь 2026). За ними нет операции весовой системы: нет снимков, события `weighing.completed` и документа по `GET`. В потоке они видны только вложением `tare` у взвешиваний, где такая тара подставлена: `id`, `ais_ref` (номер `TAR…`), `tared_at`, `massa`. Через три месяца после переноса они естественно выбывают.

Инвариант: `netto` не `null` тогда и только тогда, когда `tare.status == "applied"`. Поля объекта `tare`: `status`, `reason` (`null` у статусов кроме `not_applied`), `id` (UUID тарирования), `card_number`, `ais_ref` (`null`, если номера нет), `tared_at`, `massa`, `storno` (тарирование сторнировано после того, как было подставлено; запись взвешивания при этом не меняется).

### 5.4 Ручная операция на объекте без АИС «СВХ»

Отличаются только эти поля:

```json
  "operation": "taring",
  "source": "local_offline",
  "ais_ref": null,
  "site": {
    "code": "kokcho-koz",
    "name": "СВХ «Кокчо-Коз»",
    "customs_code": null,
    "ais_object": "0021"
  },
  "weighed_at": "2026-09-08T15:41:26+06:00",
  "recorded_at": "2026-09-08T15:41:27+06:00",
  "operator": "operator1",
  "massa": 1780.0,
  "tare": null,

```

### 5.5 Отклонённое тарирование (событие `weighing.rejected`)

Тарирование тяжелее лимита тары весов весовая система не проводит (раздел 9). Такой отказ по команде АИС «СВХ» передаётся событием `weighing.rejected`. Это не операция: записи в журнале, фотографий и `checksum` у него нет, запросы сверки раздела 8 его не возвращают. Тело события лежит в поле `rejection` конверта; поля `weighing` в таком событии нет.

```json
{
  "id": "b6f0a2d4-7c1e-4e59-a3b8-5d2c9e7f1a40",
  "operation": "taring",
  "code": "ERR_TARE_TOO_HEAVY",
  "message": "Масса 43 310 кг больше допустимой тары 25 000 кг — это гружёная машина: проведите взвешивание, а не тарирование",
  "rejected_at": "2026-11-12T10:14:07+06:00",
  "source": "ais",
  "ais_ref": "TAR000004512",
  "site": {
    "code": "kokcho-koz",
    "name": "СВХ «Кокчо-Коз»",
    "customs_code": "…",
    "ais_object": "0021"
  },
  "scale": { "…": "блок весов, как в документе операции (5.2)" },
  "vehicle_number": "01KG777AAA",
  "trailer_number": "01KG123AB",
  "operator": "Иванов И.И.",
  "tare_limit": 25000.0,
  "massa": 43310.0
}
```

| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID | Идентификатор отказа; ключ дедупликации. С `id` операций не пересекается. |
| `operation` | строка | Всегда `taring`. |
| `code` | строка | Причина отказа. В первой редакции одна — `ERR_TARE_TOO_HEAVY`; незнакомые коды сохранять как есть. |
| `message` | строка | Текст отказа, который получил оператор АИС «СВХ». Предназначен человеку: формат не фиксируется, разбирать его не нужно — числа есть в `massa` и `tare_limit`. |
| `rejected_at` | дата-время | Момент отказа по времени центра. |
| `source` | строка | Всегда `ais` — отказ по команде АИС «СВХ». |
| `ais_ref` | строка | Номер документа АИС «СВХ», по которому запрошено тарирование. |
| `site`, `scale` | объекты | Те же блоки, что в документе операции (5.2). |
| `vehicle_number`, `trailer_number` | строка / `null` | Номера сцепки из команды, по правилам раздела 2. |
| `operator` | строка | Оператор АИС «СВХ» из команды. |
| `tare_limit` | число | Лимит тары весов на момент отказа, кг. |
| `massa` | число / `null` | Измеренная масса, кг, с округлением до килограмма. `null` — только если центр не получил массу от весового ПК. |

Что в событие не входит в первой редакции:

- отказы ручных тарирований на весовом ПК (без команды АИС «СВХ») — центр о них не знает, нужно обновление агентов;
- снимки: при отказе камеры не снимают.

Оба пункта — предмет второй редакции. Если оператор повторяет команду на той же машине, каждый отказ приходит отдельным событием со своим `id`. Ключ маршрутизации — `weighing.rejected.<site.code>`: привязка очереди `weighing.#` его уже покрывает.

## 6. Фотографии

- Два снимка на каждую операцию статических весов: `front` (перед) и `rear` (зад), JPEG в родном разрешении камеры с оверлеем весовой системы (объект, дата-время, вес). Размер 0,2–1,5 МБ в зависимости от камеры объекта.
- Ссылка постоянная: `GET <базовый адрес>/vesy/ГГГГ/ММ/ДД/<id без дефисов>_photo1.jpeg` (`photo1` — перед, `photo2` — зад) с заголовком `Authorization: Bearer <токен>` и с разрешённого IP-адреса. Снимки скачивает сервер таможенной системы и показывает своим пользователям сам; браузер пользователя к центру не обращается.
- Файл после сохранения не пересжимается и не заменяется никогда; `sha256` в документе — его контрольная сумма. Ответ несёт `ETag` (= sha256) и `Cache-Control: immutable` — кэшировать можно бессрочно.
- Сразу после операции файл может ещё ехать с объекта: в норме секунды, при потере связи с объектом — до её восстановления. На это время `404`, в документе `available: false`. Повторить позже; `404` не кэшировать как «фото нет».
- Статусы: `200 image/jpeg`; `401` / `403` — доступ; `404` — файл ещё не доставлен либо путь неверен.
- Срок хранения в центре — 5 лет с момента операции. Скачивания журналируются центром.

## 7. Гарантии доставки и обязанности потребителя

- Поток строится по схеме outbox: строка события появляется в той же транзакции, что и запись операции, и публикуется фоновым процессом с подтверждением брокера и повторами до успеха. Пока брокер таможенной системы недоступен, события копятся у центра и уходят после восстановления связи в порядке постановки; неотправленное видно на дашборде и в мониторинге весовой системы («события в таможню не уходят»).
- Доставка at-least-once: одно и то же событие может прийти повторно (переподключение, повторная публикация по запросу). Потребитель сохраняет операцию upsert'ом по `weighing.id`, отказ — по `rejection.id` (или отбрасывает повтор по `event_id`) и подтверждает (`ack`) только после сохранения. Ошибка обработки — не подтверждать (`nack` / разрыв), сообщение вернётся в очередь.
- Порядок не гарантируется: операции, выполненные без связи с центром, приходят позже; тарирование может прийти после взвешивания, которое на него ссылается. Документ самодостаточен (тарирование вложено), поэтому события обрабатываются независимо друг от друга.
- `weighing.reversed` может прийти раньше `weighing.completed` той же операции только при повторной публикации; документ в обоих событиях один и тот же, поэтому обрабатывать их можно в любом порядке: `storno != null` означает «запись аннулирована».
- Пока потребитель отключён, сообщения копятся в durable-очереди без ограничения времени, ничего не теряется. Если очередь всё же утеряна — журнал за период восстанавливается запросом 8.2, а по просьбе таможенной стороны центр публикует события за любой период повторно.
- История: при подключении центр публикует все операции с начала журнала — с 02.09.2026 — по всем подключённым объектам (на 10.11.2026 — восемь объектов, девять весов; каждый объект — со дня своего подключения), включая сторнированные записи (у них заполнено `storno`). Сначала в тестовый контур, затем повторно в боевой — `event_id` при этом те же.

## 8. Запросы для сверки

Все — `GET`, тот же токен, ответы `200` с JSON; `404 ERR_NOT_FOUND` — нет такой записи. Ответы несут тот же документ операции (раздел 5).

### 8.1 Документ по id

`GET /api/v2/weighings/{id}` → `{"weighing": {…}}`

### 8.2 Список за период

`GET /api/v2/weighings?from=2026-09-08T00:00:00%2B06:00&to=2026-09-09T00:00:00%2B06:00&site=kokcho-koz&operation=weighing&page=1&per_page=200`

→ `{"weighings": [{…}], "page": 1, "per_page": 200, "total": 57}`. Отбор по `weighed_at`, сортировка по возрастанию; `site` (код объекта в весовой системе), `operation`, `source` необязательны; `per_page` ≤ 200. Параметр `site` добавляется для этой интеграции (в API для АИС «СВХ» объект задаётся её идентификатором).

### 8.3 Справочник объектов и весов

`GET /api/v2/sites` → список всех объектов весовой системы с весами (новое в редакции 0.2, по просьбе Таргет-центра):

```json
{
  "sites": [
    {
      "code": "kant",
      "name": "СВХ «Кант»",
      "customs_code": "41714106",
      "ais_object": "0002",
      "scales": [
        {
          "id": 8,
          "no": 1,
          "kind": "static",
          "name": "Весы №1 (въезд)",
          "verification": { "number": "3961", "date": "2026-02-26", "valid_until": "2027-02-26" }
        }
      ]
    }
  ]
}
```

Поля те же, что у блоков `site` и `scale` документа операции. `ais_object` задан у весов и у всех весов одного объекта совпадает; `null` — объект без АИС «СВХ».

## 9. Правила тары, нетто и журнала

- Тара привязана к сцепке — паре «голова + прицеп». Тарирование без прицепа действует только для машины без прицепа; смена прицепа означает, что действующей тары нет и нужно новое тарирование.
- Действует последнее тарирование сцепки не старше 3 календарных месяцев на момент взвешивания. Реестр тарирований единый по всем объектам: тарироваться и взвешиваться можно на разных весах.
- Единственный источник тары — тарирования, проведённые через весовую систему. Справочников тары и ручного ввода массы нет.
- Тарирование тяжелее лимита тары весов (по умолчанию 25 000 кг) весовая система не проводит: на платформе гружёная машина, а не порожняя сцепка.
- Записи журнала неизменяемы: не редактируются и не удаляются; исправление — только сторнированием новой записью (событие `weighing.reversed`). Фото и запись связаны контрольными суммами.
- Отказы в журнал не записываются: он состоит только из состоявшихся операций. Отклонённые тарирования (масса выше лимита тары) по командам АИС «СВХ» передаются таможенной системе отдельным событием `weighing.rejected` (5.5). Отказы ручных тарирований на весовом ПК и снимки при отказе — предмет второй редакции: для них нужно обновление агентов.

## 10. Динамические весы (вторая редакция)

Динамические (поосные) весы на пунктах пропуска подключаются позже (обследование «Торугарт»: двое Тензо-М ВА-Д-20; Кен-Сай: Уралвес ВАТ-Д-20 — этап 3 плана весовой системы). Для них появится отдельный тип события с тем же конвертом (раздел 4) и `scale_kind: "dynamic"`; сообщения статических весов не изменятся. Предварительный состав, будет уточнён после обследования оборудования и вопросов таможенной стороны:

- тип `axle_weighing.completed` (название предварительное) и, для аннулирования, `axle_weighing.reversed`;
- документ: `id`, `site`, `scale` (`kind: "dynamic"`, `verification`), `passed_at` (момент проезда), `direction` / `lane`, `speed`, `mode` (динамический проезд или статическая остановка на платформе), `vehicle_number` (распознанный номер или введённый оператором) и `trailer_number`, `axles` — список осей `{no, load, spacing}` (нагрузка и расстояние до следующей оси), `axle_groups` — группы осей с суммарной нагрузкой, `total_mass`, `photos` (число снимков и ракурсы — по оборудованию), `operator` (`null` при автоматическом проезде), `checksum`;
- тары и нетто у поосного взвешивания нет: `tare` и `netto` не передаются.

Пожелания Таргет-центра к составу, приняты как исходный перечень второй редакции: нагрузка по каждой оси и общая масса, число осей и осевые группы, скорость проезда, направление (въезд / выезд), госномер головы и прицепа с фото, код таможенного органа пункта пропуска, признак превышения допустимой нагрузки. Две оговорки: распознанный номер появится, только если в составе оборудования пункта будет распознавание (решение не принято; иначе номер вводит оператор); признак превышения зависит от того, кто считает нормативы — оборудование, весовая система или таможенная система, — это согласуем при подготовке второй редакции.

Уточнено Таргет-центром при согласовании версии 1.0: нормативы допустимых нагрузок считает таможенная система, от весовой системы нужны только измерения; признак превышения в сообщении не нужен — если оборудование его выдаёт, он передаётся справочно отдельным полем. В документе проезда нужны признак источника номера (распознан / введён оператором), снимок номера, полоса (`lane`) и момент проезда с точностью до секунды: на «Торугарте» таможенная система связывает проезд с номером по времени и полосе через свои камеры.

До второй редакции потребитель игнорирует незнакомые типы событий (раздел 2).

## 14. Приложение Б. Алгоритм `checksum` и контрольный пример

`checksum` — SHA-256 от строки, собранной из полей записи через вертикальную черту `|` (U+007C), в кодировке UTF-8, без завершающего перевода строки; результат — 64 шестнадцатеричных символа в нижнем регистре. Сумму считает центр при записи операции в журнал и хранит вместе с записью. Формула фиксирована и меняться не будет.

Поля — строго в этом порядке:

| № | Что | Откуда в документе | Сериализация |
|---|---|---|---|
| 1 | Идентификатор операции | `id` | UUID в каноническом виде: 36 символов, нижний регистр, с дефисами |
| 2 | Вид операции | `operation` | `weighing` или `taring` |
| 3 | Код результата | — | Константа `OK` (в журнале только состоявшиеся операции) |
| 4 | Масса | `massa` | Десятичное число с точкой и ровно тремя знаками после неё: `43310.000` |
| 5 | Момент фиксации веса | `weighed_at_utc` | Строка поля как есть: UTC, `ГГГГ-ММ-ДДTЧЧ:ММ:СС[.мкс]+00:00`; дробная часть — 6 цифр, отсутствует только при нуле микросекунд |
| 6 | Номер головы | `vehicle_number` | Строка после нормализации как есть |
| 7 | Источник | `source` | `ais` или `local_offline` |
| 8… | Хеши снимков | `photos.*.sha256` | Все имеющиеся хеши, отсортированные по возрастанию как строки (не по ролям), каждый отдельным элементом; снимков нет — элементов нет |

В сумму **не входят**: номер прицепа, оператор, тара и нетто, `ais_ref`, `recorded_at`, реквизиты объекта и весов. Неизменность этих полей обеспечивается самим журналом (записи не редактируются); `checksum` связывает идентификатор, массу, момент, номер головы и снимки.

Контрольный пример (документ 5.1; хеши снимков — условные, взяты от строк `front` и `rear`):

```
id              0d9b4d3e-8c0f-4b41-9f4c-2a6f1e3b7c55
operation       weighing
massa           43310.0
weighed_at_utc  2026-08-14T09:30:12.345678+00:00
vehicle_number  01KG777AAA
source          ais
photos.front    2d8d693177ac44895fc02c009ec3f6af32e51eb00783c17000d7051d1662b93a
photos.rear     32b36ae43a5ea4895ec88864321da8b5f4b8d6efb60c6c10183bb6def8cbf1ad
```

Строка (одна, без переносов):

```
0d9b4d3e-8c0f-4b41-9f4c-2a6f1e3b7c55|weighing|OK|43310.000|2026-08-14T09:30:12.345678+00:00|01KG777AAA|ais|2d8d693177ac44895fc02c009ec3f6af32e51eb00783c17000d7051d1662b93a|32b36ae43a5ea4895ec88864321da8b5f4b8d6efb60c6c10183bb6def8cbf1ad
```

`checksum` = `74d9970b847cdb18990e7a397979767734b55f6916bccca7ee648f184bc45099`

Проверка на Python:

```python
import hashlib


def checksum(doc: dict) -> str:
    photos = sorted(p["sha256"] for p in doc["photos"].values() if p)
    parts = [
        doc["id"],
        doc["operation"],
        "OK",
        f"{doc['massa']:.3f}",
        doc["weighed_at_utc"],
        doc["vehicle_number"],
        doc["source"],
        *photos,
    ]
    return hashlib.sha256("|".join(parts).encode("utf-8")).hexdigest()
```

Проверка снимка: SHA-256 скачанного файла должен совпасть с `photos.<роль>.sha256`, а тот входит в `checksum` записи.
