## 1. Цель и контекст

Сейчас на объектах ОАО стоят весовые ПК с ПО UniServer AUTO (ВесыСофт), к которым подключены весовые индикаторы. АИС «СВХ» проводит взвешивание через скрипт-маршрутизатор, который перенаправляет запрос в нужный UniServer. Задача — заменить эту связку собственной системой:

* **Центральный весовой сервер** — принимает команды от АИС «СВХ», хранит взвешивания и фото со всех объектов, даёт сводную картину.
* **Агент** на каждом весовом ПК — по команде центра проводит взвешивание (вес с индикатора + фото с двух камер) и возвращает результат; при отсутствии связи позволяет оператору взвешивать локально с последующей досылкой.

Проверено на практике (объекты с индикаторами CAS): чтение веса напрямую с индикатора работает — протокол «CAS 22 byte», непрерывная передача, команды весам не нужны (тест cas22_reader.py, 06.08.2026, зафиксировано взвешивание 1460 кг).

## 2. Обзор архитектуры

```
                ┌─────────────────────────┐
                │        АИС «СВХ»        │
                └────────────┬────────────┘
                             │ HTTP JSON: команды АИС (v2, согласован 17.08.2026; v1 — совместимый)
                             │ RabbitMQ: офлайн-операции центр → АИС
                             ▼
                ┌─────────────────────────┐
                │  ЦЕНТРАЛЬНЫЙ СЕРВЕР     │
                │  • API для АИС          │
                │  • маршрутизация        │
                │  • PostgreSQL + фото    │
                │  • веб-панель, отчёты   │
                └────────────┬────────────┘
                             │ WebSocket (исходящее ОТ агента, TLS, токен)
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
  ┌───────────┐        ┌───────────┐        ┌───────────┐
  │ АГЕНТ     │        │ АГЕНТ     │        │ АГЕНТ ...  │
  │ Кызыл-Кыя │        │ КАНТ      │        │ (13 объектов)
  └─────┬─────┘        └───────────┘        └───────────┘
        │ COM/RS-232 (драйвер протокола)     ┌──────────────┐
        ├──────────────► Весовой индикатор   │ Локальный    │
        │ RTSP/HTTP                          │ веб-интерфейс│
        └──────────────► Камеры (перед/зад)  │ оператора    │
                                             └──────────────┘
```

Принципы:

1. **Агент сам открывает соединение к центру** (исходящий WebSocket) и держит его. Центр не стучится на объекты — это устойчиво к особенностям сетей удалённых объектов и упрощает межсетевые экраны.
2. **Офлайн-автономность**: агент полностью работоспособен без центра — буферизует результаты в локальной SQLite и досылает при восстановлении связи. Взвешивания не теряются никогда.
3. **Драйверы индикаторов — сменные модули** с единым интерфейсом. Добавление нового протокола не трогает остальной код.
4. **Совместимость с АИС**: центр принимает запросы в текущем формате (v1) и отвечает в текущем формате — переход для АИС мог бы быть сменой одного адреса. Итог 17.08.2026: АИС переходит сразу на нативный v2 (контракт согласован, 4.1); v1 остаётся замороженной страховкой и форматом имитатора.

## 3. Агент (`ves-agent`)

Windows-служба на весовом ПК. Python 3.12.

### 3.1. Функции

* Постоянное чтение весового индикатора через драйвер протокола (COM-порт / TCP).
* Автопереподключение порта при сбоях (обязательно: переходники CH340 подвисают — подтверждено на практике, ошибка 31; лечится переоткрытием порта, при необходимости — программным перезапуском устройства).
* Проведение цикла взвешивания по команде центра или оператора (см. 3.3).
* Снимки с двух IP-камер (front/rear) в момент фиксации веса. Камера с HTTP-снапшотом (Hikvision) отдаёт готовый JPEG мгновенно; камере без него (только RTSP — Джалал-Абад) агент держит постоянный видеопоток с буфером последнего кадра (agent/cameras/stream.py, реализовано в 0.4.7): снимок берётся из буфера мгновенно, при обрыве потока — разовое подключение (см. decisions 12.08.2026).
* Локальный веб-интерфейс оператора (см. 3.4).
* Очередь недоставленных результатов (SQLite), досылка в центр.
* Самодиагностика: статус порта, поток данных, доступность камер, связь с центром — отдаётся в центр (heartbeat) и виден в локальном интерфейсе.

### 3.2. Драйверы индикаторов

Интерфейс драйвера (Python):

```python
class ScaleDriver(Protocol):
    def start(self) -> None            # открыть порт, начать чтение
    def stop(self) -> None
    @property
    def state(self) -> ScaleState      # masa, stable, ok, error, last_packet_at
    def zero(self) -> bool             # опционально (если протокол поддерживает)
```

Драйверы этапа 1:

* **cas22** — CAS CI-серия (CI-201A и др.), протокол «CAS 22 byte»: непрерывный поток, пакет 22 байта: `[0-1]` ST/US/OL, `[3-4]` GS/NT, `[9-16]` масса ASCII, `[17-19]` единица, `[20-21]` CRLF; без CRC. **Реализован и проверен** (cas22_reader.py). Параметры порта: 9600, 8-N-1, DTR/RTS не поднимать.
* Прочие статические (Пегас, Соболь, другие CAS/Keli-варианты) — по выгрузкам настроек UniServer с объектов (структура .cfg уже разобрана, из неё берутся: длина пакета, байты синхронизации, адреса массы/флага, дискретность, множитель).

Этап 2: **xk3190-dm** (динамические поосные, Торугарт/Кен-Сай) — отдельный формат (результаты по осям), отдельная логика суммирования.

### 3.3. Цикл взвешивания (конечный автомат)

```
IDLE → (команда) → WAIT_ZERO: вес < порога пустых весов, стабилен
     → WAIT_VEHICLE: ждём вес > порога заезда (таймаут → ошибка VEHICLE_TIMEOUT)
     → WAIT_STABLE: флаг ST + вес неизменен N секунд (параметры объекта)
     → CAPTURE: фиксация массы + снимки 2 камер (в одну транзакцию)
     → DONE: результат в локальную БД → отправка в центр → ответ
```

Параметры на объект (конфиг агента): порог заезда, время стабильности, дискретность, таймауты, адреса камер (RTSP/HTTP snapshot URL), порт индикатора, тип драйвера.

Принятая схема развёртывания: **одни весы = один весовой индикатор = один ПК = один агент**. На КАНТе двое весов — значит два ПК с двумя агентами; для центра это просто два объекта-весов одного СВХ.

### 3.3а. Типы операций и расчёт нетто

Каждая операция имеет тип:

* **Взвешивание (брутто)** — гружёное АТС;
* **Тарирование (тара)** — пустое АТС.

Правило расчёта (ред. 09.08.2026): при взвешивании брутто система находит **последнее тарирование этой СЦЕПКИ — пары голова+прицеп — не старше 3 месяцев** и вычисляет `нетто = брутто − тара`. Смена прицепа означает отсутствие действующей тары (нужно новое тарирование); тарирование без прицепа действует только для машины без прицепа. Если действующей тары нет — это явно отражается в результате (нетто не считается / признак «нет тары»).

Тип операции указывает инициатор: в онлайне — АИС «СВХ» в команде взвешивания (сейчас это определяется вкладкой, из которой оператор АИС жмёт «Взвесить»; в новом контракте тип передаётся полем явно), в офлайне — оператор в локальном интерфейсе агента (выбор «Взвешивание / Тарирование» + ввод номера ТС).

**Реестр тарирований** ведёт центральный сервер (единый по всем объектам: АТС могло тарироваться на одних весах, а взвешиваться на других). Реестр компактный, поэтому он **целиком реплицируется на всех агентов** при каждой синхронизации — благодаря этому агент в офлайне сам подставляет действующую тару и считает нетто без связи с центром. После восстановления связи офлайн-операции (включая новые тарирования) уходят в центр, реестр обновляется и расходится по объектам.

Весовая система — **первичный источник данных о взвешиваниях**: полный журнал (вес, тип, тара/брутто/нетто, фото, оператор, источник) хранится в центре независимо от АИС «СВХ»; АИС получает данные, но не является единственным их хранилищем.

### 3.4. Локальный веб-интерфейс оператора

Отдаётся самим агентом (FastAPI + HTMX), доступен на весовом ПК (localhost) и из сети объекта.

Главный экран оператора (аналог текущего UniServer): текущий вес крупно + флаг стабильности, **живые трансляции с двух камер**, журнал взвешиваний объекта с фото. Трансляция (уточнение по факту 0.4.7): браузер обновляет кадр раз в 2 секунды; снапшот-камеры отдают его мгновенно по HTTP, RTSP-камеры — из буфера постоянного потока, который агент держит фоновым ffmpeg (полноценный MJPEG/HLS-прокси не понадобился); распознавание номеров не делаем.

Режимы:

* **Онлайн (связь с центром есть)** — только просмотр: текущий вес, камеры, состояние оборудования, журнал. Кнопка взвешивания **заблокирована** с подписью «Взвешивание проводится через АИС „СВХ“» — по регламенту при наличии сети взвешивание ТОЛЬКО через АИС.
* **Офлайн (центр недоступен > T секунд)** — разблокируется ручной режим: оператор выбирает тип операции (**Взвешивание / Тарирование**), вводит номер ТС (и при необходимости прицеп/марку из справочника), агент проводит цикл, сам подставляет действующую тару из локальной реплики реестра (см. 3.3а) и считает нетто. Запись сохраняется с признаком `source = "local_offline"` и именем оператора. При восстановлении связи записи автоматически уходят в центр и далее в АИС.

Вход в локальный интерфейс — по учётке оператора (локальный список пользователей синхронизируется с центром).

## 4. Центральный сервер (`ves-center`)

Linux или Windows Server в сети организации. Python 3.12 + FastAPI + PostgreSQL 16. Фото — на файловой системе сервера, раздача как статики (структура путей — как в текущей системе: `/vesy/ГГГГ/ММ/ДД/<uuid>_photo1.jpeg`).

### 4.1. API для АИС «СВХ» (совместимый контракт)

Запрос (как сейчас, без изменений в АИС):

```json
{
  "ip_address": "192.168.158.20",
  "port": 8087,
  "username": "admin",
  "password": "admin",
  "autoscale": 1
}
```

Центр трактует `ip_address` + `autoscale` как ключ маршрутизации: таблица соответствия «старый адрес UniServer → объект/весы» ведётся в справочнике. `autoscale` — номер весов на объекте (для объектов с одними весами АИС шлёт 1 — подтверждено 12.08.2026); менять ключ в справочнике только синхронно со стороной АИС. Ответ (байт-в-байт текущая структура):

```json
{
  "code": "OK",
  "massa": 43310.0,
  "weighing_datetime": "2025-04-16T15:59:26",
  "unit_meas": "kg",
  "front_image": "/vesy/2025/04/16/913cb979ae034d0eb4748278d9f4cfcf_photo1.jpeg",
  "rear_image": "/vesy/2025/04/16/913cb979ae034d0eb4748278d9f4cfcf_photo2.jpeg"
}
```

Решено немного поменять интеграцию (согласовано): контракт расширяется полем **типа операции** и структурированными ошибками. Запрос дополняется полем `operation`: `"weighing"` (взвешивание брутто) или `"taring"` (тарирование); ответ при взвешивании дополняется полями `tare`, `netto`, `tare_datetime` (или признаком `no_valid_tare`). Точный состав финализировать вместе с разработчиками АИС.

Коды ошибок (`code`), предлагаемый перечень:

| code | Значение |
|---|---|
| `OK` | успешно |
| `ERR_AGENT_OFFLINE` | нет связи центра с агентом объекта |
| `ERR_SCALE_OFFLINE` | агент на связи, но нет данных от индикатора (порт/кабель) |
| `ERR_NOT_ZERO` | весы не пусты перед началом операции |
| `ERR_VEHICLE_TIMEOUT` | АТС не заехало за отведённое время |
| `ERR_UNSTABLE` | вес не стабилизировался за таймаут |
| `ERR_CAMERA` | камера недоступна — операция НЕ проведена, вес не возвращается (решение 09.08.2026) |
| `ERR_BUSY` | на этих весах уже выполняется операция |
| `ERR_INTERNAL` | прочее (детали в поле `message`) |

**Нативный API v2 — согласован с разработчиками АИС 17.08.2026** (эталон — `docs/contracts/ais-api-v2.md`, версия 1.0; АИС переходит сразу на него, v1 остаётся замороженным). Суть:

* `POST /api/v2/weighings` — синхронная команда: `ais_ref` (номер документа АИС `WEI…`/`TAR…` — одна строка, он же их идентификатор), `ais_object` («Специальный идентификатор СВХ» из справочника АИС, строка из 4 цифр с ведущими нулями: 0014 Кызыл-Кыя, 0013 Джалал-Абад ПЗТК, 0002 Кант) + `scale_no` (№ весов на объекте, «Авто весы 1/2»), `operation`, `vehicle_number` и `operator` обязательные, `trailer_number`. Привязка «идентификатор СВХ + № весов → весы» — в справочнике центра.
* Авторизация — сервисный Bearer-токен интегратора (тот же, что для фото) + IP-allowlist серверов АИС (192.168.140.150 боевой, 192.168.6.116 тестовый); JWT не используется.
* Ответ — HTTP 200 `{code, weighing}` / `{code, message}` (коды из таблицы выше); 401/403/404/422 только для неверного запроса. **Документ операции** один на все каналы: id (uuid), номер карточки, объект/весы со свидетельством о поверке, массы, **тарирование во вложении** со статусом `applied | expired | not_applied` (устаревшая тара показывается с датой, массой и номером АИС, нетто null), фото с sha256 и `available`, checksum.
* **Идемпотентность по `ais_ref`** (один документ АИС = одна операция): повтор по состоявшейся → тот же документ с `repeated: true`; повтор во время выполнения → дождаться и отдать тот же исход; после отказа → новая попытка. Так АИС повторяет запрос при потере ответа, не плодя взвешиваний.
* Сверка — `GET /api/v2/weighings/{id}`, `?ais_ref=…`, список за период.

### 4.1а. Офлайн-операции: события RabbitMQ и обратная связь (согласовано 17.08.2026)

Синхронная команда «взвесить» — HTTP (соответствует рабочему процессу оператора АИС; онлайн-операции событиями НЕ публикуются — их исход АИС берёт из HTTP-ответа). RabbitMQ нужен для операций, выполненных на объекте офлайн (ручной режим при потере связи) — единственный путь доставить их в АИС:

* **Брокер — свой, на ВМ центра** (контейнер в docker-compose, vhost `vesy`, учётки `vesy-center` пишет / `ais-svh` читает; решение 17.08.2026 вместо «существующего брокера организации» из v1.1 — доступа к нему так и не появилось, а контракт сообщений от места брокера не зависит). Системщик открывает 5672 с серверов АИС до ВМ.
* Событие `weighing.completed` — документ операции (тот же, что в ответе v2) в конверте `{event_id, type, version, published_at, ais_object}`; exchange `vesy.events` (topic), routing key `weighing.completed.<ais_object>`, одна durable-очередь `ais-svh.weighings` на все объекты. Публикация из outbox центра с подтверждением брокера и повторами; at-least-once, АИС дедуплицирует по `weighing.id`.
* **Обратная связь**: у офлайн-операции нет номера АИС — АИС заводит документ по событию (по объекту, номеру машины и времени; не сошлось — создаёт без привязки к регистрации, руками не сопоставляет) и сообщает номер `POST /api/v2/weighings/{id}/ais_ref`; номер хранится рядом с записью (правило №2), после этого виден в GET, панели и во вложении `tare.ais_ref`.
* Не вошло в первую версию (возможные расширения по запросу АИС): `agent.status`, `weighing.reversed`, проверка тары до взвешивания `GET /api/v2/tares`, публикация событий и по онлайн-операциям.

### 4.2. Протокол центр ↔ агент

WebSocket поверх TLS, соединение открывает агент, аутентификация по токену агента. Сообщения JSON:

* `hello` / `heartbeat` (агент → центр): статус оборудования, версия, текущий вес.
* `weigh_request` (центр → агент): `{request_id, scale_id, params}`.
* `weigh_result` (агент → центр): `{request_id, massa, stable, datetime, photos[], source}` — фото передаются следом бинарными кадрами либо HTTP-загрузкой на центр.
* `offline_sync` (агент → центр): пакетная досылка накопленных офлайн-записей.

### 4.3. Веб-панель центра

* Сводка по 13 объектам: связь с агентом, состояние индикатора и камер, последнее взвешивание.
* Единый журнал взвешиваний: фильтры (объект, дата, номер ТС, источник — АИС/офлайн), фото, выгрузка CSV (открывается в Excel; реализовано 11.08.2026).
* Справочники: объекты, весы, камеры, пользователи, соответствие «старые адреса UniServer».
* Отчёты (этап 4, реализовано 18.08.2026, `center/reports.py` + экран `/panel/reports`): период (пресеты или даты по Бишкеку) + объект → итоги (взвешивания, тарирования, офлайн-операции, нетто, отказы АИС, офлайн без номера АИС), массы (нетто по взвешиваниям с тарой = Σбрутто − Σтары; без тары — число и брутто отдельно; причины «без нетто» и сцепки к перетарированию), таблица и графики по объектам, динамика по дням/неделям/месяцам (суммарно или по объектам), ручные операции по операторам, надёжность (доступность по событиям мониторинга, инциденты, отказы АИС по кодам), сравнение с прошлым периодом; печатная версия, выгрузки CSV и .xlsx. Всё — чтение журнала и служебных таблиц, без витрин; графики — серверный SVG. См. decisions 18.08.2026.
* Роли: администратор (видит систему целиком и правит справочники), диспетчер (просмотр; при заданной привязке к объекту видит только его, без привязки — все объекты), оператор объекта (учётка агента, реплицируется на весовой ПК). Реализовано 11.08.2026, см. decisions.

### 4.4. Неизменяемость журнала

Зафиксированное взвешивание не редактируется и не удаляется (только сторнирование отдельной записью со ссылкой на исходную). Фото и запись связаны контрольной суммой. Это важно для споров по весу и для контрольных органов.

## 7. Безопасность

* TLS на всех соединениях (внутренний CA организации или Let's Encrypt при наличии DNS).
* Токены агентов (по одному на объект, отзываемые). JWT для пользователей.
* Совместимый API v1 принимает старые `username/password`, но проверяет их по своей базе; после перехода АИС на v2 — v1 отключается. Уйти от admin/admin.
* Интеграторы (АИС «СВХ»): сервисный Bearer-токен + IP-allowlist — и для команд v2, и для фото; JWT для интеграторов не используется (решение 17.08.2026: один интегратор во внутренней сети). Учётка RabbitMQ у АИС — только чтение своей очереди.
* Доступ к локальному интерфейсу агента — только из сети объекта.
* Журналирование всех команд взвешивания (кто, откуда, когда).

### Доступ к фото (интеграции)

Фото хранятся только в весовой системе и наружу отдаются через nginx/центр. Подтверждено: АИС «СВХ» забирает фото **сервером** и проксирует своим пользователям (server-to-server). Схема доступа:

* URL фото — стабильные и постоянные (`/vesy/ГГГГ/ММ/ДД/<uuid>_photoN.jpeg`), не протухают: интегратор может повторно скачать старое фото в любой момент в пределах срока хранения.
* Каждому интегратору — свой **сервисный токен** (АИС «СВХ» — один, системе таможни в будущем — другой), передаётся в заголовке `Authorization`, не в URL. Проверка токена + допуск по IP сервера интегратора. Без токена фото не отдаются, даже по точной ссылке.
* Токены выпускаются и отзываются в центре независимо друг от друга; права можно ограничить (например, таможне — только чтение фото и журнала). Все скачивания логируются (кто, что, когда).
* Сервис фото недоступен из интернета — только сеть организации и защищённые каналы ведомств.
* Срок хранения фото (retention): **5 лет** (решение от 07.08.2026); запись журнала и фото связаны контрольной суммой.

### Хранение фото

* Фото хранятся **файлами на диске** центра (структура `/vesy/ГГГГ/ММ/ДД/<uuid>_photoN.jpeg`), в БД — путь, размер, sha256. На агенте — так же файлами до досылки.
* Формат — **JPEG, качество ~85, родное разрешение камеры** (2560×1440). Качество выбирается один раз в момент снимка; далее файл **неизменен навсегда** — никаких пересжатий (потеря качества + нарушение контрольной суммы, фото — доказательство в спорах).
* При сохранении один раз генерируется **миниатюра** (~30–50 КБ) для списков журнала.
* Оценка объёма: ~300 взвешиваний/день × 2 фото × 0,6 МБ ≈ 130 ГБ/год → **на 5 лет достаточно диска ~1 ТБ** с запасом. Архивирование/пересжатие не применяется; по истечении 5 лет — удаление по регламенту.

## 7а. Обновление агентов и мониторинг парка

### Автообновление агентов

Вручную подключаться к 13 весовым ПК при каждом изменении (например, правке драйвера индикатора) нельзя — обновление делается через центр (реализовано 18.08.2026: `center/rollout.py`, экран «Релизы», агент 0.4.19 — см. decisions):

1. Новая версия агента (архив сборки, sha256 считает центр) загружается в центр (`agent_releases`, экран «Релизы» или каталог на ВМ), назначается канал: `pilot` (один объект) → `stable` (все).
2. Центр сам шлёт агентам канала на связи команду обновления (не больше 3 одновременно, повторы отказов ограничены); агент скачивает пакет с центра, проверяет контрольную сумму и оглавление.
3. Ставит новую версию рядом с текущей, перезапускает службу; **самопроверка** после старта (порт открылся, поток с индикатора идёт, связь с центром есть). Если самопроверка не прошла — **автоматический откат** на предыдущую версию и алерт в центр.
4. Раскатка поэтапная: сначала канал `pilot`, после N дней без проблем — перевод релиза в `stable` (кнопкой; экран показывает дни в pilot и сбои).

Конфигурация агента (порты, камеры, пороги) тоже управляется из центра: правится в веб-панели, агент подхватывает по heartbeat. Локально на весовом ПК руками ничего править не нужно.

### Мониторинг

Отдельный раздел веб-панели центра — **«Состояние объектов»**, по каждым весам:

* связь с агентом (онлайн/офлайн, длительность), версия агента, канал;
* индикатор: порт открыт, поток данных идёт, время последнего пакета, текущий вес;
* камеры: доступность каждой (перед/зад), время последнего успешного снимка;
* очередь недосланных офлайн-записей;
* история недоступности (когда и сколько объект был без связи).

Алерты при событиях (объект офлайн > N минут, пропал поток с индикатора, камера недоступна, неудачное обновление) — на email и/или в Telegram/чат дежурного. Технически это уже заложенный heartbeat (3.1) — здесь он становится витриной и системой оповещения.

Параллельная работа с UniServer (агент на другом порту/ретрансляция), сверка результатов N дней. Критерий: 100% совпадение веса с UniServer/табло, фото на каждом взвешивании.

**Этап 2 — тарирование, офлайн-режим и тираж на статические объекты.** Реестр тарирований с репликацией на агентов и расчёт нетто; ручное взвешивание/тарирование при потере связи; досылка офлайн-записей в АИС через RabbitMQ (контракт v2 согласован с разработчиками АИС 17.08.2026 — `docs/contracts/ais-api-v2.md`); автообновление агентов (7а); установка на остальные SCS/Пегас/Соболь по мере снятия протоколов; вывод UniServer из эксплуатации пообъектно.

**Этап 3 — динамические весы (Торугарт, Кен-Сай).** Драйвер XK3190-DM, поосная логика, свой цикл и экранные формы.

**Этап 4 — сводная аналитика.** Отчёты по ОАО, дашборд, при необходимости — интеграции помимо АИС. Начат 18.08.2026 раньше остатка этапа 2 (тот упирается во внешние зависимости): экран «Отчёты» (4.3) сделан целиком — итоги, массы, по объектам, динамика, ручные операции, надёжность, сравнение с прошлым периодом, печать, CSV/.xlsx.

## Приложение А. Чек-лист обследования объекта

1. Фото шильдика и табло весового индикатора.
2. Если стоит UniServer: Настройки → Весовой индикатор → название протокола; кнопка «Экспорт...» → файл .cfg (прислать).
3. Параметры порта: номер COM, скорость; чем подключено (прямой RS-232 / USB-переходник — какой чип / TCP-конвертер).
4. Камеры: модель, IP, есть ли HTTP-snapshot / RTSP, логины.
5. Схема: где стоит весовой ПК, расстояние до весов, до камер.
6. Версия Windows на весовом ПК, есть ли свободный USB/COM.
7. Контакт местного оператора/администратора.
