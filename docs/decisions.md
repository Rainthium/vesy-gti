# Журнал архитектурных решений (ADR)

Формат записи: дата · решение · причина. Новые решения дописывать сверху.

---

**10.08.2026 · HTTP-snapshot камер: Basic превентивно + Digest по challenge (agent-v0.1.1).** Проверка боевого конфига на камерах Кызыл-Кыи показала: Hikvision ISAPI по заводской настройке отвергает Basic (401) и принимает только Digest — с прежним кодом (только превентивный Basic) обе камеры были бы «недоступны» и каждая операция падала бы ERR_CAMERA. Теперь первый запрос уходит с Basic (камеры без challenge, без лишнего круга), на 401 с Digest-challenge повтор делает stdlib HTTPDigestAuthHandler (его заголовок вытесняет Basic через unredirected_hdrs). Снимки с обеих камер объекта получены кодом агента (проверено 10.08.2026 из сети предприятия).

**10.08.2026 · Упаковка агента: PyInstaller onedir, сборка на GitHub Actions windows-runner, служба через nssm.** Onedir (папка app/ с exe и _internal/), а не onefile: служба стартует без распаковки во %TEMP% (под системной учёткой nssm это источник проблем), обновление — атомарной заменой папки (update.bat, старая версия остаётся в app_old для отката). Основной путь получения exe — workflow «Сборка агента»: тег `agent-v*` → windows-runner собирает и прикрепляет к релизу архив ves-agent-<версия>-win64.zip (app/ + config.example.toml + install-service.bat/update.bat + УСТАНОВКА.md); запасной — packaging/agent/build.bat на любой Windows с uv. Ресурсы (шаблоны, статика, шрифт оверлея) кладутся в datas по тем же относительным путям, по которым модули ищут их через Path(__file__).parent. Служба: автозапуск, рестарт при падении, логи в logs/agent.log с ротацией, PYTHONIOENCODING=utf-8. Инструкция установки — docs/install-agent-windows.md (в архиве — УСТАНОВКА.md); там же зафиксировано поведение при занятом UniServer'ом COM-порте: агент показывает «нет данных» и сам оживает после освобождения порта. Два урока сборки: (1) замороженный Python работает в изолированном режиме и игнорирует PYTHONUTF8/PYTHONIOENCODING — UTF-8 для stdout/stderr включает runtime-хук rthook_utf8.py (errors=replace: кодировка вывода никогда не валит службу); (2) логи Actions анонимно недоступны (gh не авторизован), поэтому шаги сборки при сбое публикуют хвост лога error-аннотациями — их видно через публичный API check-runs/<job_id>/annotations.

**10.08.2026 · Подтверждена модель интеграции: наш центр заменяет сервис-прокладку АИС (со слов Игоря).** Сегодня АИС «СВХ» общается с весами не напрямую, а через промежуточный сервис: он принимает команды взвешивания и перенаправляет их на нужные весы (UniServer конкретного объекта). Наша система заменяет именно эту прокладку: центр принимает запросы v1 и маршрутизирует по legacy-адресу (ip+port+autoscale из запроса) на своих агентов. Переключение АИС = смена адреса прокладки на адрес центра — как и закладывалось. Следствие: поле ip_address в запросе АИС — адрес весов (UniServer объекта), которым прокладка пользовалась для маршрутизации; для Кызыл-Кыи ожидаем 192.168.158.20:8087 (сверить с разработчиками АИС до пилота — вопрос в PROGRESS).

**10.08.2026 · Веб-интерфейс оператора агента на пилоте открыт в сеть предприятия (host 0.0.0.0, решение Игоря).** Доступ по IP весового ПК на порту 8090, как привычно с UniServer (8087). Вход по учёткам операторов; TLS внутри сети предприятия на пилоте не требуется.

**09.08.2026 · Тара привязана к СЦЕПКЕ: пара голова+прицеп (решение Игоря).** Прежде тара искалась только по номеру головы (как «тара из базы» UniServer) — смена прицепа подставляла тару старой сцепки и искажала нетто. Теперь ключ реестра тар — (vehicle_number, trailer_number): тара подставляется только при совпадении ОБОИХ номеров; тарирование без прицепа действует только для машины без прицепа; несовпадение = no_valid_tare, нужно новое тарирование. Затронуты: tare_registry центра (миграция, составной PK, '' = без прицепа), реплика агента (пересоздаётся автоматически при старте старой схемы — данные расходные, центр пришлёт снимок), оба режима агента, фолбэк-расчёт v1, подсказка тары в форме оператора, реестр в панели. Правило №4 в CLAUDE.md/architecture обновлено.

**09.08.2026 · Камеры обязательны: без снимков ОБЕИХ камер операция не проводится (решение Игоря).** Прежняя семантика ERR_CAMERA («вес возвращается с предупреждением», architecture §4.1) отменена: фото — доказательство взвешивания, операция без него не имеет силы. Агент при сбое любой камеры отвечает ERR_CAMERA без веса и НЕ создаёт запись (авто- и ручной режимы); v1 отдаёт только {code, message}. Индикатор без данных и раньше блокировал операцию (ERR_SCALE_OFFLINE). Центр присланные записи сохраняет как есть (агент — единственный их источник и ERR_CAMERA с весом больше не шлёт).

**09.08.2026 · Конфиг агента — TOML (stdlib tomllib), оркестратор agent/main.py.** TOML читается стандартной библиотекой — нулевые зависимости под PyInstaller. Валидация pydantic с extra=forbid: опечатка в конфиге — ошибка при старте, а не молча проигнорированный ключ. Боевой конфиг (токен агента, пароли камер в URL) живёт только на весовом ПК (правило №7), в репозитории — config.example.toml с плейсхолдерами. Правило №3 воплощено в оркестраторе: manual_allowed = отсутствие связи с центром (CenterClient.connected). Веб оператора — 127.0.0.1:8090 (8087 занят UniServer на время параллельной работы). Локальные операторы заводятся CLI: python -m agent.main --config ... add-operator. Снимки-сироты убираются при старте, до запуска служб.

**08.08.2026 · Оверлей на фото: шрифт в комплекте агента, прожиг в store_shots, безопасная деградация.** Плашка (камера · дата/время Бишкека · вес) прожигается однократно в момент фиксации, до расчёта sha256 — далее файл неизменен (правило №2). Шрифт — сабсет DejaVu Sans Bold (латиница+кириллица, 32 КБ, свободная лицензия в fonts/DEJAVU-LICENSE.txt) лежит в agent/cameras/fonts/: наличию системных шрифтов на весовом ПК не доверяем, PyInstaller упакует свой. Ошибка прожига (битый кадр) не теряет снимок — сохраняются исходные байты, проблема в лог.

**08.08.2026 · Автоматический режим агента: запись с весом сохраняется локально ДО отправки weigh_result; ошибки без веса не сохраняются.** Оркестратор agent/weighing/auto.py: доставка двухканальная и самовосстанавливающаяся — живой weigh_result отвечает АИС сразу, локальная запись (synced=0) гарантирует доставку досылкой offline_sync при обрыве (приём центра идемпотентен по uuid), ack помечает synced, после чего PhotoUploader дольёт файлы. Операции, не дошедшие до фиксации веса (ERR_NOT_ZERO и т.п.), локально не сохраняются: при обрыве связи запрос АИС всё равно уже умер по тайм-ауту центра. Параллельная команда — сразу ERR_BUSY. Общий тайм-аут (timeout_s из weigh_request) завершается кодом текущей фазы (WAIT_VEHICLE → ERR_VEHICLE_TIMEOUT и т.д.).

**08.08.2026 · Развёртывание центра: nginx проксирует ВСЁ в приложение, файлы напрямую не раздаёт.** Авторизация фото (сервисные токены + IP-allowlist + аудит) живёт в приложении — прямая раздача nginx'ом её обошла бы. Реальный IP клиента доходит до allowlist через X-Forwarded-For (uvicorn --proxy-headers; доверие любому прокси безопасно — порт app наружу не публикуется, до него дотягивается только nginx внутри сети compose). Миграции применяет одноразовый контейнер migrate, app стартует после его успеха. CENTER_ENV=production заставляет задать секреты явно (отказ старта с dev-дефолтами); V1_USERNAME/V1_PASSWORD могут остаться admin/admin (совместимость с АИС), но переменные обязаны присутствовать.

**07.08.2026 · В weighings оператор хранится строкой (operator), а не FK на users.** Ручные офлайн-операции приходят с агентов, чьи локальные операторы не обязаны существовать в users центра в момент досылки; строка с именем сохраняет запись самодостаточной и неизменяемой. FK operator_id из architecture §5 не используется.

**08.08.2026 · Механизм фото: метаданные — в WeighingRecord.photos, файлы — отдельной HTTP-загрузкой.** Метаданные снимков (роль, sha256, размер) едут вместе с записью в обоих каналах (weigh_result и офлайн-досылка) и фиксируются в контрольной сумме записи центром. Файлы агент догружает фоновым загрузчиком (POST /agents/photos/{uuid}/{role}, токен агента, ретраи до успеха) — независимо от WebSocket. Канонические пути /vesy/ГГГГ/ММ/ДД/<uuid>_photoN.jpeg формирует ЦЕНТР (front→1, rear→2, как в UniServer); имена файлов агента не используются. Центр сверяет sha256 тела с зафиксированным — подмена или порча файла отвергается (409). Миниатюра строится один раз при приёме; оригинал хранится байт-в-байт.

**08.08.2026 · В запрос v1 добавлены vehicle_number/trailer_number (ожидают подтверждения АИС).** Без номера ТС невозможны подстановка тары/расчёт нетто и попадание тарирования в реестр — пробел исходного контракта. Отсутствие полей не ломает операцию (tare/netto = null). Также зафиксировано: v1 всегда отвечает HTTP 200 с полем code (совместимость со старыми клиентами), путь эталонного эндпоинта — /api/v1/weigh.

**07.08.2026 · Время: везде Бишкек (Asia/Bishkek, UTC+6), в БД — UTC, в контрактах — ISO 8601 с явным поясом `+06:00`.** Отсутствие пояса в текущем контракте АИС признано ошибкой и исправляется в новом контракте (АИС подтвердить парсинг).

**07.08.2026 · Тара действует 3 месяца; единственный источник — тарирования в системе.** Механика UniServer «тара из справочника» и ручное занесение тары НЕ переносится. Оператор в офлайн-режиме вводит ТОЛЬКО номер АТС и номер прицепа и выбирает тип операции — все массы система определяет сама.

**07.08.2026 · Фото на взвешивании — 2 (перед-голова и зад-прицеп).** В UniServer 4 слота камер, но подключены и работают всегда две. Агент прожигает на снимок собственный оверлей: имя камеры, дата/время, зафиксированный вес (часам камер не доверяем).

**07.08.2026 · Ручная операция — одношаговая, как в ВесыСофт.** Решение Игоря: программа сама ждёт заезда и стабилизации массы, оператор вводит номера и жмёт «Взвесить» — в момент нажатия масса и снимки фиксируются и операция сразу записывается в журнал. Отдельного шага «Зафиксировать» (как было в макете operator-manual) нет; экран результата — информационный. Кирпичи prepare/commit/discard сохранены в ManualOperationFlow на случай сценариев с подтверждением.

**07.08.2026 · В weigh_request нет поля scale_id.** Architecture §4.2 описывает `{request_id, scale_id, params}`, но по схеме «одни весы = один ПК = один агент» WebSocket-соединение однозначно определяет весы — scale_id избыточен и стал бы источником рассинхронизации. Маршрутизацию по весам делает центр при выборе соединения агента.

**07.08.2026 · Хранение фото 5 лет, JPEG q85, без пересжатий.** Фото — файлами на диске, sha256 в БД, миниатюры генерируются один раз. Пересжатие запрещено: потеря качества + нарушение контрольной суммы (фото — доказательство). Объём ~130 ГБ/год, диск 1 ТБ достаточен.

**07.08.2026 · Доступ к фото — постоянные URL + сервисный токен в заголовке + IP-allowlist.** АИС «СВХ» забирает фото сервером (проксирует пользователям), поэтому подписанные протухающие ссылки не нужны. Каждому интегратору (АИС, в будущем таможня) — свой отзываемый токен. Все скачивания логируются.

**07.08.2026 · Разработка на эмуляторе индикатора.** К реальным весам не подключаемся без явного указания (боевые объекты). Эмулятор cas22 пишется первым, финальные проверки — выездом на объект.

**07.08.2026 · Код на английском, комментарии/коммиты/UI на русском.** Решение Игоря: команде сопровождения удобнее русский, идентификаторы — стандартный английский Python.

**06.08.2026 · Один весы = один индикатор = один ПК = один агент.** В т.ч. на КАНТе (двое весов = два агента). Снимает проблему удалённых весов (600 м) и упрощает агента.

**06.08.2026 · События в АИС — через существующий RabbitMQ организации, отдельный vhost.** Синхронная команда взвешивания остаётся HTTP (совместимый v1). Досылка офлайн-операций — событиями weighing.completed. Тот же контур, что события распознавания камер.

**06.08.2026 · Агент открывает исходящий WebSocket к центру.** Центр не стучится на объекты: устойчиво к сетям погранпереходов, проще firewall. Офлайн-буфер SQLite, досылка после реконнекта.

**06.08.2026 · Реестр тарирований реплицируется на агентов целиком.** Единый по всем объектам (тарирование и взвешивание могут быть на разных весах), компактный. Обеспечивает расчёт нетто офлайн. Правило: тара действует 3 месяца.

**06.08.2026 · Стек: Python 3.12 + FastAPI везде, PostgreSQL в центре, SQLite на агенте, HTMX/Jinja2 для UI.** Python уже на весовых ПК, драйвер CAS проверен, нагрузка малая, один язык проще сопровождать. Тяжёлые SPA-фреймворки не используем.

**06.08.2026 · Совместимый API v1 для АИС.** Центр принимает текущий формат запроса (legacy ip/autoscale = ключ маршрутизации) и отвечает текущей структурой + новые поля. Переход АИС = смена одного адреса. Параллельно вводится нативный v2 (site_id/scale_id, JWT).

**06.08.2026 · Протокол «CAS 22 byte» подтверждён практикой.** Непрерывный поток 22-байтовых пакетов, 9600 8-N-1, DTR/RTS не поднимать (CH340, ошибка 31 — лечится переоткрытием порта). Команды весам не требуются; обнуление — кнопкой на индикаторе.
