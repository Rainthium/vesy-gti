# Аудит защищённости центра — 04.11.2026

Проверка перед анализом инфобезопасности системщиками. Проверялись: код
центра (`center/`, `deploy/`), конфигурация на ВМ 192.168.140.70 (по SSH,
без sudo), внешняя доступность домена vesy.gti.kg, зависимости (pip-audit),
логи nginx/app за 14–30 дней. Значения паролей и токенов в документ не
попадают.

## Итог в двух словах

Прикладной уровень сделан аккуратно: секреты только в окружении, пароли —
PBKDF2, токены агентов хранятся хешем, сессии подписаны и привязаны к
паролю, перебор входа ограничен в два рубежа, API АИС закрыт токеном и
списком адресов, БД и порт приложения наружу не торчат, Swagger выключен.
Снаружи (через корпоративный прокси) — HTTPS Let's Encrypt, TLS 1.2/1.3,
HTTP → 301 на HTTPS. За 14 дней в логе nginx нет ни одного адреса
не из сети предприятия.

Главные дыры — не в коде, а в контуре и в обслуживании ВМ:

1. **Внутри сети всё ходит открытым текстом** — панель по
   `http://192.168.140.70`, агенты по `ws://` с токеном в заголовке, АИС по
   `http://` с сервисным токеном, RabbitMQ по AMQP без TLS. Любой, кто
   видит трафик на пути объект → ВМ (а 25.09 агент Аламедина ходил даже
   через публичный адрес AKNET), снимает токены и пароли.
2. **ВМ 86 дней без перезагрузки**, а ядро и libc обновлены на диске —
   `/var/run/reboot-required` ждёт с ядром 5.15.0-202 (работает 187).
3. **Pillow 12.3.0** — около 40 CVE, закрытых в 13.0.0 (центр им
   декодирует JPEG от агентов для миниатюр). Плюс multidict 6.7.1.
4. **Парольный вход по SSH включён** (cloud-init), хотя ключ — один.
5. **Роль БД `ves` — суперпользователь**: `REVOKE TRUNCATE` для неё
   ничего не значит, триггеры неизменяемости она может отключить.
6. **Резервных копий по расписанию нет** — crontab пуст, последние
   дампы — ручные, сентябрьские.

Остальное — «по красоте»: заголовки безопасности, `server_tokens off`,
свежий образ nginx, процесс в контейнере не от root, закрыть неиспользуемый
API v1 с admin/admin, журнал входов и админ-действий в БД, подпись релизов
агента, проверка firewall для 5672 (нужен sudo).

## Что уже хорошо (можно показывать системщику)

### Секреты и учётки

- Секреты только в `deploy/.env` на ВМ (права 600, в git нет); центр
  с `CENTER_ENV=production` **отказывается стартовать** с пустыми или
  dev-значениями (`center/app.py::_check_production_env`).
- Пароли панели — PBKDF2-HMAC-SHA256, 200 000 итераций, соль 16 байт,
  сравнение постоянного времени (`shared/passwords.py`); минимум 8 символов,
  admin/admin запрещён; логин по белому списку символов.
- Токены агентов — 32 случайных байта, в БД только sha256-хеш
  (`center/db/repo.py::hash_agent_token`); файлы с токенами в `~` на ВМ — 600.
- Учётка АИС в RabbitMQ `ais-svh` — только чтение своей очереди, без
  `configure`; панель брокера 15672 слушает 127.0.0.1.
- На ВМ один пользователь, один ED25519-ключ в `authorized_keys`, sudo
  только с паролем, `/etc/sudoers.d` пуст.

### Сессии и панель

- Cookie подписана (`PANEL_SECRET`), HttpOnly, SameSite=Lax (кросс-сайтовый
  POST cookie не получает — защита от CSRF без токенов, принятое решение
  13.08.2026); права и статус учётки перечитываются из БД на **каждый**
  запрос; штамп пароля в cookie — смена пароля выбивает все сессии.
- Open redirect закрыт (`_safe_next_path`: только `/panel/`, без `..` и `\`).
- Перебор входа: nginx `limit_req` по реальному адресу (последний элемент
  X-Forwarded-For от прокси) 1 r/s + общий потолок 5 r/s, в приложении —
  пауза по логину (10 неудач за 10 мин → 60 с, 429, PBKDF2 не считается).
  За 30 дней: 23 неудачных входа (из них 20 — тесты `throttle-test`/`adf`),
  7 ответов 429 — всё ожидаемо.
- Swagger/ReDoc выключены; шаблоны Jinja2 с автоэкранированием; LIKE
  экранируется; SQL только через SQLAlchemy.
- Загрузка релиза — только admin, имя файла по регулярке, zip проверяется,
  версии не перезаписываются; раздача релизов/инструментов — только с
  токеном агента, имена валидируются (обход путей невозможен).

### API АИС и фото

- v2: Bearer-токен **и** `AIS_ALLOWED_IPS` в приложении (с 21.10.2026) +
  `allow`-список в nginx. Адрес прокси в списках нет → через домен из
  интернета API недоступен (403/deny).
- Фото `/vesy/`: токен + allowlist + 50 r/s с адреса; путь файла
  проверяется на выход из хранилища; скачивания — в `audit_log`.
- v1 (admin/admin по контракту) — только с 192.168.15.9; **за 30 дней
  0 запросов** (все 8 объектов на v2).

### Контур и ВМ

- Наружу у ВМ слушают только 22, 80 и 5672; порт приложения 8080 и

## Находки

Приоритет: **A** — закрыть до/сразу после аудита, **B** — в ближайший
релиз, **C** — по красоте.

### A1. Нет TLS внутри сети (панель, агенты, АИС, AMQP)

Факт: агенты — `ws://192.168.140.70/agents/ws` (все 9 конфигов), панель
открывается по `http://192.168.140.70/panel/`, АИС 192.168.140.150 ходит на
порт 80 (84 077 запросов за 14 дней с токеном в `Authorization`),
RabbitMQ 5672 без TLS. `PANEL_COOKIE_SECURE=0`. В `docs/architecture.md`
§«Безопасность» TLS на всех соединениях заявлен, в nginx.conf блок 443 —
закомментированная заготовка.

Риск: перехват токенов агентов и АИС, пароля панели и cookie на любом
сегменте между объектом и ВМ. Токен агента = возможность слать операции
от имени весов; токен АИС = команды взвешивания и фото.

Что сделать (нужны системщики: сертификат):

1. Сертификат для ВМ — от внутреннего CA организации на имена
   `vesy.gti.kg` + `192.168.140.70` (SAN с IP), либо копия LE-сертификата
   с прокси (тогда только по имени и нужна внутренняя DNS-запись
   `vesy.gti.kg → 192.168.140.70` для агентов и АИС).
2. nginx: раскомментировать 443, `ssl_protocols TLSv1.2 TLSv1.3`,
   открыть `443:443`, порт 80 оставить только для 301 → https; прокси
   переключить на `https://192.168.140.70`.
3. Агенты: `url = "wss://vesy.gti.kg/agents/ws"` (или `wss://192.168.140.70`
   при SAN с IP); при внутреннем CA — корневой сертификат в хранилище
   Windows на 9 ПК **или** в комплекте агента (`certifi`-бандл + путь в
   config.toml — доработка агента). Переключать по одному объекту.
4. АИС: адрес `https://…` + их доверие к CA; RabbitMQ — 5671 с тем же
   сертификатом (`ssl_options` в rabbitmq.conf), 5672 закрыть после
   переключения АИС.
5. После этого `PANEL_COOKIE_SECURE=1`.

### A4. SSH принимает пароль

Факт: `/etc/ssh/sshd_config.d/50-cloud-init.conf` (27 байт, недоступен
для чтения без sudo — ровно `PasswordAuthentication yes`), в основном
конфиге строка закомментирована → пароль принимается. `fail2ban` не
установлен. Ключ в `authorized_keys` один, системщики заходят через
гипервизор — пароль по SSH не нужен никому.

Что сделать (под sudo):

```bash
sudo tee /etc/ssh/sshd_config.d/60-hardening.conf >/dev/null <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
MaxAuthTries 3
X11Forwarding no
ClientAliveInterval 300
ClientAliveCountMax 2
AllowUsers vesy
EOF
sudo sshd -t && sudo systemctl reload ssh
```

Проверить из второго терминала, что вход по ключу работает, **не закрывая
первый**. Пароль `vesy` остаётся для sudo и консоли гипервизора.

### A5. Роль БД `ves` — суперпользователь

Факт: `select rolsuper from pg_roles where rolname='ves'` → `t`
(`POSTGRES_USER` в compose создаёт суперпользователя). Суперпользователь
не подчиняется ACL — `REVOKE TRUNCATE` (deploy/README §4) для него
декоративен, триггеры неизменяемости (правило №2) он может снять
`ALTER TABLE … DISABLE TRIGGER`. SQL-инъекций в коде нет, но защита
«в глубину» отсутствует: компрометация приложения = полный контроль БД.

Что сделать: отдельная роль приложения без суперправ и без владения
таблицами.

```sql
CREATE ROLE ves_app LOGIN PASSWORD '…';
GRANT CONNECT ON DATABASE ves TO ves_app;
GRANT USAGE ON SCHEMA public TO ves_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO ves_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO ves_app;
ALTER DEFAULT PRIVILEGES FOR ROLE ves IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO ves_app;
ALTER DEFAULT PRIVILEGES FOR ROLE ves IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO ves_app;
REVOKE UPDATE, DELETE ON weighings, weighing_photos FROM ves_app;  -- неизменяемость и на уровне прав
```

В compose: `migrate` остаётся под `ves` (владелец, миграции), `app` —
`DATABASE_URL` с `ves_app` (`DB_APP_PASSWORD` в `.env`). Проверить тесты
и `tools/center_admin.py`/`tools/import_ais_tares.py` (они идут через
`docker compose exec app` — им нужен UPDATE по `tare_registry`,
`agents`, `users`; `weighings` они не правят — сторно пишет новую запись).
Это половина дня работы с проверкой на стенде.

### B1. Заголовки безопасности и версия nginx

Факт: ни панель, ни прокси не отдают `X-Frame-Options`,
`X-Content-Type-Options`, `Referrer-Policy`, `Content-Security-Policy`,
`Strict-Transport-Security`; по прямому IP nginx показывает
`Server: nginx/1.27.5`; образ `nginx:1.27-alpine` собран 16.04.2025
(ветка 1.27 закрыта, база Alpine 18 месяцев без обновлений).

Что сделать в `deploy/nginx.conf` (через прокси заголовки проходят):

```nginx
server_tokens off;
add_header X-Frame-Options SAMEORIGIN always;
add_header X-Content-Type-Options nosniff always;
add_header Referrer-Policy strict-origin-when-cross-origin always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
# после перевода на https (A1) — и на прокси, и здесь:
# add_header Strict-Transport-Security "max-age=31536000" always;
```

CSP — отдельно: панель использует HTMX и инлайн-скрипты графиков
(`charts.js`), нужен аккуратный список `script-src 'self'` + nonce; делать
после проверки на стенде. Образ — `nginx:1.29-alpine`.

### B2. Процесс центра работает от root в контейнере

Факт: `docker exec ves-center-app-1 id` → uid=0. В Dockerfile нет `USER`.
Побег из контейнера при уязвимости в приложении даёт root в контейнере

`photos` (один раз, `docker run --rm -v ves-center_photos:/d alpine chown
-R 10001 /d`). `migrate` может остаться от root.

### B5. Подпись релизов агента

Факт: агент проверяет sha256 и оглавление архива, которые сообщает центр.
Администратор панели (или тот, кто украл его сессию) может выложить любой

Что сделать: минимум — Ed25519-подпись манифеста релиза офлайн-ключом
(`tools/sign_release.py` на маке, публичный ключ зашит в агент, агент
0.4.38 отказывается ставить неподписанное); максимум — Authenticode на
`ves-agent.exe` (сертификат покупной). До этого — только один admin в
панели и короткие сессии.

### B6. Firewall для 5672 (RabbitMQ)

Факт: порт 5672 опубликован докером на 0.0.0.0 и **минует ufw**
(README §2а это помнит); проверить, кто реально может подключиться, без
sudo нельзя. Пароли учёток случайные, `ais-svh` только читает, но AMQP без
TLS (см. A1).

Проверить (под sudo):

```bash
sudo ufw status verbose; sudo iptables -S DOCKER-USER
```

Если в `DOCKER-USER` только `RETURN` — доступ к 5672 есть со всей сети.
Тогда:

```bash
sudo iptables -I DOCKER-USER -p tcp --dport 5672 ! -s 192.168.140.150 -j DROP
sudo iptables -I DOCKER-USER -p tcp --dport 5672 -s 192.168.6.116 -j RETURN
```

(и `iptables-persistent`, чтобы пережило перезагрузку), либо попросить
системщиков закрыть на внешнем firewall.

у камер слабые пароли (`admin12345`, `Qwerty12`, `qwerty12`) — это
инфраструктура объектов, а не наша, но системщик это увидит. Что в наших
силах: FileVault на маке, NTFS-права на `C:\vesy-agent\config.toml` только
SYSTEM + администратор, в агенте — не показывать токен на экране
«Диагностика» (проверить).
